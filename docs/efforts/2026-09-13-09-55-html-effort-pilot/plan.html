Two supported forms of an effort

Drew's second review keeps Markdown as a first-class choice for new efforts. Choose the representation according to the work's materials and planning needs. A bug fix with a short plan and log usually fits one note; an investigation with benchmarks, prototypes, or a substantial visual plan benefits from a folder. Task labels alone do not decide the format.

FormUse whenContent location
Markdown effortA concise plan and execution record fit naturally in one note.Inline sections, with ordinary links as needed.
Effort folderSeveral materials or a substantial plan deserve separate documents.An HTML entry note with explicit links to the plan, log, and collateral.

Recommended shared contract: an Effort interface implemented by the existing EffortNote and a proposed EffortWorkspace entry-note type. The entry note holds the folder effort's identity; the directory is its material location. Start with fields both forms actually share, such as ID, name, summary, status, and creation time.

Rhizome already uses interfaces such as SpecLike. A GraphQL union groups alternatives but does not declare shared fields, so an interface fits uniform effort reads. Authored unions are currently rejected by the ontology compiler. General union support should remain a separate capability decision rather than a prerequisite for this effort.

A shared interface does not normalize inline plans and linked plans by itself. Define one execution-context recipe or read contract that returns the effort's scope, plan, log, and approval evidence with precise source references. Preserve representation-specific writes, section identities, and existing approval meanings. Optional promotion from a note to a folder would need explicit identity and link preservation; no automatic conversion is required.
