# Stores / SQLite guidance

## Scope

The SQLite foundation under the unified `.rhizome/db.sqlite` code index and the separate durable `.rhizome/user-state.sqlite` preferences store. `pkg/sqliteutil` owns connection opening + pooling (`OpenDSN`, `pkg/sqliteutil/db.go`), DSN/pragma policy (`DSNWithOptions`), the custom CGO driver registration (`driver_cgo.go`), sqlite-vec auto-extension setup + probe (`sqlitevec.go`), the FTS5 query sanitizer (`FTS5QueryFromText`, `fts5.go`), corruption detection (`QuickIntegrityCheck`, `corruption.go`), WAL checkpointing (`Checkpoint`), and the per-domain migration runner (`pkg/sqliteutil/migration/runner.go` + `migration/domains/`). Consumers: the intel store (`pkg/anchors/sqlite/store.go`), note/code embeddings stores (`pkg/search/embeddings/sqlite`, `pkg/search/embeddings/codeindex/sqlite`, shared runtime in `pkg/search/embeddings/internal/sqlstore/runtime.go`), wired by `pkg/app/bootstrap/live.go` and `pkg/app/indexing`.

## Design constraints

- **Personal preferences are durable, independent data.** `pkg/app/userstate` owns ignored `.rhizome/user-state.sqlite` and its server lifecycle ([[view-preferences|SPEC-0114]]). Keep the database, WAL/SHM, and initialization sidecars out of Git. Index rebuild, replacement, and derived-store recovery must never reset it. Its own `user_state` migration domain uses the shared SQLite open, initialization lock, transaction retry, and local-filesystem policies; it is not part of the index writer queue or index lock. Never offer index rebuild as recovery for preference corruption or an unsupported future schema.
- **Worktree preference seeding is one-time and independent.** `rzm new-worktree` copies the whole personal-state database with the consistent copy-on-write clone or snapshot fallback. `userstate.SeedWorktree` holds the destination initialization lock and preserves any existing database or WAL/SHM sidecars. An absent source is optional. Copies retain revisions, legacy claims, and reset tombstones; later changes in either checkout are independent. Failed copies remove only the newly created destination files so a retry can seed again.
- **Preference mutations preserve unrelated keys.** Read snapshots are consistent, named-key patches are atomic and revision-fenced, and reset is transactional with tombstones. JSON null is a value, not removal. Each legacy source is claimed transactionally by at most one concrete instance, even when its import is suppressed. Unique sources can fill missing keys until a personal patch or reset permanently closes migration for the instance; imports never overwrite existing keys or restore changed or reset state. A new handle or server restart must retain those guarantees. Checkout ownership is implicit in the database; no cloud or cross-checkout sharing is provided.
- **Derived obligations survive interrupted indexing.** Intel v71 stores coalesced kind/path work, activation, retry deadlines, and attempts. Monotonic per-scope sequences survive acknowledgement to prevent delete/recreate reuse. A domain epoch invalidates path results after complete invalidation; a separate revision invalidates complete results after any path edit. Old acknowledgement or failure cannot clear or postpone newer work. Inactive obligations block computation until structural recovery activates them. Store retry metadata contains no provider error text or source content.
- **Structural fingerprints fence direct publications.** `DerivedSourceFingerprint` records the durable inputs used by a derived domain independently of watcher tickets. The runtime compares it under the publication lease before writing results from provider work. Vector, chunk, and score outputs are excluded so publication cannot invalidate itself.

- **Validation generations publish atomically.** Intel v66 stores complete diagnostics, checks, paths, scopes, and action membership in one write transaction. Lifecycle and the last published generation remain separate. Snapshot table inserts use the shared parameter-bounded `execValuesBatch` helper within the same atomic writer transaction. Reads pin a generation; retain the latest two published generations, reject expired cursors, and use indexed membership joins for bounded scope summaries. Persisted findings never grant repair authority.
- **Diagnostic queries share one filter.** Pages and scope summaries use `validationDiagnosticFilterSQL`, so a count always matches the list it links to. A `type` scope is the snapshot's explicit type rows plus issues with note membership in a note that `ontology_note_types` currently resolves to that type. An `interface` scope is its explicit interface rows plus issues in notes resolved to any implementing type; the store has no schema, so callers pass implementors in `ValidationDiagnosticFilter.InterfaceImplementors`, and without them an interface scope matches explicit rows only. Callers resolve implementors from the live schema on every request, and they are not part of the filter identity a pagination cursor checks (`json:"-"`). A cursor therefore stays valid for its generation across a schema change that alters an interface's implementors, and later pages apply the new membership, so the full traversal can miss issues that joined before the cursor position and mixes the two memberships; restart from the first page after such a change. `repairAvailability=applicable|inapplicable` tests for a `safe` or `needs_confirmation` action; `present|absent` test for any action, including `agent_required` guidance. `sort=file` keysets on (file key, `diagnostic_order`), where the file key is the primary path, else the first affected path, else `""`, and returns `fileTotals` for the file keys on the page. Intel v70 adds `variant_key`/`variant_label` (default `''`, meaning no variant) to `validation_diagnostics` with an index on `(generation, code, variant_key)`; the `variant` filter requires `code` and enters the cursor's filter identity. The v70 step, not the baseline statements, creates that index because `ResetDomain` retains validation tables. `GetValidationIssueGroups` reuses the scope-summary candidates CTE and filter in one `GROUP BY` over check, code, and variant, so each group's issue and affected-file counts equal the scope summary for the narrowed filter, and its applicable-repair count equals that summary's issue count with `repairAvailability=applicable`. The grouped read is bounded per code: it returns at most `ValidationIssueGroupVariantLimit` (25) variant rows by issue count, and a window rank folds the rest into one row with no variant and `otherVariants` set, so distinct file and repair counts stay exact. A row with an empty `variant_key` is reachable only through its code, because the `variant` filter cannot select "no variant"; no current producer mixes variant and variant-free findings under one code.

- **Intent cache provenance is atomic with its rows.** `ReplaceIntentEmbeddingSnapshot` replaces exemplar rows and their versioned provider fingerprint in one write transaction. Legacy rows without matching provider identity are not reusable. Publication during full indexing goes through the existing queued writer; snapshot reads observe one consistent database view.

- **Single-writer discipline is layered, not one mechanism.** Verified in code:
  1. **In-process shared write mutex.** Every store guards writes with `withWrite`/`withWriteTx` taking a `sync.Mutex` (`pkg/anchors/sqlite/store.go`, `sqlstore/runtime.go`). Bootstrap and indexing override each store's local mutex with **one shared mutex per DB file** via `SetWriteMu(&sharedWriteMu)` (`pkg/app/bootstrap/live.go`; `pkg/app/indexing/unified.go`). So all stores on the unified DB serialize writes on a single lock.
  2. **One queued writer lane for indexing.** `indexwriter.Writer` (`pkg/app/indexwriter/writer.go`) is "the single durable write lane": producers fan out, but every SQLite-backed write is submitted (`Submit*`) and flushed in batches by one goroutine (`run()`). Reached via context: `codeintel.WithWriteQueue` (`pkg/app/codeintel/write_queue.go`); ontology rebuilds share it through `deltaWriteQueue` (`pkg/ontology/sync.go`).
  3. **Cross-process `.rhizome/index.lock`** (`pkg/vault/indexlock`) prevents concurrent indexers.
  Why: SQLite WAL commits one writer at a time; write concurrency only buys `SQLITE_BUSY` retry storms. Serializing turns contention into observable wait/hold stats (`writeStats`, logged every 200 writes).
- **Write transactions retry, but only on busy/locked.** Code and both embedding stores use `sqliteutil.ExecTxWithRetry` while holding their existing writer mutex. Only typed SQLite busy/locked failures retry (at most five attempts), with cancellation-aware waits of 50/100/150/200 ms and no wait after the final failure. Permanent failures return immediately. This aligns Intel's former exponential jitter with the embedding stores' linear schedule. Callbacks may run repeatedly and must keep their effects inside the transaction.
- **Batching is the throughput lever.** The queue accumulates per-kind batches with rows/bytes/idle flush policies (e.g. code: 512 rows / 8 MiB / 100 ms) and persists each batch as one transaction. Store-level batch APIs (`ApplyCodeIndexBatch`, `pkg/anchors/batch.go`) exist so a flush is one tx, not per-row autocommits.
- **DSN/pragma policy is centralized** in `sqliteutil.DSNWithOptions`: `_journal_mode=WAL`, `_synchronous=NORMAL`, `_busy_timeout=30000`, `_foreign_keys=on`, `_cache_size=10000`, and internal per-open `_txlock=immediate|exclusive` through `DSNOptions`. Non-positive `BusyTimeoutMs` retains the 30-second default; explicit `NoBusyWait` takes precedence and sets the native timeout to zero on every connection. Managed read-only Intel handles opt into no wait so lock contention returns immediately, including during initial connection setup before context-aware schema validation; contention remains an operational error and never authorizes repair. Session handles retain their 100 ms wait and ordinary writers retain the default. Transaction locking is not user-configurable; `RHIZOME_SQLITE_TXLOCK` is ignored. The registered driver `sqlite3_rhizome` sets `mmap_size` (default 1 GiB, `RHIZOME_SQLITE_MMAP_SIZE`) via ConnectHook. Pool defaults `MaxOpenConns=4` (`OpenDSN`) — multiple readers, writes still funnel through the shared mutex. Never hand-roll a DSN.
- **Creation and migration of a database file are serialized across processes.** Every write-capable store open (`anchors/sqlite`, `embeddings/sqlite`, `codeindex/sqlite`, own pool or shared pool) holds `sqliteutil.LockSchemaInit` on `<db>.init.lock` from before its first connection until the schema is validated. The lock resolves the full database path through the same `paths.ResolveSymlinks` helper as the DSN, so an existing database-file symlink and a shared pool use the same sidecar. For a missing database, the lock creates and canonicalizes its parent directory. SQLite cannot do this alone: the switch into WAL mode and a deferred migration transaction both upgrade a read lock to a write lock, which SQLite refuses immediately instead of waiting for the busy timeout, and two migrators reading the same version replay non-idempotent steps. The lock is a `flock`/`LockFileEx` sidecar released on process exit, waited on without bound but honouring cancellation, and skipped on a filesystem that refuses it. Read-only opens take no lock.
- **WAL databases stay on a local filesystem in one host/VM.** `OpenDSN` rejects known shared/network filesystem types (`virtiofs`, FUSE, NFS, CIFS/SMB, 9p, and similar) because SQLite WAL depends on coherent POSIX locks and shared memory. This explicitly excludes a host process and container process opening the same Docker bind/passthrough database. `RHIZOME_SQLITE_ALLOW_UNSAFE_FS=1` is an expert-only escape hatch after independently verifying those semantics.
- **The bundled SQLite must include the WAL-reset corruption fix.** The vendored `mattn/go-sqlite3` version embeds SQLite 3.51.3 or newer; `TestOpenDSN_SQLiteIncludesWALResetCorruptionFix` pins that floor.
- **Migrations are per-domain versioned plans.** `migration.EnsureDomain` tracks `rzm_migration_state`/`rzm_migration_log`, sets a `dirty` flag, runs each forward `Step` in its own transaction, supports `DiscoverLegacyVersion` for pre-state DBs and a post-migration `Validate` that returns `ErrSchemaDrift` only for observed structural mismatches (including absent required schema objects). Operational validation errors retain their classification and never authorize Intel reset; managed existing-only opens likewise propagate proof-read failures without relabeling them as schema drift. Missing or mismatched proof, structural errors, corruption, and future schemas remain unavailable to managed readers; newer-than-supported DBs fail with `ErrFutureSchema`. Index-domain errors offer `rzm index --rebuild`; personal-state errors require an upgrade and never suggest rebuilding durable data. Index domains: `intel`, `note_embeddings`, `code_embeddings` (`migration/domains/`). Personal preferences use an independent migration domain and database owned by `pkg/app/userstate`; the index reset rules below do not apply to it. Intel is derived and uses a consolidated v56 baseline: fresh/reset domains bootstrap that baseline once instead of replaying historical migration commits, versions before v56 and dirty/drifted v56 domains reset only Intel, and only post-v56 changes enter the forward migration plan. Intel v61 is the append-only source/projection provenance step; it backfills legacy note rows as Markdown plus `stale` projection state without rereading source or claiming current parser output. Note/code embedding domains remain untouched by Intel recovery.
- **Graph score replacements batch SQL inside one transaction.** Document and anchor scores use the existing 900-parameter values helper (112 document rows or 300 anchor rows per statement). Argument preparation, filtering, validation and cancellation checks precede the writer lock. Input order, last-write duplicate replacement and the initial delete remain within the original `withWriteTx`; internal chunks never commit separately. Revision triggers remain active and roll back with score rows.
- **Graph cache freshness is transactional.** Intel v62 introduced a singleton database incarnation and graph revision; v63 narrows the `notes` update trigger to `UPDATE OF path, title` so indexing metadata the web graph never reads (`mtime`, `content_hash`, `indexer_version`, key/segment columns) no longer invalidates cached graph responses. Graph-input triggers advance the revision within the writing transaction; rollback restores it and external-only evidence stays excluded. Reads use one singleton query through the existing pool. Migration validation compares stored trigger SQL against the current specs, so any trigger change requires a schema version bump plus a migration that drops and recreates the affected triggers. Older binaries reject v63: stop all processes and restore a pre-upgrade index or explicitly rebuild derived state with the older binary for rollback, without automatic downgrade or live-file replacement.
- **Warm schema proofs are validation results, not timestamps.** A current Intel domain may skip repeated DDL and exhaustive validation only when one coherent probe matches migration target, clean state, the code-owned schema-plan fingerprint, and SQLite `schema_version`. Missing, legacy, dirty, mismatched, externally changed, corrupt, or future state falls back to the authoritative ensure/validate path (or its existing hard failure); the proof is refreshed only after successful full validation. Successful Intel maintenance (`ANALYZE`, `PRAGMA optimize`, and `VACUUM`) revalidates the existing schema and refreshes that proof when SQLite changes its schema cookie, so completed indexing remains readable without reopening a writer. Maintenance propagates validation failures and never repairs or approves schema drift. Validation and proof publication retry together through the existing bounded, cancellation-aware transaction retry if a concurrent writer invalidates the read snapshot; validation callbacks keep effects inside the transaction.
- **Session dedupe separates reservations from committed history.** Candidate keys are reserved in bounded set-oriented batches with opaque ownership, then emitted keys are committed and omitted owned keys released in a second batch. Existing committed rows remain seen across migration, abandoned reservations are TTL-reclaimable with bounded future-clock skew, and cleanup is read-before-claim due-gated so ordinary one-shot opens do not write merely to discover that cleanup is unnecessary.
- **FTS5 requires a build tag.** mattn/go-sqlite3 only compiles FTS5 with `-tags "fts5"`; the Makefile passes it everywhere (`CGO_TAGS`). FTS MATCH input must go through `FTS5QueryFromText` — it quotes tokens so user text can never inject FTS5 operators. CGO required; the `!cgo` driver fallback (`driver_nocgo.go`) is a stub name only.
- **sqlite-vec is mandatory at open**: `OpenDSN` registers the auto-extension and probes `vec_distance_cosine`, failing fast if unavailable.
- **Corruption is distinguished from contention**: `QuickIntegrityCheck` retries transient busy/locked errors with backoff and only reports `IntegrityCheckFailed` for a real non-ok integrity result (used by scheduler maintenance, `pkg/app/bootstrap/schedulers.go`).
- **Rich agent commands query existing validated state read-only and persist only bounded session dedupe.** The ordinary Intel-store open runs `QuickIntegrityCheck`, including default runtime and explicit `rzm index` paths. Explicit rich one-shot commands instead open the existing database with SQLite `mode=ro` and `query_only`, accept only the current validated migration proof, and perform no directory/database creation, migration, repair, session cleanup, or indexed-state writes. A separate existing-only, single-connection handle may write only through the narrow `SessionDedupeStore` capability; each operation has a short timeout and fails open under contention. Missing or incompatible state becomes fail-soft indexed-context remediation. Minimal start opens no store at all. Unsafe-filesystem refusal, DSN read policy, future-schema rejection, and normal SQL failures remain authoritative. Do not reuse these open paths for serve, index, maintenance, or general callers.
- **Rationale FTS schema belongs to initialization.** Fresh/reset/migration assembly establishes the rationale FTS table, rowid map and index, and store validation checks the exact FTS5 definition, map columns and required index. The versioned validation fingerprint prevents old proofs from bypassing stronger checks. Rationale search, replacement and deletion issue no permanent schema DDL; failures after open remain SQL errors instead of triggering lazy repair.
- **Read paths probe vector tables before DDL.** A fresh store handle must first check whether the dimension-specific Intel vec table already exists and cache that readiness. Current-index queries therefore execute zero vector schema statements, including on `mode=ro`/`query_only` handles. Only write-capable indexing/runtime paths may create a genuinely missing vec table.
- **Vector owner filters use immutable vec partitions.** Intel v67 stores normalized chunk `owner_type` beside each embedding as a sqlite-vec partition key. The numbered migration stages exact vector blobs in the migration transaction, recreates each dimension table, restores rows with orphan vectors assigned to the empty partition, and validates the partition column before publishing the version. KNN queries apply non-empty owner filters at the vector table while retaining the eligible-chunk join for path, kind, granularity, note-type, and test filters. Unknown owner values remain restrictive; an empty owner filter remains unrestricted.
- **Current metadata authorizes vector identity and dimension.** All Intel embedding query lanes require `intel_embeddings.chunk_row_id` with the query's dimension before KNN selection or scalar limits. The metadata FK cascades with chunk deletion, so unfiltered and owner-only KNN can use its row-ID set directly without an extra chunk join. Filtered KNN and scalar search join the same eligible metadata set with current chunks. Retained orphan vectors and previous-dimension rows remain stored but cannot establish searchable identity; vector bytes remain the scoring source.
- **Embedding publication batches identity reads with writes.** `UpsertEmbeddings` resolves chunk IDs with one parameter-bounded query per existing 50-row publication batch, inside its writer transaction. Missing chunks and empty embeddings remain skipped. Stable input ordering, mixed dimensions, vector-owner partitions, and the single final generation advance remain unchanged; a failure in a later batch or generation publication rolls back metadata and vector bytes from every batch. Never cache row IDs or resolve them before the transaction.
- **Chunk content retires stale embedding evidence atomically.** Both chunk replacement APIs compare each chunk ID's final effective incoming hash with existing chunks before upsert, using parameter-bounded batches inside the replacement transaction. This final-hash view follows existing natural-key deduplication and preserves sequential upsert order, including repeated IDs across batch boundaries. A changed hash deletes its canonical embedding metadata and ontology embedding sidecar; equal hashes, other owners, and sibling families retain their evidence. Physical vectors and content-hash caches remain stored. A later chunk-write failure rolls back retirement and publication together. Metadata-count changes invalidate the composite search fingerprint immediately without an extra embedding-generation advance. Previously overwritten hashes cannot identify already-stranded metadata; explicit `rzm index --rebuild` repairs that derived state.
- **Automatic DB/WAL/SHM removal is disabled.** The index lock is not a lifecycle lock held by every database opener, and SQLite cannot portably bridge a closed-handle checkpoint into atomic file deletion. Corrupt, incompatible, or full-replacement rebuilds preserve the files and instruct the operator to stop every Rhizome process and move the DB plus sidecars aside manually.
- **Keys are vault-root-relative paths** via `pkg/paths` (`VaultPaths.RelStrict` family); absolute or escaped paths must never enter SQLite (AGENTS.md path-normalization rule; `paths` import in `pkg/anchors/sqlite/store.go`).
- **Startup enrichment reads are scoped in SQL.** Exact-file and directory-subtree code-to-note lookups normalize vault-relative targets, apply directory-boundary predicates, deterministic ordering, and a hard SQL `LIMIT` before returning rows. The normalized empty subtree is the bounded whole-vault root; file readers still reject empty keys and all readers reject path escapes. Graph-summary reads require persisted score evidence and fail soft when it is absent. Do not use graph-wide readers followed by in-memory filtering for latency-sensitive context.
- **Indexed ontology summaries use authored-type projections.** Read schema readiness/materialization from `ontology_schema_state`, totals from `notes`, and bounded public type counts/examples from `ontology_note_types`. Do not enumerate `ontology_nodes` for public type summaries because it also stores internal fallback catalog nodes.
- **Ontology facts and catalog publish together.** `OntologyDelta.ReadModels` are applied in order inside the delta transaction. A failed replacement rolls back the rebuild clear and preserves the prior catalog. A later full rebuild supersedes earlier buffered deltas; incremental publications retain their catalog order. Validation uses `ApplyOntologyDeltaPreservingSemantic` to preserve independent semantic data.
- **Ontology semantic cleanup is mode-specific.** `ReplaceOntologyNodeReadModel` remains the full-index catalog replacement and prunes stale ontology-owned chunks/embeddings/sidecars. Validation projection uses `ReplaceOntologyNodeReadModelPreservingSemantic`, which converges catalog and field rows without advancing or pruning those independent semantic domains. Semantic lookup binds preserved chunks through canonical `intel_chunks.owner_id = ontology_nodes.node_id`; integer row IDs are replaceable storage details and must not become ownership keys.
- **Ontology state records materializer identity.** `ontology_schema_state.materialization_version` distinguishes stale-but-internally-consistent derived rows across binary upgrades. Migrations default existing rows to zero so the ontology coordinator performs one full rebuild and republishes the current version. Intel v64 adds `has_issues`/`type_ambiguous` to `ontology_note_assessments` with default 0; the materialization bump, not the migration, populates them.
- **Note source and provider projection state are independently durable.** `notes.format_id` is authored-source identity; Store and SQL accept only non-empty lowercase trimmed IDs. One-to-one `note_projection_state` records provider/projection versions, source-hash basis, `stale`/`current`/`fatal` status, diagnostic code/detail, and update time. SQL requires non-empty `current` version/hash fields and non-empty `fatal` versions/diagnostics; Store writes additionally enforce source-hash equality against the note row whenever a hash is available. `stale`/`current` reject diagnostics. The existing note snapshot/delta write transaction replaces this state with the note's derived metadata and deletes it with the source row. Raw Store readers remain gated by global metadata readiness and can expose migration-stale legacy rows. `notemeta.Indexer` publishes current/fatal state, includes selected provider/version freshness, and gates source/graph reads on provider-current rows. Do not add a side writer or mark migration backfill current.
- **Projection collections publish with source state.** Intel v65 migrates `note_markdown_targets` to `note_fragment_targets`, preserving heading and block rows while admitting element IDs and legacy names. It adds ordered `note_projection_diagnostics` and `note_search_regions`. Snapshot and delta APIs batch and replace these rows inside the same `withWriteTx` as source and projection state. Fatal summary columns remain exact derived compatibility data; consumers use the diagnostic collection as truth.
- **Exact-note fact bundles use one read snapshot.** `DurableNoteFactsByPaths` reads metadata, property values, and tags for canonical paths through one short read-only transaction and returns no partial bundle on error or cancellation. Consumers may filter provider-stale paths after the transaction, but must remove their associated properties and tags and must not reread those facts during the request.
- **Ownership transitions fail closed and carry durable reconciliation debt.** `ApplyOwnershipTransitions` retires note/code/search/graph/ontology rows and publishes replacement note source provenance in one `withWriteTx`. An exact note-source re-publication is an atomic no-op when there is no coexisting code owner and durable source identity, filesystem facts, provider versions, projection status, and diagnostics match; a new observation time alone does not invalidate metadata or advance reconciliation. Current note source and coexisting code ownership are read in parameter-bounded batches inside that transaction. Reverse-index rows are retired for the complete effective path set in bounded batches, followed by one orphan-target cleanup even when root owner rows are missing. An effective transition returns sorted affected source paths plus affected note-anchor IDs, removes only anchors that became orphaned, deletes `note_metadata_state` so legacy freshness cannot falsely no-op, and advances an `index_metadata` reconciliation generation in the same transaction. `PendingOwnershipReconciliation` survives process interruption; `AcknowledgeOwnershipReconciliation` clears the obligation only for the exact current generation. The metadata layer has no state-only publication write: its complete delta is the barrier that keeps source, metadata, and ontology aligned. Shared structural orchestration must rederive the returned dependencies, perform complete structural recovery when a generation remains pending, and acknowledge only after structural publication and derived-work activation are durable.
- **Both structural drivers use typed queued-writer ownership controls.** `SubmitOwnershipTransitions` fences all earlier durable writes before one atomic replacement transaction; `AcknowledgeOwnershipReconciliation` similarly fences the final exact-generation acknowledgement. Neither is a general queued closure, and neither may be replaced by a direct coordinator write. A failed or cancelled structural publication leaves the durable generation pending for coarse recovery. Once structure is committed, separate derived obligations own semantic and graph retries.
- **Untouched-domain evidence stays narrow.** Validation projection reads count/max-generation summaries for files, anchors, chunks, embeddings, and graph-score tables. The graph-web revision tracks response-cache freshness and is not a substitute for these domain-specific validation summaries.

- **Code batch freshness is atomic with its artifacts.** `ApplyCodePersistenceBatch` commits summaries/metas, references/external evidence, Intel and rationale together in one `withWriteTx`; internal statement chunks never commit separately. A failed or canceled batch preserves prior complete rows so hash guards cannot skip an unfinished projection. The queue bounds normal batch size; individual oversized files remain possible. Service-level doc-link writes precede this DTO and are outside this atomic seam.

- **Validation invalidation is one transaction.** `MarkPublishedValidationStale` retains the published snapshot, marks its freshness, and advances the existing `validation_state.generation` even when no snapshot exists. This fences late publication and error completion. A superseded running state becomes `ok` with retained results or `never_ran` without them; the next admitted run allocates a newer generation. No schema or persistent failure latch is needed.

## Must-dos when changing this subsystem

- Route every new durable write through the existing lane: inside indexing, add a `Submit*` + handler on `indexwriter.Writer`; inside a store, wrap with `withWrite`/`withWriteTx` so the shared mutex and retry/backoff apply. Never call `db.Exec` for writes from new code paths.
- When constructing a new store on an existing DB file, wire `SetWriteMu` to that DB's shared mutex (follow `pkg/app/bootstrap/live.go`).
- Batch: accept slices in store write APIs and execute them in a single transaction; give queue-level kinds a flush policy and flush in both `flushAll` and `flushExpired`.
- Schema changes: add a numbered `Step` to the right domain plan in `pkg/sqliteutil/migration/domains/`, bump the domain `Target`, keep DDL idempotent within the step's tx, and extend the domain `Validate`. For Intel, append only post-v56 forward steps and keep the consolidated fresh-schema baseline synchronized. Never `CREATE TABLE`/`ALTER` outside the runner or the Intel baseline bootstrap for migrated tables.
- Open connections only through `sqliteutil.OpenDSN(sqliteutil.DSNWithOptions(...))` or `sqlstore.OpenDB`; keep pragma changes in `DSNWithOptions` so all handles agree.
- Do not bypass the WAL filesystem check. A new open path must produce the same unsafe-filesystem refusal and actionable override diagnostic.
- Run tests with the FTS5 tag (`go test -tags "fts5" ...` or `make test`).

## Review checklist — problems to catch

- A write-capable open path that creates or migrates schema outside `sqliteutil.LockSchemaInit`, or a lock taken after the first connection opens.
- Direct `db.Exec`/`tx` writes that bypass `withWrite*`/the queued writer lane (silent contention with the shared mutex holders).
- New store on the unified DB without `SetWriteMu` wiring — two uncoordinated writer locks on one file.
- Per-row statements in loops where a batched multi-row insert or one wrapping tx would do; queue submits without a batch policy.
- Long-held write transactions (provider calls, file I/O, network inside `withWriteTx`) — they hold the shared mutex and block every other store's writes.
- Schema change without a migration step / `Target` bump, or DDL executed outside `migration.EnsureDomain`.
- Absolute or non-vault-relative paths used as row keys (use `pkg/paths` strict helpers).
- FTS tables written without the matching content sync, or raw user text passed to `MATCH` instead of `FTS5QueryFromText`.
- Connection or statement leaks: stores own one `*sql.DB` with a `closeFn`; don't open ad hoc handles per call, and close `rows` on every read path.
- Retry loops that retry non-retriable errors (mask real bugs) or skip backoff (busy-spin on the writer lock).
- New code importing `mattn/go-sqlite3` directly instead of going through `sqliteutil` (loses mmap hook, sqlite-vec, pragma policy).
- Any automatic rebuild/recovery path that removes DB/WAL/SHM files without a lifecycle lock held by every opener.
- `SkipIntegrityCheck` propagated by a caller other than `rzm agent start`, or an index/default open that no longer runs `QuickIntegrityCheck`.
