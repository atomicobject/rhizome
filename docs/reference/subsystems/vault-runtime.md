# Vault runtime guidance

## Scope

- `pkg/app/runtime`: discovery and client contract. `InstanceManifest` (`.rhizome/runtime.json`, mode 0600, carries run id, build id, mode, control token), `LiveManifest`/`Probe` with three error classes, `Ensure` (find or spawn a headless runtime under the spawn lease), the loopback control routes and timing constants, `AutostartEnabled`/`IdleTimeout` configuration, and the global instance `Registry`.
- `pkg/fileio` owns the cooperative read and namespace replacement primitives used by runtime manifests, registry entries, and port preferences as well as repository configuration. Runtime publishers retain their temporary-file and permission responsibilities; the lower-level OS contract is documented in the vault-core note.
- `pkg/app/bootstrap`: `LiveRuntime`, the phased async bootstrap for long-running processes and one-shot commands; election on `.rhizome/runtime.lock` (`live_election.go`); leader indexing startup (`live_indexing.go`) and the indexing lane (`lane/`): the single serialized executor for boot catch-up, watcher ownership batches, validation projections, embedding cycles, graph cycles, and explicit index jobs.
- `pkg/app/cli/serve`: serve orchestration below Cobra: readiness gates, interrupted-write recovery, `ControlHooks` assembly into `web.RuntimeControl`, headless lifecycle (log file, idle exit, root removal), `rzm stop`.
- Consumers: `cmd/serve.go`, `cmd/stop.go`, `cmd/index.go` (delegation), `cmd/agent_code_serve.go` (agent operations), `cmd/agent_start.go` and `cmd/mcp.go` (ensure only). Contract: [[vault-runtime-coordination|SPEC-0104]].

## Diagnostics

- Command execution installs one per-vault process recorder under `.rhizome/diagnostics`. Serve carries its recorder through async bootstrap, the indexing lane, and HTTP requests without changing cancellation or election authority. Embedded serve callers open a recorder only when no command recorder exists. Diagnostics failures remain advisory.
- Capability phases publish independent readiness and duration reports. Runtime ensure records probe counts, unresponsive probes, spawn lease waits, attachment, spawn, and headless replacement. HTTP requests record registered route, method, status, bytes, duration, and terminal outcome. Catalog tools record actual Go errors and structured MCP `IsError` failures. Request and tool traffic uses events rather than individual report files.
- Control clients propagate opaque hexadecimal trace and parent operation identifiers. The server accepts those identifiers only for authorized loopback control requests. No arguments, queries, request bodies, headers, credentials, or provider response text enter structured diagnostics. Legacy standard logs retain severity, component, finite cause categories, and an explicit redaction marker. Runtime initialization and repair recovery use explicit named events instead of that fallback.
- Headless process output and pre-election child startup errors use `.rhizome/diagnostics/runtime-output.log`; the elected Go-output capture caps each file at 5 MiB with one retained rotation, marking retained tails when a write exceeds the cap. An inherited native descriptor remains available for pre-election errors and runtime crashes; abrupt native writes can temporarily exceed that allowance, and the next spawn/capture open retains a bounded tail. Windows retains null inherited descriptors so an inherited log handle cannot prevent rotation. This raw crash/startup fallback is distinct from authoritative structured events and reports. Existing `.rhizome/runtime.log`, `logs.d`, and `logs` files are left untouched and receive no new writes.

## Design constraints

- **Structural readiness precedes provider completion.** Debounced watch-hub events wake structural reconciliation directly; the periodic tick remains a recovery mechanism. Ordinary rewrites do not wait for the former per-path cooldown. The watcher publishes `node.changed` only after shared structural publication commits, and derived completion publishes `index.changed` with the completed domain. Resync invalidation does not replace the subsequent committed-path event. Open panes refresh affected successful or pending reads on committed path events, because raw file-watch reads can precede catalog type publication.
- **Derived computation releases the writer lease.** The runtime scheduler reads durable work on startup and quiet retry ticks, prepares under a lane job, computes outside the lease, and publishes through bounded lane jobs after checking work identity and structural inputs. Explicit indexing and external priority cancel computation. Shutdown cancels and joins computation and publication before stores close; cancellation alone is not completion.
- **Desktop uses the existing runtime owner.** The desktop bridge resolves the exact executable, requires its headless capability, verifies existing manifest and health folder identity and loopback origin, then calls `Ensure` with that executable's build identity. External-manager shims retain their manager's build authority, so their shim file is never used to derive a runtime replacement identity. It never exposes control tokens to the native UI or stops a runtime when a window closes. Discovery probes reject HTTP redirects, so a manifest grants authority only to its recorded listener.

- **Replacement fallback restarts after indexing.** When an index job loses its runtime because the database was replaced or the owner exited, the outer index/worktree command owns any restart. It restarts only after in-process indexing and its cleanup return, including failure cleanup; the delegation helper never spawns a successor over an unfinished replacement.

- **Validation follows filesystem changes and supports manual refresh.** Filesystem reconciliation invalidates validation for note, code, schema, configuration, and query-recipe changes. The readiness coordinator queues a debounced replacement after successful reconciliation. The Problems page can also request a runtime-owned refresh through `POST /api/v2/validate/refresh`; it keeps prior results visible while validation runs. Startup and queued refreshes wait for the boot index attempt, including any explicit index that supersedes it, before they may create projection state. Projection writes join the indexing lane and retry after interactive preemption while their request remains valid. The suite runs after projection releases the lane. Both success and failure publish a validation event so the browser receives the terminal state.

- **One runtime per vault root, decided by the lock, published by the manifest.** A process becomes the runtime only after `TryAcquire` on `runtime.lock` succeeds; it writes `runtime.json` only after the listener is bound; it removes the manifest only when the manifest still names its own PID, and before it releases the lock. `fileio` manifest readers share deletion on Windows so polling cannot block owner cleanup or replacement: `writeFileReplace` calls `fileio.Replace` with POSIX semantics (`FileRenameInfoEx`), which replaces a target held open with delete sharing, and falls back to `os.Rename` only where POSIX rename is unsupported. Registry listings read instance files the same way; a reader that does not share deletion can still block replacement. Failed manifest replacements preserve the published file so readiness updates can retry without losing discovery. An election loser exits with `ExitCodeAlreadyRunning` (3) and touches nothing. The runtime also records its bound port in `.rhizome/runtime-port`, which shutdown leaves in place; with `--port 0` the next start tries that port first and falls back to a random one (then recorded) when it is taken. The port file is a preference, never discovery: clients find a runtime only through the probed manifest.
- **A manifest is evidence, not truth.** Clients trust it only after `Probe` answers with the manifest's run id and PID. Nobody listening means absent (the manifest is written after listen); a different process answering means absent; listening but unhealthy with a live PID means unresponsive, and unresponsive callers wait rather than spawn. The shared lock primitive recovers a dead owner from a proven earlier local boot, requiring the exact hostname and acquisition before this boot; foreign or uncertain identities remain protected. A live election owner without a manifest is starting or stopping, not an absent runtime: discovery avoids a competing spawn, and stop waits for publication or ownership release within its grace period.
- **Startup remains discoverable before HTTP publication.** A pending token is registered before detaching a child; elected owners register before write recovery. Stop and stop-all cancel that token and wait for cleanup, while manifest publication checks the same cancellation gate. Successors have different tokens and cannot be canceled by an older stop. Elected startup records, watcher lookups, and cleanup use the canonical vault path captured at startup, so disappearance of an alias cannot strand an intent or trigger a false cancellation. Live registry entries survive old heartbeats.
- **Startup-record readers participate in the intent gate.** Polling and stop-all discovery serialize their reads with startup-record replacement and removal. Otherwise an open reader can deny cancellation's file replacement on Windows. Gate waits honor the caller's context and the existing startup or stop deadline; mutators already inside the gate use the internal reader without reacquiring it. A partial stop-all discovery retains known targets, stops them, and reports incomplete discovery instead of abandoning unrelated runtimes.
- **Spawning is leased.** `Ensure` takes `runtime-spawn.lock` before starting `serve --headless`; losers wait and re-probe. Election makes a double spawn harmless, the lease makes it rare. The spawned child is detached from the client's session and terminal on every platform and never waited on beyond the spawn budget.
- **The lane owns background indexing locks.** Every indexing writer submits a `lane.Request`; the lane acquires `.rhizome/index.lock` per job with the job kind as `Role`, polls priority every second, cancels background jobs for explicit jobs or external priority, and requeues cancelled background work. `rzm index` submits an explicit job and renders its events. Interactive repair and edit saves retain their repair-engine lease, requesting priority and waiting cancellably for the lane to yield; priority requests from the runtime's own PID are honored.
- **Priority cancellation reaches validation.** Boot indexing runs the configured validation snapshot before relinquishing its job lease. Identifier migration checks cancellation between notes, recursive sections and reference scans; the suite returns cancellation after joining its checks and never publishes partial repair authority. A canceled boot attempt leaves ownership reconciliation pending and the existing submitter retries it after priority clears.
- **Watcher inputs survive cache reads.** The semantic watcher retains hub events and resync notices independently of the cache until its destination batch succeeds. A cache refresh by a save or reader cannot consume embedding and graph work; events received during a running batch remain for the next batch, and retry preserves newer events.
- **Watcher job outcomes report structural reconciliation.** Required structural destination, cache-refresh, and reconciliation-debt read errors reach the lane's handle, terminal event, and last-error status. Job-context cancellation takes precedence after work drains, preserving explicit preemption identity. The watcher retains failed inputs and pending generations for retry. Provider failures belong to durable derived work and do not change an already committed structural result.
- **The runtime never outlives its database file.** A lane preflight compares the database on disk with the file the runtime opened; a deleted, renamed, or replaced database fails the job with `lane.ErrDatabaseReplaced` and shuts the runtime down so the next client starts one against the new file. `rzm index` falls back to in-process indexing and restarts the runtime.
- **A pre-upgrade serve still owns its vault.** Election, `Ensure`, and status recognize a live `watcher.lock` owner and refuse to compete; a new owner clears the stale legacy files.
- **Writable code readiness survives brief opening contention.** Phase 3 retries only typed SQLite busy/locked opening failures within 30 seconds of the first attempt, with cancellable exponential waits from 100 ms up to one second. It publishes neither a store nor a terminal capability error between attempts. Missing or incompatible indexes still fail immediately. The recovery policy applies to owned and shared writable handles, which retain their native per-attempt busy timeout. Read-only one-shot runtimes attempt opening once and return SQLite contention promptly to their fail-soft consumer. An in-flight native call may outlast the recovery window, but no new attempt starts afterward. It never replays a published phase. Shutdown cancels waits and prevents further attempts while draining any in-flight native open.
- **Concurrent openers of a fresh database do not race.** A one-shot command and the headless runtime it auto-starts create the same database at once; every write-capable store open holds `sqliteutil.LockSchemaInit` across creation and migration (see the stores note), so the loser waits and finds a finished schema instead of a permanent `database is locked` code phase.
- **Background work never rewrites configuration.** The boot catch-up runs with `SkipConfigPersistence`; only an explicit index persists resolved settings, because a config rewrite invalidates open code-mode connections.
- **Runtime-executed agent operations keep one-shot freshness.** Only cache-snapshot plans get the runtime's note cache, after `MarkStale` plus a completed recrawl; every other note state reads disk, as the one-shot host does.
- **Runtime typed reads prove currency against disk.** Code-mode `ontologyQuery` and recipe runs served here first call `LiveRuntime.SyncWatcher`, which compares selected notes on disk with the persisted metadata rows (size and modification second, then a content hash once per exact nanosecond stat, remembered for the runtime's lifetime) instead of trusting filesystem events, which can still be in flight. A pending resync, a pending configuration, ignore, or schema event, and a stored note discovery no longer returns also count as waiting. Waiting work goes to one watcher batch that starts after the call. Pending inputs and source event counters share `pendingMu`; derived provider work runs separately and does not delay structural synchronization. The caller also requires the ontology state to match the current schema and the metadata notes hash. Anything unproven within budget, or a boot catch-up or explicit index in progress, returns the call to the code-mode host's in-process refresh ([[code-mode-skill-scripts|SPEC-0115]]).
- **Rebuild never runs inside a live runtime.** `PrepareFreshRebuild` refuses when a live manifest exists; `rzm index --rebuild` stops a headless runtime, rebuilds in-process, and restarts it, and refuses against an attached runtime. The database is never unlinked under an open handle.
- **Control routes are loopback, token-gated, and count as activity.** Health is open; index jobs, shutdown, and agent operations require the manifest's bearer token and a loopback `Host`. Every authorized request touches the idle timer, and a headless runtime is never idle while a UI event stream (`/api/v1/events`, node events) is open; `IdleTracker.Hold` counts them. Headless runtimes idle-exit after `runtime.idleTimeout` (default one hour); attached runtimes never do; both exit when the vault root disappears.
- **A human asking for the UI outranks a headless runtime.** `rzm serve` and `rzm start` both stop a live headless runtime and win election as attached. Against a live attached runtime `rzm start` opens its URL and exits 0; `rzm serve` exits 3.
- **Build identity replaces headless runtimes, never attached ones.** `BuildID` is computed once at startup; a client with a different build replaces a headless runtime through graceful shutdown and re-spawn, and reports an attached mismatch instead.
- **Optional session writers follow requested code initialization.** A runtime needing both a CodeIndex reader and an existing-only session writer opens the reader first, then the writer after code initialization finishes, including failure. Concurrent initial WAL connections must not make the runtime contend with itself and discard available indexed evidence. The wait honors runtime cancellation; note-only sessions open independently and never wait for an unrequested code capability.
- **Readers stay in-process.** `rzm agent` and MCP commands ensure a runtime exists (without waiting) and keep reading the shared SQLite index through their one-shot runtimes; only `rzm index` and code-mode catalog operations execute inside the runtime. Local-only code-mode operations stay in the stdio host.
- **Shutdown drains runtime-owned startup and callbacks.** `LiveRuntime.Close` cancels and joins directly owned async initialization, leader startup, boot catch-up, session cleanup, and note-cache warmup before closing the lane and stores or releasing election ownership. Optional embedding-provider closers are registered as soon as a factory succeeds, including query-only providers and failed later initialization. Providers close after their embedding lanes and stores; compatible query-only code work reuses the note provider before construction. Cancellation alone does not mean a callback has finished writing. Serve also cancels and joins readiness workers, including validation publication that must finish after cancellation, before closing the runtime. It reports that it stopped only after this cleanup completes. A failed post-election startup recovery also closes the runtime and releases election ownership.
- **Native namespace recovery precedes ontology recovery.** Startup stabilizes native required-file publication and terminal decision/Git release before ordinary ontology recovery can pass its writer-admission guard. This barrier needs no projection dependencies; settled terminal journals retain later authored and Git edits for current-footprint convergence through the existing refresher.
- **Startup recovery waits for active writers.** After election and before readers or background work start, journal recovery acquires the shared index lease with cancellation. A writer draining from a previous process is contention to wait for, not a corrupt journal or failed restart. Completed repair journals may outlive later source edits: startup preserves those edits and journal evidence, warns with validation guidance, and continues. Only unfinished writes require safe rollback before readers start; committed forward verification remains a repair-session gate.
- **Long-running startup stays responsive.** Election is synchronous and cheap; everything heavy stays in the phased async init. After the owner-only write-recovery barrier, initialization must not block the listener, the health route, or the MCP handshake.

Shared embedding nodes retain physical provider/batch metrics in a bounded runtime-owned collector. The `runtime.embedding-provider` report follows node drain at shutdown, including initialization cleanup, and states its shared runtime lifetime scope. Ticket reports retain logical work and cannot claim ownership of mixed physical batches. A missing completed physical summary while the runtime is active or after a crash is unknown coverage.

## Must-dos when changing this subsystem

- New runtime work goes through `lane.Submit` with the right `Kind`; never call `indexlock.TryAcquire` from `pkg/app/bootstrap` outside the lane and `live_election.go` (a guard test enforces this).
- New control routes register in `pkg/app/web/runtime_control.go` behind the token middleware and a `ControlHooks` field; nil hooks answer 503 so lanes can land independently.
- Manifest fields change in `pkg/app/runtime` and in `Health` together; clients compare run id and PID, never instance id alone.
- Platform code (spawn, PID liveness, termination) lives behind build tags with tests on both CI platforms; use the helper-process pattern for spawn tests.
- A change to lifecycle behavior (start, stop, replace, idle exit, delegation, fallback) extends `tests/integration/runtime`, which drives the real binary against temporary vaults with an isolated home directory. Unit and helper-process tests prove the pieces; that suite proves they compose.
- Update `docs/reference/guides/Index lock and background coordination runbook.md` when wait, yield, or reclaim behavior changes, and the package `CONTEXT.md` files when entry points change.

## Review checklist — problems to catch

- A new write-capable open of the vault database that bypasses the schema init lock.
- A manifest written before the listener is bound, or removed without the owner check.
- A client that spawns on `ErrRuntimeUnresponsive`, trusts a manifest without a probe, or compares instance id instead of run id.
- A background runtime path acquiring `.rhizome/index.lock` outside the lane; an interactive edit bypassing the repair lease; a background job that ignores its context between provider batches or files.
- Unlinking or clobbering the database while a manifest is live.
- A control route without the token middleware, or a mutation reachable by simple browser POST.
- Force-killing an attached runtime; idle-exit logic that ignores open event streams or a busy lane.
- Blocking the serve listener, health route, or agent handshake with synchronous work.
