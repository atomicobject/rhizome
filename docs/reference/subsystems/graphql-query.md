# GraphQL query layer guidance

## Scope

The typed query layer executes read-only GraphQL-shaped queries over the note graph. `pkg/ontology/query` compiles the ontology schema into executable SDL and resolves roots/selections; `pkg/ontology/pushdown` decides which filters/sorts can be served by the indexed SQLite read model versus evaluated residually in memory; `pkg/ontology/queryrecipe` loads, validates, binds, and compiles saved deterministic recipes that skills and views invoke by id. The ontology core (schema compile, indexing, edges) is upstream — see [[ontology]]. Relation scheduling, hydration, batching, and limits are owned by `noderead` — see [[noderead]]; this layer compiles selections into a `noderead.NodeReadPlan` rather than reading SQLite/files itself.

Entry points: `query.BuildExecutableSchema`, `query.Prepare` / `PrepareWithVariables`, `query.Execute` (`pkg/ontology/query/schema.go`, `prepare.go`, `execute.go`); `pushdown.Planner` (`pkg/ontology/pushdown/planner.go`); `queryrecipe.LoadDefaultSources` / `Validate` / `BindVariables` / `Compile` (`pkg/ontology/queryrecipe/load.go`, `validate.go`, `bind.go`). CLI surfaces: `rzm agent ontology-query` / `ontology-query-schema` (`cmd/agent_ontology.go`, `cmd/ontology_query.go`) and `rzm query-recipe` / `rzm agent query-recipe` (`cmd/query_recipe.go`). MCP: `pkg/app/mcp/tool_ontology.go`. Web/public API: `pkg/app/web/ontology.go`, `public_api.go`.

## Design constraints

- **Section neighbors include provider-authored links.** Sources absent from the legacy note snapshot contribute current executable-provider link facts through the shared read scope. Admit only paths in the canonical note cache, skip already scanned sources, require authored-link extraction capability, and use shared projected-link resolution. Catalog ownership and capabilities, rather than a format-name switch, govern participation.

- **Selected navigation waits for publication.** `SelectedNotePaths` identifies singular canonical note/node roots, including fragments and workspace selections, without granting early raw-note readiness. After complete readiness, the web server waits for existing selected sources to have provider-current metadata and a catalog witness matching that source content hash and schema. Existing rows from an earlier source version do not establish readiness. Intentional empty projections and absent sources remain final misses.
- **Root source semantics are explicit.** Every `NoteNode` exposes `format`, `sourceRepresentation`, `evidenceRepresentation`, and `sourceCapabilities`. `content` remains authored raw UTF-8; provider search regions remain derived evidence. Capability values come from the executable runtime for the current admitted row rather than filename inference.

- **Selected query discovery uses the executable AST.** `DiscoverSchema` returns the original full SDL when unselected; a selected type returns an explicitly labeled fragment with root arguments, transitive input/enum/scalar dependencies and names of unexpanded output types. Root first limits and mutually exclusive selectors are advertised from the implementation. It performs no query execution or projection refresh.

- **Compiled SDL drives everything.** Roots, type names, field names, and relation names come from `buildSDL` over the compiled ontology schema (`schema.go`). Never hand-author or guess names; clients discover the contract via introspection (`introspection.go`) and `ontology-query-schema`. Anything not in the SDL is an error, not a fuzzy match.
- **Computed relation lists expose generated counts.** Every `@neighbors` or `@reverse(field:)` list emits a sibling `<name>Count: Int!` field on its type or interface and resolves it through the request's shared read scope; an authored field with that exact name suppresses generation and remains authoritative. The list itself takes an optional `first: Int` that caps the targets read per record, in the batched relation read (`FirstPerSource`) and on a single record alike, before any target is hydrated or resolved (`firstEdgeRows`, `filterTypedRecords`, the reverse ref cap); omitted, it returns every target, so a view reads `<name>Count` for fill and a capped list only where it shows targets. Reverse lists follow only inbound structural edges bearing the named source field, retain full refs for embedded source nodes, and count each distinct embedded node rather than its containing note. Prose and a second same-type relationship cannot enter the result. Section-derived authored interfaces expose the Section runtime fields required by GraphQL. Link filters accept `eq`/`in` for uniquely resolved target membership and `exists`; unsuitable operators or unresolved targets produce errors. Scalar `contains` remains supported.
- **Records expose updatedAt and issueCount.** Note and embedded object types gain `updatedAt: DateTime` and `issueCount: Int!`. `updatedAt` is the indexed modification time of the record's source note, in RFC3339, or null without indexed metadata. It is the file system mtime, not the last commit, so a fresh clone or checkout gives every file the same value; the field description and the kit API reference state this limit. `issueCount` counts issues in the published validation snapshot whose note membership is the note, or, for an embedded record, whose node membership is its node ID; it is 0 before a snapshot is published. An authored field or a generated relation count with either name takes precedence. An interface, including `Note` and `NoteNode`, declares a fact only when every concrete implementor carries it and no interface extending it authors the name; an interface without implementors declares it, so every generated `implements` clause stays valid. Generic views therefore select the facts on concrete types. Resolvers leave a placeholder for each selected fact, and after the selection tree resolves, `fillRecordFacts` loads them all through the shared scope and one validation scope summary read per 200 scopes (`record_facts.go`), so facts on nested link targets, relation lists, and section-field records under any number of parents cost no per-parent or per-record reads ([[group-views-and-view-platform|SPEC-0111]]). A typed root's `sort` accepts `updatedAt` where the record fact applies: the store orders by the note's indexed modification time before its limit (`ontologyNodeBuiltinFieldSort`, through `updatedAtSortResolver`, for sorts only), so a capped read takes the most recently changed records however many the type has. Under a non-empty edit overlay, whose merge re-sorts in memory, it stays a residual sort over the bounded candidates with one metadata read (`root_filters.go: rootSortUpdatedAt`).
- **Link target resolution is bounded and shared.** GraphQL and views try indexed path lookup for any literal target before title/alias discovery; an exact canonical note-root path takes precedence over a same-text alias regardless of provider. Title/alias discovery reads at most 5001 target catalog rows across all implementors, uses candidate-scoped aliases, and reuses the candidate set within one request. More than 5000 targets yields `link_filter_resolution_incomplete`, never a false unique or unresolved answer; callers can supply the canonical note path or narrow the target type. An alias read error also fails resolution.
- **`NoteNode` is the universal note read interface.** Generated SDL keeps `NoteNode` on every file-backed note type. If the authored schema defines `interface Note`, generated `NoteNode` implements it and every file-backed note object exposes those nullable general fields, including otherwise-untyped `note(path:)` reads. Domain-specific interfaces remain explicit opt-in; `Note` is the only universal authored interface.
- **Roots must be bounded.** Typed note roots permit an omitted selector with bounded `first`; when present, `path`, `find`, `property`, and `semantic` are mutually exclusive; generic `notes(...)` requires type/find/property/semantic; `node`/`nodes`/`resolve` require refs. Enforced in `prepare.go` (`validateSelectionSet`, `validateNotesRootArgs`) along with `first` limits. This is the safety boundary that keeps the layer from becoming an unbounded scan engine.
- **Typed-root pages disclose coverage.** Generated typed roots keep their existing array shape and gain a nonnegative `offset` argument. Each successful root adds `extensions.typedRoots[responseAlias]` to the GraphQL result with `requestedFirst`, `returnedCount`, `offset`, nullable `hasMore`, nullable `nextOffset`, and `status`. `complete` means lookahead proved exhaustion; `capped` means another match exists and `nextOffset` continues it. `unknown_page_bound` at the 5000-row maximum permits a next-page probe without claiming more matches. `unknown_candidate_bound` means residual filtering reached its 5000-candidate safety cap; both continuation fields are null and the caller must narrow the query. Aliases have independent coverage. Saved recipes and code mode retain the same `query.Result` extensions. Offsets continue through SQL for indexed roots; selector and residual paths stay within the bounded candidate window.
- **Not a second runtime.** Execution is read-only over indexed state plus bounded markdown projection (`doc.go`, `CONTEXT.md`). Runtime roots are limited to `ontology` and bounded known-path `code` evidence; agent command/capability metadata comes from `rzm agent surface`, not GraphQL. Providers degrade with warnings when absent—never block or widen.
- **Source-link inventory is path-based.** Section/source-link resolution intersects current Markdown metadata with the current reader inventory and admits aliases only for those paths. Building this lookup must not read unrelated note bodies. Resolution establishes eligible path identity; opening the target owns later content-read or parse errors. Inventory and aliases refresh for each execution.
- **Exact note roots use path availability.** An operation composed only of singular `node(ref:)` / `note(...)` roots may read retained metadata while global reconciliation is pending only after every requested candidate path has a provider-current durable row and the live indexing selection policy still assigns it to notes. Fragmented `node` refs require the complete model because their section or embedded-node identity resolves through the ontology catalog and projection. Admission reads metadata, properties, and tags in one short SQLite transaction and supplies immutable in-memory loaders for that request; later hydration cannot combine generations if publication advances. Its nested selections must also stay within raw-note fields and must not inspect runtime type identity through `__typename`, `resolvedType`, `ref.typeName`, or type-conditioned fragments; those reads require the complete type model. Workspaces, neighborhoods, local graphs, built-in relations, authored links, and section/node results also require the complete model. Include, exclude, and code-ownership reloads update the read-side selector in leaders and followers. A selected path without a row waits for its own publication even when the one-shot complete gate is already open. Public saved-recipe execution runs the same prepared-query admission and request-local snapshot path as direct GraphQL. Mixed operations, broad selectors, identifier refs, code refs, runtime roots, semantic queries, validation, and introspection also wait for complete index readiness. The exact-row dependency is additive and optional; without application-supplied provider and ownership checks, callers retain globally gated reads.
- **Singular roots report deleted sources as missing.** `node(ref:)`, `nodes(refs:)`, and `note(...)` return null for a note or section whose source file is gone even while indexed rows remain until the watcher publishes the deletion. The check is one stat per requested root through `Deps.NoteReader` and skips paths an edit-session overlay touches. Broad selectors and relation traversal stay on indexed state alone.
- **Not unified note-and-code search.** GraphQL supports bounded typed note/relationship reads, the notes-only `search` root, `semantic:` selectors, ontology-scoped surveys, validated recipes, and known-path docs/code/tests. `search(query:, type:, first:)` runs the shared unified engine (lexical, semantic, and structural lanes with exact-title navigation) through the `NoteSearcher` dependency (`pkg/app/unifiedsearch/note_searcher.go`), restricted to notes and filtered to the requested type's concrete implementors before retrieval; it has no mode argument. Code results never appear in GraphQL. Use `semantic-query` for broad mixed note/code discovery, `file-context` for known-path constraints and related docs, and `code-symbol`/`code-references`/`code-symbol-context` for exact proof.
- **Not a second runtime.** Execution is read-only over indexed state plus bounded markdown projection (`doc.go`, `CONTEXT.md`). Runtime roots (`ontology`, `code`, `agent`) adapt existing providers and must degrade with warnings when providers are absent — never block or widen. The ontology `nextId` adapter preserves ordered prospective path inputs, stable provider error codes, and nullable strategy-specific metadata rather than reconstructing allocation behavior in GraphQL.
- **Search is explicit only.** `search` and `semantic:` are selectors the caller opts into; neither is an implicit fallback for unresolved queries. `semantic:` stays chunk-only nearest-neighbour and requires a configured provider; `search` prepares `UsesSearch`, initializes embeddings when configured, and degrades to lexical lanes with engine warnings when they are absent. Misses return warnings/errors/nulls instead of broadened matches (`execute.go`).
- **Identifier resolution preserves cross-kind ambiguity without weakening path/alias precedence.** A bounded check of the `noderead.Scope` note hit's own preferred field gates comprehensive preferred-identifier discovery. When that note is itself among the preferred candidates, `resolve(ref:)` unions note and embedded candidates, collapses only equivalent projections of that note, and returns structured ambiguity instead of selecting one physical node. A path or alias hit whose note is not a preferred candidate remains authoritative over an unrelated embedded identifier with the same text and must not trigger vault-wide identifier or section scans.
- **SQL field sorts aggregate only selected-type nodes.** The store scopes field aggregates by candidate node IDs using existing node-type and node/field indexes. Preserve field-name-only MIN/MAX aggregation, null placement, ordering ties, and parameter binding; denormalized field type/kind must not filter values that the previous query included.
- **Pushdown must preserve semantics.** `pushdown.Planner` may move a filter/sort into SQL only when `ontology.IndexedFieldCapabilityForField` says the indexed read model supports that op; otherwise it residualizes. Sort partitioning is prefix-match: push the maximal supported prefix, residualize the coherent suffix (`planner.go`, `types.go`). Pushed and residual evaluation must produce identical result sets/order — divergence is a correctness bug, not a perf tradeoff.
- **One planner, two call sites.** `pkg/app/views/source_ontology.go` (configured views, `ViewResolver`: `frontmatter.`/`inline.` prefixes, case-insensitive) and `pkg/ontology/query/execute.go` (public roots, `SchemaResolver`: canonical names, case-sensitive) share the planner so aliasing, coercion, and residual semantics never fork (`resolver.go`).
- **Recipes are deterministic, validated artifacts.** Input binding reports undeclared and missing/invalid inputs in sorted name order. Envelope is `rhizome.query-recipe.v1` (`types.go`); older apiVersions are rejected explicitly. `Validate` compiles every recipe's GraphQL against the live executable schema with sample inputs, so schema drift surfaces as issues, not silent runtime failures. Variable binding is the contract (`BindVariables`); `{{placeholder}}` text substitution is deprecated (`deprecated_placeholder` issue in `bind.go`). Recipe ids must be unique across all roots (`load.go`: `.rhizome/query-recipes`, `docs/query-recipes`, `docs/rhizome-md-templates`, `.agents/skills`).
- **Discovery diagnostics remain applicable.** `HasDefaultSources` derives presence from the same recipes and issues as `LoadDefaultSources`. Missing roots are benign; broken root symlinks, invalid roots, and unreadable roots produce inspection diagnostics. Empty roots and unrelated skills do not enable the recipe check. Validation invokes discovery only when query-recipes is selected.
- **Broad selector inventory is execution-local.** Find and interface roots reuse a successful metadata read only within their current execution. Do not retain failures as cached misses or suppress cancellation. Keep the inventory immutable; ranking and type filtering use their own candidate slices, and a new execution reads the provider again.
- **Staged scalar selections validate current values.** Untouched note fields retain their batched committed assessment. Touched root fields call the pure ontology scalar assessment with already-loaded values and authored presence, so invalid optional fields return null, invalid required fields emit field errors, and repairs clear stale errors without new reads. Preserve sibling data, aliases/error paths, enum/list/cardinality rules, and authored empty lists. Frontmatter and workspace field values retain raw authored content independently of the typed selection.
- **Residual scalar evaluation agrees with indexed columns.** Note and embedded roots carry compiled fields into residual filters and sorts. Query residual evaluation and noderead overlay evaluation share the pure scalar and stable-key rules in `pushdown/scalars.go`, with `FieldValueRow` selecting predicate operand types and `StoredFieldValue` retaining materialized-row validation. Invalid typed operands may use the indexed textual fallback; authored blank presence for sorting does not imply nonempty `exists` membership. Integers remain exact, text stays textual, and dates/datetimes compare the canonical indexed text, including authored datetime offsets. Sort keys are prepared once per record before comparisons; list keys use minimum ascending and maximum descending, with missing or invalid typed values last independently of direction. Authored blank text bindings retain the indexed empty string's presence for sorting. Equal sort keys use the SQL tie tuple of note path, numeric source offset, and canonical catalog node ID. Builtin `path`/`notePath` equality and membership use canonical path spelling without case folding; their raw path sort keys retain indexed lexical ordering before pagination for selectors and coherent residual sorts. Authored String fields retain normalized scalar comparison. Predicate coercion does not relax scalar-selection validation or change advertised capabilities.
- **Batching through one scope.** One loader set creates one `noderead.Scope` (`loaders.go`); relation caches are keyed by relation/provenance/type/limit and must remember empty source groups. Per-parent field resolution must hit cache, not requery.
- **Identity lookups do not render unused links.** Query target resolution uses `Scope.Resolve` with `OmitLocators` for canonical refs and summary records, then preserves the existing preferred-identifier ambiguity checks. Do not bypass catalog resolution with a fabricated ref. Scope owns requested-path fallback and provider-current eligibility; loaders must not add a second vault-wide snapshot fallback for misses or errors.
- **Projection-owned child refs stay readable when content identity is ambiguous.** A field binding or global-source traversal may project its exact current-snapshot refs with the bound-node path, which verifies byte ranges and structural identity together. Catalog rows, root arguments, copied refs, and replayed refs must use ordinary resolution so duplicate unanchored content remains an explicit ambiguity instead of selecting by offset.
- **Node workspace reads stay composable.** `Node.workspace` publishes generic source-preserving metadata, including the focused node's schema-aware semantic `parentRef` and its `parentTitle` (one summary hydration over the request scope, so clients never fetch a preview to label the parent), and selected-domain flags over the same request scope. Its bounded `bodies(first:)` selection carries ordered body blocks for the focused node and descendants that render inline (declared INLINE sections and headings no schema field declares, per `NodeBodyBlock.RendersInline`, shared with the REST workspace graph), plus binding/field/collection metadata for structural descendants needed by collection rows. An undeclared heading's body `parentRef` is the body that contains it, so nesting follows the Markdown; declared descendants keep the semantic parent; its bounded `sourceLinks(first:)` selection preserves authored internal-link/embed occurrences in source order while resolving unique known-note targets through one shared scope batch. Same-file Markdown anchors pass their authored fragment-only destination to that scope with the canonical source path supplied separately; never splice a decoded filename into raw URL syntax. Field states expose `links` for relation fields: each authored value with its resolved `ref` and target `title`, so clients show titles instead of link text. Targets come from the indexed field values (`ontology_node_field_values.target_ref_json`, the rows configured views read) in one batched read shared by workspace fields and every body's fields, titled by one batched summary hydration; only values the index cannot vouch for (staged notes or values whose text changed since indexing) fall back to one index-only `Scope.Resolve`. Both traversal and source-link resolution stay capped rather than becoming unbounded subtree or per-link reads. Relation selection combines typed neighborhood groups with one bounded code-aware graph read for ordinary connections, backlinks, and code evidence; every target retains its exact node kind. A fragment-bearing target is labelled with its own projected node title, resolved through one batched summary hydration over the shared scope, and falls back to the fragment only when the node is unknown. Body block Markdown preserves projected whitespace, including leading separators and indentation required for source-preserving narrative replay. Frontend pane stacks, tabs, rails, heterogeneous pane nodes, and compatibility view models are assembled in TypeScript rather than frozen into the GraphQL schema. Edit-session overlays flow through the scope before projection and assessment resolution.
- **Workspace fields carry edit authority.** Every projected workspace field exposes its owner-specific value kind, cardinality, required state, enum values with their `@view` labels and tones (`enumOptions`; a label falls back to the raw value), relation target, value origin, identifier role, effective display importance, supported write operation, and any read-only reason. Clients select controls and presentation order from this projection and never infer editability from a displayed value or join capabilities by field name across different owners.
- **Document root locators retain file identity.** Public NOTE refs serialize as a bare note path even when indexed refs carry structural fingerprints or node IDs. Existing `#struct:` root locators resolve to the note only when their fingerprint matches the current projected document root; unknown fingerprints must not fall back to the file.
- **Locator actions remain canonical and read-only.** Public `NodeLocator` exposes its canonical `ref`/`kind`, its link target's `ref`, structured diagnostics, and planned fix actions from the ontology locator contract. This lets a client stage make-linkable work without constructing a browser-specific action DTO; actual source mutation remains on the explicit edit-session surface.
- **Public section refs retain projected identity.** Lightweight heading-match records use the current note projection to publish canonical structural fingerprints without changing internal scheduling refs or warmed cache keys. Indexed catalog refs and existing projections remain readable without new content hydration.
- **Section fragment namespaces stay distinct.** Explicit Markdown paths with generated heading fragments resolve as `SECTION`; explicit `#^block-id` refs resolve only against authored block IDs. Never normalize away the caret and let a generated heading shadow an explicit block target.

## Must-dos when changing this subsystem

- New root, argument, filter op, or field capability: it must appear in the generated SDL (`schema.go`), pass `Prepare` validation, survive introspection, and show up in `ontology-query-schema` / authoring-guide output. A capability that executes but does not introspect is invisible to agents and therefore broken.
- Pushdown changes: add equivalence coverage proving pushed and residual paths agree (extend `pkg/ontology/pushdown/planner_test.go` and the end-to-end cases in `pkg/ontology/query/query_test.go`). Check both consumers — views and GraphQL — since they share the planner.
- Recipe envelope or binding changes: update `Validate`/`Compile` so `rzm agent validate query-recipes` catches the new failure mode, and migrate or explicitly reject existing recipe files (the apiVersion bump precedent in `queryrecipe/types.go` documents the pattern).
- New limits or warnings: prefer structured warnings over silent narrowing/widening; keep ordinary roots quiet and put explanation behind `ontology.queryPlan(...)` diagnostics.
- Keep `pkg/ontology/query/CONTEXT.md` and [[ontology-graphql-query-contract]] in sync with behavior changes; CLI/MCP descriptions (`cmd/agent_ontology.go`, `pkg/app/mcp/tool_ontology.go`) follow.
- Run `go test ./pkg/ontology/query/... ./pkg/ontology/pushdown/... ./pkg/ontology/queryrecipe/...` plus `go test -tags=integration ./...` when execution or recipe surfaces change.

## Review checklist — problems to catch

- **Pushdown/in-memory divergence**: a filter op pushed to SQL that normalizes values (e.g. `ValueNorm` lowercasing) differently than residual evaluation, or a sort pushed without its prefix so the residual sees an incoherent suffix.
- **N+1 per-node reads**: relation or scalar resolution that bypasses the shared `noderead.Scope`/loader cache and requeries SQLite or projects markdown per parent. Selection pre-execution must warm the same scope resolvers use.
- **Silently broadened matches**: unresolved roots, missing semantic searcher, ambiguous link targets, or unavailable runtime providers returning "best effort" results instead of warnings/nulls.
- **Unbounded roots sneaking in**: a new root or field that skips `validateNotesRootArgs`-style mode checks or `first` caps in `prepare.go`.
- **Recipe schema drift**: recipes that validate only structurally — `Validate` must compile against the live `ExecutableSchema`; a recipe referencing a renamed field/root should fail validation, not fail at run time. Also: duplicate ids across roots, placeholders surviving in variable-mode recipes.
- **Resolver fork**: view-side and GraphQL-side field-key resolution drifting apart instead of going through `pushdown.Resolver` implementations.
- **Introspection lying**: SDL or capability changes not reflected in `introspection.go`, so agents author queries the executor rejects.
- **Markdown projection creep**: projecting note content when the indexed `ontology_node_field_values` hydration would suffice (only project for `content`, children/workspace bodies, or non-indexed selections).
