# Search subsystem guidance

## Scope

Unified search pipeline: orchestration → planning → concurrent retriever fan-out → ranking/shaping → answer assembly → optional budgeted packing, plus chunk-based semantic search and the embedding-lane runtime that feeds it. Entry points:

- `pkg/search/service.go` — `Service.Search(ctx, spec)` runs retrieve → classify → rank, with approx-rank fallback on deadline/cancel.
- `pkg/search/planner/planner.go` — `Planner.Plan()` builds the retrieval plan (never executes it).
- `pkg/app/searchengine/engine.go` — shared cycle-free planner/ranker/service execution used by CLI, MCP, and HTTP search.
- `pkg/app/unifiedsearch/execute.go` — `Execute` is the one application entry point for every caller (CLI, MCP, HTTP, agent code mode, GraphQL `search` through `NoteSearcher`): effective policy, request identity, fixed-window continuation, assessment, and answer assembly over `Run`'s retrieval.
- `pkg/app/unifiedsearch/run.go` — runtime wiring and retrieval (`Run`); adapts ranked output into `pkg/app/answer` packets.
- `pkg/app/semanticops/` — shared semantic provider construction (`PrepareProvider`) used by indexing and unified search.
- `pkg/app/semanticruntime/` — indexing-time embedding provider lanes (`PolicyFor`, `Runtime.EnsureLane`).
- `pkg/search/semantic/search.go` — chunk-scored semantic search with fair owner interleaving.

## Design constraints

- **Operational metrics preserve measurement coverage.** Persistent request and indexing operations attach their own bounded `indexingperf` collector. Structured snapshots export cumulative counts, gauges, span durations, DB waits, and retained-prefix quantiles without raw samples or interval timelines. Coverage states when series, samples, or intervals were dropped; a partial union or quantile must not be treated as complete. The existing text timing collector remains available. Search stage events bridge into the contextual collector without copying error text. Search outcome uses the actual returned error, and existing fallback branches record finite reason counters without changing retrieval behavior.
- **Search report selection keeps ordinary calls cheap.** Every search retains quiet correlated start and terminal events; terminal events include duration, outcome, and result count. Detailed metric snapshots are persisted only for calls taking at least 250 ms, errors, cancellations, panics, or observed degradation/fallback. Healthy calls below the threshold skip snapshot serialization and report publication while retaining contextual metrics and `--timings` events. A reused collector is disclosed as `metrics_scope: context`; a search-owned collector uses `search_operation`. Shared timing displays bind each operation's collector through context, so concurrent facets cannot redirect one another's metrics.
- **Provider diagnostics separate logical calls from transport attempts.** Record HTTP status counts, finite transport classes, measured and scheduled backoff, bytes read and submitted, and cache/reuse decisions. Configuration identity is an opaque digest excluding API keys and URL authentication/query/fragment. Never persist provider bodies, query text, endpoint URLs, or raw upstream errors in metrics. Returned provider error behavior is unchanged. Store reset logs use finite reason codes; write summaries carry the current operation context.

- **Search controls apply before bounded retrieval and packet construction.** Public project-search scope, owning-note concrete type, literal vault-relative folder boundaries, test exclusions, and exact-symbol requirements (`search.Filters`, including `ExactSymbols`) filter eligible candidates in the engine before limits, ranking, answer roles, body selection, counts, and pagination; explicit seeds are re-checked against the owning-note type in `Run` because seed retrieval bypasses retriever filters. Folder matching treats `%` and `_` literally and includes only the selected directory or descendants. Continuation tokens bind effective controls, vault identity, a fixed candidate window, the ordered-result digest, and a bounded exact query-vector snapshot when provider output participates. The v2 cursor payload is losslessly zlib-compressed before base64 encoding; existing uncompressed v2 tokens remain readable. Encoded input is bounded to 1 MiB and decompressed JSON to 4 MiB to accommodate the permitted vector batch, and exact query vectors are never rounded or regenerated to save response budget. Every caller resends the same queries, seeds, mode, and controls with the token. Continuation identity covers result membership only: response projection (`compact`, `explain`, `timings`, body budget) is not bound and may differ between pages of one sequence. Conflicts are rejected, changed ranked windows become stale, and obsolete cursor versions require refresh. Optional compact output owns source bodies in one collection with resolvable role references, while retaining warnings, freshness, counts, continuation, and body truncation/dedupe state.
- **Intent reuse requires provider identity.** The cache fingerprint includes normalized provider, model, endpoint, and requested dimensions. Automatic dimensions may reuse a compatible, internally consistent snapshot before the provider learns its dimensions; missing identity, changed models, or malformed vectors require regeneration. Intent queries prefer the code provider, matching indexing, and validate the stored fingerprint, vector shape, and exact current exemplar pair set before comparison; incompatible snapshots fall back to current-provider detection.
- **Concurrent facets share one complete query-vector pair per text.** The request memo coordinates one pending attempt per trimmed text without holding its mutex during provider work or waits. The winning caller owns computation under its existing context and stage deadline; followers cancel independently. An ended winning context permits a live follower to retry, while genuine provider failures reach that attempt's participants and remain uncached. Only successful work from a still-live caller publishes vectors. Returns, seeded records, and cursor snapshots are isolated copies. Distinct texts remain concurrent; no global cache or detached work. Distinct-provider failure cancels its sibling with the original wrapped cause, retaining per-provider timings and genuine caller cancellation.
- **Voyage recovery is bounded per logical batch.** The existing request timeout remains 120 seconds; recursive splits share a 240-second budget. Retry-After is honored fully when it fits the remaining budget, otherwise recovery fails explicitly. Status retries use cancellation-aware exponential jittered backoff.

- **Same-handle evidence merge.** Candidates with the same `Handle` are one entity; retrievers contribute evidence merged via `MergeCandidate` (`pkg/search/merge.go`): bounded evidence growth (max 12 total, 3 per type), deterministic fact deduplication and provenance retention, and first-non-empty entity metadata. Argument order can affect entity metadata, but cannot affect retained evidence or its order. Concurrent service retrieval, nested composite retrieval, and auto-expansion base retrieval merge metadata in configured retriever order, independent of completion timing; deadline-driven progressive retrieval retains its intent-priority order.
- **A note's lanes are scored together.** The vector lane, `note_lexical`, and root regions return one note under different handles (node chunk, `note:` handle). Before ranking, `Service.Search` coalesces each note's whole-note candidates, those whose canonical identity is the note path (no `NodeRef` or a `NOTE` one), by owning note (`coalesceNoteCandidates`, `pkg/search/merge.go`), so a title match and embedding similarity add up instead of being scored apart and reduced to the maximum by `CanonicalizeSources`. Embedded and section nodes keep their own identity, so facet aggregation sees the same source in every facet, and Intel FTS sections (`doc_section`) stay distinct under `MaxPerOwner`. The member with the strongest semantic evidence is the base, keeping the best chunk as the displayed node; `MergeCandidate` fact dedupe counts several chunks' similarity once, and only the base keeps `query_specificity` so the deadline fallback cannot stack it. Found from a dogfood query ("Innovation teams") whose four title-matching notes first appeared at ranks 6, 14, 18, and 26; on the title-phrase corpus with pinned `voyage-4-lite` vectors it raised navigation success at rank 1 from 0.750 to 1.000 (EFF-2026-10-08-07-40).
- **Support-only evidence lanes.** Rationale FTS matches are evidence for an already-addressable handle, not a standalone result class. `SupportOnly` candidates must merge into a non-support candidate with the same handle or be filtered before ranking.
- **Answer relevance uses source-owned proof.** Query specificity may use link labels and routing snippets for ranking, but those fields cannot establish strong answer relevance. Strong source support comes from canonical candidate identity or exact normalized terms in source-owned Intel/rationale excerpts with validated producer provenance. Explicit quoted, code-shaped, or ownership-cued entities require one ordered contiguous match within one identity field or one source-owned excerpt; missing excerpts mean unestablished support, not proved absence.
- **Structural evidence binds the target it proves.** A primary caller, callee, or test edge remains strong even when the returned source name does not repeat the target name. An explicit file seed may acquire a selected target only when its primary evidence carries one unique persisted `target_fqn`; conflicting or incomplete proof stays unresolved.
- **File-seeded test evidence is exact or supporting.** A test symbol receives primary `tests` evidence only from a persisted edge to an actual declaration in the seeded file. Whole-file path associations remain supporting. Exact test candidates are ordered by query specificity without changing the proved target.
- **`MaxPerOwner` diversity.** `Candidate.Owner` caps per-note/file results in rankers (`pkg/search/relevance/ranker.go`) and the approx fallback path (`pkg/search/scoring.go`). This is what keeps one note from monopolizing results.
- **Planner does not execute.** `Planner.Plan()` only constructs a `Plan` from `QuerySpec`; retrieval/ranking happen inside `Service.Search`.
- **Retrievers run concurrently** (or progressively under deadline — `Service.retrieveProgressive`). New retrievers must be I/O-bounded and registered through the service's retriever list, never invoked ad hoc downstream.
- **Ontology-node chunks need catalog identity** before becoming candidates; stale chunks without it are skipped (`pkg/search/retrieval/seed_vector_test.go`, `pkg/search/semantic/search_test.go` — `...SkipsOntologyChunksWithoutCatalogIdentity`).
- **Ontology consumers require current materializer identity.** Planner ontology retrievers and raw-note embedding eligibility accept persisted ontology state only when `materialization_version` equals `ontology.OntologyMaterializationVersion`. The ontology coordinator converges older rows; future rows require upgrading to a binary that supports their version.
- **Layer ownership.** `pkg/app/unifiedsearch` owns resource wiring, effective request policy, ranked-to-answer conversion, source assessment, and continuation. `pkg/app/searchengine` owns the shared planner/ranker/service call without importing adapters. `pkg/app/answer` is pure packet assembly (no retrieval, embeddings, FS walks, or live ontology projection); public adapters (MCP, HTTP, GraphQL `NoteSearcher`) translate inputs, call `Execute` once, hydrate the returned page for presentation, and serialize outputs without re-running retrieval, assessment, answer selection, or pagination. Semantic hits preserve provenance for their owning sources.
- **Continuation identity separates membership from freshness.** Membership identity includes normalized query facets with each facet's mode, canonical eligibility filters, profile, candidate window, owner cap, vault identity, and ranking-policy version. Presentation limit and body budget do not change membership. Freshness is checked separately against the committed note metadata hashes, code corpus fingerprint, unified embedding generation and configuration, scope hash, and indexer version. Unified vector upserts advance the embedding generation atomically; deletion/rebuild and provider configuration changes also change the composite fingerprint. Cursor candidate bounds must equal the effective policy bound.
- **Changed chunk content cannot reuse old current-vector proof.** Chunk publication retires canonical vector metadata and ontology embedding sidecars transactionally when the content hash changes, before provider work. Search excludes retained vector bytes until current embedding metadata is published, retry planning remains eligible after failure, and metadata retirement changes the continuation fingerprint immediately. Equal hashes retain their evidence and hash-addressed caches remain reusable. For metadata already stranded by earlier publication behavior, run explicit `rzm index --rebuild`; ordinary indexing cannot recover the lost original hash.
- **Root search owns its providers and stores.** `unifiedsearch.Run` opens providers and stores directly from its options (or uses injected ones) and never routes through the agent runtime or the MCP adapter. It registers optional provider closers before opening stores, drains owned resources on failure or result cleanup, and decides compatible code/note reuse before constructing a second provider. Injected providers remain caller-owned; semantic-runtime lanes borrow their providers. The optional embedding cache is factory-owned, while the rerank cache remains intentionally memoized for process lifetime; `pkg/app/unifiedsearch` must not import `oneshotruntime`, `bootstrap`, or `mcp`, because the MCP adapter now calls `Execute` and those packages depend on it.
- **Exact hits survive module rollup.** `Service.Search` checks candidate eligibility before ranking and rollup. With nonempty `Filters.ExactSymbols`, `CodeRollupper` preserves every ranked candidate's identity, even when its evidence is only lexical or vector similarity. Otherwise it may replace a file's symbol hits with its module anchor when relevance is spread or the file is small, unless the top hit carries `symbol_exact`, `symbol_match`, or `definition_anchor` evidence.
- **Callers may widen, never narrow, the candidate window.** `ApplicationOptions.CandidateWindow` raises the profile window so a visible limit above the profile default (GraphQL `first` up to 200, the Explorer's 200-result search) is honored; the effective window stays part of continuation identity. Ambiguous precision candidates pass through the caller's `search.Filters` before they are returned, and a `noteType` restriction fails closed when owning-note types cannot be resolved.
- **Strong support needs more than one shared word.** In `AssessQuery`, a query with exactly one meaningful concept reaches strong only through canonical identity evidence (`path_exact`, `note_title_exact`, `symbol_exact`, `definition_anchor`). Coverage is measured over `queryConcepts` — the deduplicated meaningful concepts `queryframe` scores against, each with its term variants — never over raw phrase tokens, because question words, stop words, and repeated tokens can never appear in the `matched` inventory and must not dilute the denominator. Lexical corroboration of a semantic hit needs at least half of those concepts; standing alone as strong source-owned identity or content needs all of them. Ranking-only observations (`query_specificity`, retriever ranks, graph authority) belong to no retrieval lane and never corroborate, but both `intel_fts_match` and `intel_doc_match` belong to the `intel_fts` lane their retriever ran.
- **Short queries need every concept.** `query_specificity` ranking evidence is `queryframe.Score.RankValue`. For a query with at most three concepts (`maxTitleConcepts`) that is not an explanatory question (`Frame.IsExplain`: how, what, where, why, or explain), a concept (a term and its variants) counts once per field and earns at most its share of the score, so one word repeated across path, title, breadcrumb, and heading cannot stand in for the words a source lacks. Explanatory questions and longer queries keep `Value`, because a strong identity match on their key word is the signal: the cap dropped `decorators.py` for a seven-concept decorator question (nDCG@10 0.984 to 0.604) and the Container class for "how does Container work?" (1.0 to 0.71). `Value` keeps its meaning for answer assembly's `DirectSpecificity` confidence thresholds. Readers of the evidence itself see `RankValue`: answer `Specificity` (ordering and the 0.7 strong-evidence branch), the auto-expansion seed gate (`MinSeedSpecificity` 0.25), and MCP match specificity. Measured fast (lexical) on the title-phrase corpus: nDCG@10 0.790 to 0.860. Short queries whose secondary results previously tied at the cap and were ordered by handle now follow coverage, which moved development navigation nDCG@10 from 0.937 to 0.920 with rank-1 and rank-3 success unchanged.
- **High confidence needs an identity match or two lanes.** `finalizeAssessedConfidence` grants high only when every must-read source is strong and at least one must-read source has an identity match or meaningful support (raw score ≥ 0.25) from two distinct retrieval lanes (`search.LanesForEvidence`). A page with no strong source is low, not medium. No-answer and ambiguous-target controls on the repository corpus are the regression guard.
- **The identity leader goes first.** For non-precision intents, `selectAssessedItems` puts the highest-scored strong source with an identity match at the head of must-read before role and facet coverage fill the packet; a caller who typed a title, path, or symbol gets that source first.
- **Bare symbols resolve to declarations.** For a bare symbol token, target resolution keeps only declaration-kind anchors (functions, methods, types, classes, interfaces) when any exist, so same-named struct fields do not make `go_to_def` ambiguous; an explicit `Qualifier.Symbol` keeps the member. Candidates that remain ambiguous are ordered declarations first, deeper paths first, then FQN, and `dedupeTargetCandidates` preserves that order. Once a `go_to_def` target is selected, only its own declaration stays a primary definition; same-named anchors in the same file are demoted to supporting (`DemoteNonTargetDefinitions`).
- **Default intent is inferred once, and only when the caller omitted one.** `Execute` applies `InferDefaultIntent` (moved from the MCP adapter into `pkg/app/unifiedsearch/default_intent.go`) when a caller supplies no intent and at least one query input omitted its mode, and reports `IntentSource`/`IntentScore` on the effective request; adapters must not route the same text differently. Facets that all carry explicit but differing modes share no uniform mode yet were still chosen by the caller, so they keep the `search` aggregate intent rather than acquiring one inferred from their joined text.
- **A facet is covered by its own leader.** `FacetSupport.Covers()` is the single rule for required-facet coverage, facet-proof selection, and the quality evaluator: strong support, or useful support from that facet's top-ranked result (`LeadsFacet`, from the multi-query rank evidence), with precision facets still requiring the resolved relationship. Paraphrased facets can never be strong, so without the leader rule facet coverage is structurally zero.
- **One request, one intent.** `Execute` derives the intent from the explicit intent input, else from a mode shared by every query input, else `search`; `Result.Intent` reports the intent that actually ran after target repair, and adapters report that value rather than the requested one.
- **Raw CLI presentation is materialized before resource cleanup.** The application retains the selected page's coalesced note chunks plus anchor spans and module exports only when raw rendering is requested. The CLI renders that bounded data after search stores close; JSON and answer transports do not pay the extra Intel reads or expose renderer-only fields.
- **Diagnostics are additive only.** Raw/explain traces must never change retriever selection, ranking, pack budget, warnings, or answer role selection (see [[search-diagnostics-explain-architecture]]).
- **Query-provider diagnostics count actual calls.** `semantic.QueryEmbedder` records one provider call for a shared provider instance and one per independently invoked code/note provider. The counter is observational only and must not change provider reuse, cancellation, or error precedence.
- **Indexed graph expansion never hides a live crawl.** Planner callers that select indexed-only graph sources use fresh persisted graph scores when present, then the ready raw-note `GraphSnapshot` projection when scores are absent/stale. They never fall through to `ComputeGraphAnalysis` over a live `NoteReader`; non-indexed callers retain that fallback and diagnostics identify it explicitly.
- **Vector KNN preserves the scalar contract.** Unified embedding search uses exact vec0 `MATCH` over the existing dimension table, prefilters eligible chunk IDs before KNN, and orders equal scores by chunk ID. Adaptive tie probing protects the K boundary; scalar search is only the explicit cap/tie fallback. New filters must extend scalar/KNN parity coverage rather than post-filtering an undersized nearest-neighbor set.
- **Provider regions are root-owned evidence.** Root-only note formats become ontology-node chunks from provider `SearchRegions`; semantic chunking never parses their raw source. Visible and supplemental chunks retain distinct granularities and source ranges. Search queries those partitions independently, applies the supplemental factor, merges deterministically, and only then enforces the caller limit, so supplemental evidence cannot consume the visible candidate window.
- **Provider regions share lexical search.** Durable root search regions become canonical note candidates in the existing Intel FTS lane. Supplemental BM25 scores are reduced before the SQL limit. Metadata replacement, fatal projection, deletion, and ownership change remove those FTS rows in the same SQLite transaction as source fact replacement.
- **Primary code chunks carry their explanation.** `SynthesisPolicy.BuildAnchorChunks` receives a `SymbolChunkContext` (the file's module-doc summary plus the rationale comments inside the anchor's span) and renders it as `Module:`/`Rationale:` prose in every primary chunk, so a paraphrased question can reach code whose explanation lives in comments. Measured on the repository corpus with pinned embeddings this lifted navigation nDCG@10 from 0.781 to 0.819-0.870 and cut unjudged top-10 sources by half, at a cost of 0.565 → 0.510 on multi-facet cases; a chunk-text change re-embeds, so re-index after touching it.
- **Doc classes are a taxonomy, not a score prior.** `InferDocClass` separates specs, efforts, and analysis artifacts from curated reference docs; only the existing seeded overview shaper and locality ranker consume the classes. A measured unseeded spec-up/effort-down multiplier (`×1.06`/`×0.88`) interacted badly with chunk prose (navigation nDCG@10 0.870 → 0.627) and was removed; do not reintroduce a class-based multiplier without an in-family ablation.
- **Facet leaders are role-aware.** A facet whose wording asks for documentation or tests leads with its top-ranked result in that role (`facetRoleCue`, `leads_facet` rank evidence); otherwise the facet's top-ranked result leads. `FacetSupport.LeadsFacet` reads that evidence, never rank 0 directly.
- **Live-provider evaluations pin embeddings.** `RHIZOME_EMBEDDING_CACHE` wraps any non-test provider in a SQLite content-hash cache (`embeddings.NewCachedProvider`), and `tools/searchquality -embedding-cache` exports it to the isolated indexer. Two live Voyage runs of identical code differed by about 0.03 nDCG@10 and 0.05 must-read precision on the repository corpus, the same size as the effects under test; compare runs only within one cache family, and treat a single-case top-10 swap between cached runs as index-order noise. Isolated runs before `3603ec11d` staged no `.rhizome/ontology/*.graphql`, so typed-note and repository-corpus results from them are not comparable with later isolated runs.
- **A low-confidence page names no source it cannot vouch for.** When a broad-intent answer finalizes as low because no source has identity-level or corroborated support, a must-read item survives only with FinalScore >= 0.85 and query aboutness: an identity match, `note_title_match`, `intel_doc_match`, `symbol_match`, `query_match`, `note_vector_similarity`, or a body-term hit (`intel_fts_match`) whose query-specificity `support_score` is at least 0.45. Graph popularity alone is never aboutness. Demoted items lead the supporting list, and an emptied page reports "no source is about the query". Measured on the repository and fixture development splits: every no-answer control abstains, fixture must-read precision holds at 0.885 (0.909 before the rule), and precision intents are exempt because their must-reads were all correct.
- **A precision target must be named, and documents are peers.** A token seeds a precision target only when the query names it as code: the request is the identifier alone, the token is qualified (`.`/`_`/`:`/`/`), carries an uppercase letter, is quoted, or sits next to a code cue word (`func`, `method`, `type`, `class`, `def`, ...). Other tokens become `speculative_symbol_match` candidates that never write explicit seeds, never clear competing candidates, and never block precision fallback (`ShouldBlockPrecisionFallback`); ambiguity from an identifier the user did name still fails closed. When no named code target survives, `inferExactDocumentMatch` resolves the one indexed note whose title/slug equals the whole query phrase (separator- and case-normalized, compared against basenames and path segments) at `note_title_exact` confidence 0.95, so an exactly named document outranks a code member that shares one of its words. This came from a blind diagnosis of the held-out go_to_def cases, all of which failed the same way; those eight cases are therefore development evidence now.
- **Link text names a note.** `LinkTextRetriever` (`pkg/search/retrieval/link_text.go`) scores a note by the labels and lines of links that point to it, read from `graph_doc_edges.link_text` (`NoteLinkTextMatches`). Per linking note it takes the best concept coverage of a label, or half that of the line around the link. A note linking more than 20 targets counts 20/N, and linking notes combine as a noisy-OR capped at 0.5 each, so one stray label (0.5) cannot match a label several notes agree on (three notes: 0.875). It emits `link_text_match` on the lexical channel, which has no retrieval lane, is not aboutness, and never satisfies exact-title or exact-path precedence. When at least two linking notes share a label that names every query concept, the evidence carries it as `alias`. `queryframe.ScoreCandidate` then reads it with the title, and `pruneCandidates` protects the note the way it protects exact symbols, because the window is pruned before query specificity runs. Measured on the link-dense `linked-topics-vault` corpus with pinned `voyage-4-lite` vectors: navigation nDCG@10 0.564 to 0.895 on development and 0.648 to 0.927 on held-out, with every alias target first. Existing corpora were unchanged on development and rose on held-out (0.786 to 0.795). On a local copy of a 3,700-note personal vault, notes reached the top 3 for 13 of 30 labels that at least two notes agree on, up from 6 (EFF-2026-10-08-16-23).
- **Graph features stay seed-only for text queries.** `unifiedsearch.Run` enables graph, ontology, and personalized PageRank expansion, and the graph and ontology channel weights, only when a request names a note seed. Turning them on for text queries left the linked-topics corpus flat (navigation nDCG@10 0.606 to 0.602, conceptual 0.711 to 0.715), so they stay off.
- **Linked corroboration was tried and removed.** A ranker decorator gave a candidate with its own lexical or semantic evidence bounded support for each linked candidate that also had it. On the linked-topics corpus it moved conceptual nDCG@10 from 0.716 to 0.707: with live vectors nearly every windowed candidate counts as relevant, and distractors link to each other, so the signal rewards being linked rather than being about the query. Do not reintroduce neighborhood boosts without an aboutness test stricter than retrieval and a judged ablation.
- **Pseudo-relevance feedback was tried and removed.** A capped lexical follow-up probe seeded by the top-8 titles and symbol names looked like a recall win only while it re-added the intel lane to rows the base pass had already found (double counting that also broke limit-1 continuation with same-file duplicates); restricted to new candidates it lowered development must-read precision on conceptual (0.500 → 0.385) and multi-facet (0.583 → 0.333) cases by feeding probe-only candidates into role coverage. Do not reintroduce a second lexical pass without must-read ineligibility for its candidates and a judged in-family ablation.
- **Reranking is opt-in and additive.** `rerank.NewFromEnv` (`RHIZOME_RERANK_PROVIDER`, optional `RHIZOME_RERANK_MODEL`) wraps the engine ranker in `relevance.RerankingRanker`, which blends cross-encoder scores (weight 0.3) into the top 30 results on the base score scale, pins any result carrying identity evidence (`path_exact`, `note_title_exact`, `symbol_exact`, `definition_anchor`, `explicit_seed`) at its base position, and leaves the tail in place. Any provider error, deadline, or score-count mismatch keeps the base order and records a `rerank_unavailable` warning; the stage never changes retrieval, candidate membership, or `MaxPerOwner`. `RHIZOME_EMBEDDING_CACHE` also pins rerank scores (`rerank_cache` table), so live comparisons stay inside one cache family. `tools/searchquality -rerank-provider` is rejected with `-fast`.
- **Semantic fair interleaving** (`interleaveScoredChunksByOwner`, `pkg/search/semantic/search.go`): limit = total chunks (default 25); chunks group by owner/note, groups ordered by top-chunk score, then round-robin picks so no note hogs slots. Doc-section and ontology-node chunks keyed by note path.
- **Semantic section handles use source order without body hydration.** Doc-section result positions come from `IntelDocSectionIDsByPath` in `(start_byte, section_id)` order, memoized per note path for one search request. Keep the content-bearing section reader for consumers that need bodies. Missing sections or failed position reads retain the note-level handle fallback.
- **Embedding lanes** (`pkg/app/semanticruntime`): compatible provider/model/endpoint/dimension work shares one node; provider defaults and runtime policy set batch/concurrency. Persisted vault config must not emit or honor batch-size/concurrency knobs. Lane sharing changes provider execution only — never chunk ownership or SQLite writeback.
- **Provider construction is shared** (`pkg/app/semanticops`): app packages own command flow; semanticops only adapts embedding config/API-key resolution into an embeddings provider.
- **Query-only note metadata is never repaired.** Existing note-embedding metadata must match the configured provider, model, and dimensions. A wholly unknown legacy placeholder row (empty provider/model and zero dimensions) is treated like absent legacy metadata when current unified vectors already exist; partially populated or mismatched rows remain incompatible. Vector-table dimensionality is still enforced when embeddings are read.

## Must-dos when changing this subsystem

- Preserve `MergeCandidate` semantics (bounded evidence, first-non-empty metadata, argument order) when touching candidate flow.
- Respect `MaxPerOwner` and `Limits.Total` everywhere ranked results are produced, including approx/timeout fallback paths.
- Ranking/weight changes need regression coverage: extend `pkg/search/archetype_regression_test.go` (archetype specs with explicit weights + `MaxPerOwner`) and run affected entries from [[search-quality-evaluation-corpus]], comparing answer-shaped vs raw ranked output.
- Keep retrievers pluggable: implement the `Retriever` interface (`pkg/search/types.go`), register in service wiring, and let evidence merge handle overlap — never special-case one retriever's results downstream.
- If adding support-only retrievers, include service tests for both merge-with-primary and drop-when-alone behavior so evidence lanes cannot bloat results.
- Respect token budgets in packing: `Packer.Pack` renders into caller budget; `pkg/app/presentation` may do bounded reads only on already-ranked text.
- New `Ranker` implementations should also satisfy `ApproxScoreProvider` so pruning and timeout fallback stay score-aligned.
- Keep CLI flags (`cmd/agent*.go`), shared handlers and their `ToolDescriptor` memberships, and the docs (`pkg/app/mcp/CONTEXT.md`, `README.md`) in sync with behavior changes.

## Review checklist — problems to catch

- Duplicate candidates not merged: a retriever emitting handles that don't match existing handle construction (`knowledge.ParseHandle`/`NoteHandle`/`FileHandle`), producing duplicate rows instead of merged evidence.
- Per-owner caps bypassed: results assembled outside `Ranker.Rank`/`approxRankCandidates`, or `Owner` left empty so diversity limiting silently no-ops.
- Score blending broken: evidence added with the wrong `Channel`, weights changed without updating `ApproxChannelWeights`, or archetype regression tests weakened to pass.
- Budget overruns: packing or `presentation` reads ignoring `Limits`/budget caps; unbounded snippet expansion.
- Retriever added outside orchestration: retrieval calls from `pkg/app/answer`, `cmd`, or post-rank adapters instead of the service retriever list.
- Fairness/interleaving broken in semantic search: bypassing `interleaveScoredChunksByOwner`, changing the diversity key so doc-section/ontology chunks stop grouping by note, or treating limit as per-note instead of total chunks.
- Diagnostics changing behavior: explain/raw payloads computed via a second ranking pass or altering warnings/pack output.
- Indexed graph policy falling through to a live note-reader crawl, a persisted snapshot loader re-running filesystem freshness checks, or persisted readiness being presented as proof of live note freshness.
- Vector filters applied after a fixed-size global KNN result, which can silently drop the nearest eligible candidates; tie handling that lets vec0's internal equal-distance order define result membership.
- Ontology-node chunks promoted to candidates without catalog identity (stale-index leakage).
- Ad hoc embedding batchers added in indexing paths instead of going through `semanticruntime` lane policy.
- Timeout fallback regressions: errors on `context.DeadlineExceeded`/`Canceled` instead of degrading to approx ranking (`pkg/search/service.go`).
