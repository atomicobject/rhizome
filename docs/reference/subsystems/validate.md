# Validation subsystem guidance

## Scope

Vault-wide validation checks plus the fix-suggestion/apply pipeline. `pkg/validate` owns check execution (`RunSuiteOnce`/`RunSuiteOncePrepared` → per-check funcs), issue/fix data shapes, and fix application through `ApplyRepairSession`; consumers render. Entry points:

- `pkg/validate/registry.go` — typed check descriptors: public identity, aliases, default/all/audit membership, applicability, projection prerequisites, execution surfaces, remediation, runtime requirement, and implementation.
- `pkg/validate/catalog/catalog.go` — dependency-light canonical check IDs, public names, and aliases shared by validation, REST, and GraphQL.
- `pkg/validate/selection.go`, `applicability.go` — exactly-one-selector composition plus explicit `completed` / `not_applicable` / `blocked` prerequisite outcomes.
- `pkg/validate/suite.go`, `checks.go` — `RunSuiteOnce`/`RunSuiteOncePrepared` (read-only concurrent check fan-out, shared ontology runtime), result normalization, and registry-backed name resolution. Applying a reviewed result is a separate `ApplyRepairSession` call; there is no combined scan-and-apply entry point.
- `pkg/validate/types.go` — check id constants, `DefaultChecks`, `Issue`/`CheckResult`/`FixAction`/`Options`/`RunContext`.
- `pkg/validate/apply.go`, `fixes.go` — `BuildFixPlan`/`ApplyFixPlan` with safety tiers (`safe`/`needs_confirmation`/`agent_required`).
- `pkg/validate/fix_plan.go`, `transaction.go`, `repair_planner.go` — stable issue/action identities, validated repair-plan finalization, explicit write/rename/delete operations, connected transactions, and transaction-local conflicts.
- `pkg/validate/transaction_stage.go`, `transaction_journal.go`, `transaction_cleanup.go` — raw-byte composition, staged installation, journal-v1 recovery, rollback validation, terminal cleanup tombstones, mode preservation, and exact committed deltas.
- `pkg/validate/ontology_operation_adapter.go` — preview-only ontology `EditSession` adapter. Its dependency omits commit methods; conflicts produce no repair writes.
- `pkg/validate/ontology_edit_session_adapter.go` — converts a reviewed web edit-session preview into complete-file repair operations. One shared session identity connects mixed-file saves into a single journaled transaction.
- `pkg/validate/identifier_repair_adapter.go`, `identifier_repair_mapper.go` — sealed EFF-0048 intent mapping, consumer action binding, lease-held authoritative remapping, and identifier-required postcheck orchestration.
- `pkg/validate/identifier_check.go`, `identifier_inventory.go` — complete prepared-runtime preferred/alias inventory across note and embedded nodes, pool-aware reconciliation, structured collision evidence, and deterministic repair-plan assembly.
- `pkg/validate/postapply.go` — opaque vault-bound `IndexLockLease`, the `PostApplyRefresher` consumer contract, and prepared-runtime cleanup ownership. The repair engine alone owns lock release.
- `pkg/validate/repair_session.go` — validate-owned plan/apply session: consumes one reviewed in-memory `Result`, preserves sealed identifier authority, chooses the generic or identifier/mixed engine, and returns the exact held-lease prepared postcheck plus execution evidence.
- `pkg/validate/diagnostic_snapshot.go`, `run_snapshot.go` — complete public diagnostic snapshots and one immutable provider-current source view per content-reading suite run.
- `pkg/validate/repair_review.go`, `repair_path_reservations.go` — generation-bound repair review authority and shared admission for overlapping repair and manual-edit paths.
- `pkg/app/indexing/validation_postapply.go` — concrete borrow-only `PostApplyRefresher`: exact repair-delta mapping, canonical vault proof, held-lock projection, and runtime/close ownership transfer.
- `pkg/validate/lifecycle_policy.go` — raw before/after lifecycle classification for terminal effort history; caller metadata and claimed exceptions are validated against source bytes.
- `cmd/validation_product.go`, `cmd/validation_product_runner.go` — shared human/agent/CI grammar, rendering, canonical vault/config composition, lightweight projection, and explicit repair-session handoff.
- `pkg/app/validationrun/run.go`, `result.go` — neutral selection/applicability orchestration, additive JSON contract, and exit codes below CLI and projection wiring.
- `pkg/app/cli/validation_contract.go`, `validation_catalog.go`, `ci_renderer.go` — source-stable aliases plus human/agent/CI catalog and rendering. Thin Cobra fronts consume these actions.
- `pkg/app/validationproduct/projection.go` — read-only EFF-0046 adapter: one live/scratch projection refresh, domain-specific evidence, persisted code facts, prepared-runtime execution, and idempotent close.
- `pkg/app/web/validate.go` — web server also runs the suite; keep `pkg/validate` UI-agnostic.

## Design constraints

- Identifier block-id migration checks cancellation between notes, recursive sections, migrations, and reference-source scans. Cancellation discards partial diagnostics and repairs. The suite joins its checks before returning cancellation, so indexing releases its lease without publishing an incomplete snapshot as complete.

- Historical rename evidence must come from an actual matching wikilink outside code spans; textual prefixes and code examples do not prove that a rename orphaned a link. Direct check callers must supply the configured `RunContext.NoteMetadata` runtime when historical source projection is needed; a missing runtime reports a prerequisite error instead of weakening the repair candidate.

- **Admit a replacement before canceling active validation.** `RefreshCoordinator` advances the durable generation before canceling the older run, so older completion loses publication authority and returns `ErrRefreshSuperseded`. Failed replacement admission leaves the active run and its authority intact.
- **Invalidation fences earlier validation work.** Serve readiness owns durable invalidation before broadcasting the event, including before server binding. It cancels captured queued, startup, and running request contexts and atomically marks the retained snapshot stale while advancing the existing durable generation. Earlier runs cannot publish, complete with an error, or regain repair authority. Failed reconciliation queues no replacement; a later successful event or manual-save request may run the live projection and publish a fresh result.

- **Diagnostic error counts describe failed checks.** Recovery can block every selected check without executing any. Publish that as incomplete with blocked outcomes, deriving the snapshot error count from failed check outcomes instead of copying suite-level recovery errors.

- **Unexpired repair receipts survive capacity pressure.** Applied and failed reviews retain their terminal result through the advertised expiry; capacity may evict pending/stale reviews but must reject new admission with `repair_review_capacity_full` when only applying or terminal reviews remain. Expired receipts may be reclaimed. Process restart still invalidates in-memory authority.

- **Deterministic output.** Checks run concurrently (`RunSuiteOnce` goroutines) but results are re-sorted to the selected-check order; within a check, sort scanned paths and (effort, spec)-style pairs before emitting (see `frozen_scope_drift.go`). Same vault state ⇒ same issues in the same order.
- **Stable check ids.** Canonical ids are snake_case constants in `types.go` (`frozen_scope_drift`); CLI accepts kebab-case and aliases via `CanonicalCheck`. Ids are a public contract — JSON consumers and skills key on them. Never rename; add aliases instead.
- **One typed registry.** Every check has exactly one descriptor in `registry.go`; defaults, CLI help, aliases, runtime acquisition, and dispatch derive from it. Registry validation rejects incomplete descriptors, duplicate identities, and ambiguous aliases at startup.
- **One selector, explicit composition.** An invocation accepts omitted/`default`, `all`, fixed `audit`, or one named check. `validation.default.add/skip` and `validation.all.add/skip` are strict and deterministic. Explicit named checks bypass configured composition; `audit` is maintenance-only and never implied by `all`.
- **Applicability is data, never a silent skip.** Every selected check resolves to `completed`, `not_applicable`, or `blocked`. A completed outcome must have exactly one executed `CheckResult`; the other outcomes must have none. Legacy runner `Skipped` values are rejected at the product boundary. Explicit checks remain visible even when absent or blocked.
- **Recipe applicability follows selected discovery.** Both live and CLI resolve authoritative selection before feature facts and call `queryrecipe.HasDefaultSources` only when query-recipes is selected, covering `.rhizome/query-recipes`, `docs/query-recipes`, `docs/rhizome-md-templates`, and `.agents/skills`. A recipe or inspection/load diagnostic makes the check applicable so execution can publish its findings. Broken root symlinks remain diagnostics; missing or empty roots and unrelated skill files remain absent. Presence discovery does not cache an inventory or change suite composition.
- **Code-anchor applicability requires roots.** `code_anchors` uses `ApplicabilityCodeAnchors`: code must be configured and `VaultFeatureFacts.CodeAnchorRootsConfigured` must be true, meaning at least one language outside `code.disabledLanguages` has code folders after `obsidian.LoadCodeConfig` applies automatic scope (`obsidian.CodeAnchorRootsConfigured`); code on without named folders covers the whole project, so it counts. Both fact producers (`cmd/validation_product_runner.go`, `pkg/app/validationproduct/live.go`) set it. Without folders for an enabled language the outcome is `not_applicable` with a summary pointing at `rzm init --check`, folder limits, and `code.disabledLanguages`, never `blocked` on `rzm index`. `code_frontmatter` and `companion_docs` keep `ApplicabilityCode`.
- **Template frontmatter is a soft skip.** `code_frontmatter` checks that every note's frontmatter parses and that code-anchor definitions are valid. When parsing fails and the raw frontmatter block contains Templater `<% ... %>` or core `{{...}}` placeholders, the note is skipped and listed in one aggregated `Notes` entry. Other YAML errors remain `code_frontmatter_yaml_error` issues.
- **Snapshots retain applicability and indexed membership.** Published snapshots distinguish `completed`, `failed`, `blocked`, `not_applicable`, and legacy `skipped` outcomes. Public check names use canonical catalog IDs. Note counts and diagnostic note memberships derive from the indexed note inventory; producer hints alone cannot classify a path as a note. A type scope counts schema issues about the type plus issues whose note membership is a note of that type, resolved against the current ontology projection at query time; an interface scope does the same over its implementing types, which the serving layer resolves from the schema (see the stores note).
- **Browser-applicable means safe or confirmable.** Every issue may carry `agent_required` guidance, so "has a repair" filters use `repairAvailability=applicable` (a `safe` or `needs_confirmation` action), never mere action presence.
- **One run uses one immutable source view.** `RunSuiteOnce` captures provider-current note sources once for checks that consume note content, then shares the immutable reader and broken-link candidate catalog across concurrent checks and runtime preparation. The returned `RunContext` retains the caller's live reader so repair preconditions still detect source drift. Narrow suites that do not read note content skip this capture.
- **Repair review retains server authority.** A repair review selects stable action IDs from one in-memory result and binds them to its generation and plan fingerprint. Preview diffs are presentation evidence: standard line-based unified diffs (three context lines, line-numbered hunks, literal content) from `pkg/app/cli/init/diff.GenerateUnifiedDiff`, shared with edit-session plans. Apply rechecks the selection, confirmations, source preconditions, and shared path reservations before calling the canonical repair engine. Duplicate apply requests return the recorded terminal result.
- **Prerequisite evidence is domain-specific.** Validation and ontology projection evidence names the exact proven domain. Code checks establish the validation projection first, then inspect one persisted code snapshot. Unsupported scratch-CI checks return `blocked` plus the exact preparation command; validation/CI never builds code, embeddings, chunks, or graphs.
- **Projection ownership is one lifetime.** Product orchestration refreshes once, maps only explicitly fresh domains, runs completed checks through `RunSuiteOncePrepared`, and closes the projection once after checks. CI selects scratch; local/agent select live. Do not re-enter `EnsureFreshRuntime`.
- **Note projection is explicit.** `RunContext.NoteMetadata` carries the provider-aware `notemeta.Indexer` shared with indexing and ontology runtime acquisition. Suite and standalone runtime-backed checks validate it before journal, store, or lock work; no validation path selects a provider or falls back to a package-global runtime.
- **Identifiers are catalog-complete and pool-aware.** The public `identifiers` check reads preferred and alias claims for every eligible note and embedded ontology node from the prepared runtime, combines note-root raw aliases with projected field rows, and groups only claims sharing the schema-declared identifier pool. It preserves required preferred/alias mirror findings, but never falls back to the legacy note-frontmatter-only duplicate pass or opens another store.
- **Alias claims retain every authored field obligation.** Types may declare both `alias` and `aliases`. Inventory deduplicates canonical owner/value claims while retaining their source-field associations; one losing value can require removals from several fields. A canonical rewrite carries one mirror destination and sealed additional removal fields, including their normalized authority in discovery fingerprints and defensive snapshots. Collision repairs and strategy migrations remove retiring values from every authorized field, preserve unrelated values and schema source bindings, and keep one preferred rekey per owner. Declared alias fields enter resolution only for identifier-owning types, and custom rewrite fields apply only to the matching owner type, including its unchanged instances. Typed-field and free-link discovery share that type authority; ordinary fields on unrelated types never become identifiers through a rewrite elsewhere. Standard raw root aliases retain their metadata compatibility lane. Note roots retain the required raw `aliases` mirror; nonroot rewrites retain their declared mirror convention. Apply consumes only source-bound field edits and the exact held postcheck.
- **Derived identifier phases retain exact owner authority.** After a successful primary ontology preview, the identifier mapper advances alias-phase owner fragments using the sealed preferred OldRef/NewRef transition. It retains the current physical note path until the governed rename runs, rejects inconsistent or nonunique transitions, and never borrows authority from an inbound target or a similar sibling. Descendant discovery retains every alias field authorized for the child type while preserving its inherited mirror convention; parent-only custom fields do not become child aliases. Original source, range, membership, preview-conflict and held revalidation checks remain authoritative.
- **Identifier output is executable or explicitly non-materializable.** Pool collisions expose canonical claimants, keeper basis, replacements, plan fingerprint, and a confirmation-tier action backed by the sealed EFF-0048 repair assembly. Author-supplied/non-allocatable pools and other collisions without deterministic writes remain `agent_required` with structured guidance; they must not become unbacked executable actions or lose their conflict reason.
- **Identifiers are catalog-complete, pool-aware, and strategy-dispatched.** The public `identifiers` check reads preferred and alias claims for every eligible note and embedded ontology node from the prepared runtime, combines note-root raw aliases with projected field rows, and groups only claims sharing the schema-declared identifier pool. Frozen preferred/alias reservations flow through `IdentifierFormat.StrategyContract`: sequential repair retains monotonic max-plus-one behavior, while datetime repair parses the collided preferred value's timestamp family and chooses its lowest free canonical suffix from `-2`. Arbitrary historical aliases remain collision claims even when they do not parse as an allocatable value. The check preserves required preferred/alias mirror findings, but never falls back to the legacy note-frontmatter-only duplicate pass or opens another store.
- **Identifier output is executable or explicitly non-materializable.** Pool collisions expose canonical claimants, keeper basis, replacements, plan fingerprint, and a confirmation-tier action backed by the sealed EFF-0048 repair assembly. Noncanonical datetime preferred values are separate `agent_required` grammar findings; validation never derives a replacement family from the filename and never imposes ongoing filename/id equality after a move. Author-supplied/non-allocatable pools and other collisions without deterministic writes remain `agent_required` with structured guidance; they must not become unbacked executable actions or lose their conflict reason.
- **Identifier strategy migration is schema-first and pool-complete.** After an allocatable pool changes between `SEQUENTIAL` and `DATETIME`, the identifiers check classifies the prepared typed members and recovers unresolved note roots only from exactly one selector-matched allocatable type plus batched raw frontmatter. Recovery still honors identifier-gated membership: it filters selector candidates without an authored preferred identifier before ambiguity checks, so an undeclared freeform path match stays untyped while an authored old-strategy identifier is recoverable. Canonical target-strategy members are retained as reservations, so an interrupted apply or branch merge can migrate every remaining coherent old-strategy member. Missing identifiers on explicitly typed members, ambiguous identifier-bearing candidates, malformed or incompatible source values, and target conflicts block the pool. Coherent pools emit one confirmation action whose sealed rekey assembly composes with collision components over one source snapshot; note roots use governed moves, embedded roots rekey in place, and apply retains lifecycle, lease, and postcheck authority.
- **Reconciliation diagnostics are additive product evidence.** `Result.IdentifierReconciliation` (JSON `identifierReconciliation`) carries the deterministic plan separately from non-fingerprinted diagnostics. Human, JSON, and GitHub CI render all six stages in stable order: inventory, git provenance, reference discovery, transaction construction, apply, and post-validation. A stage not performed by the current run is zero. Git provenance is keeper-selection evidence, so collision-free inventories skip it and collision runs query only canonical collision claimants; the full frozen inventory still owns reservations and replacement allocation. Identifier apply records its apply/postcheck durations as non-JSON execution evidence; `BuildValidationResult` and the post-build `validationrun.AttachFixExecution` seam copy them into a fresh public envelope without mutating the reviewed planning result.
- **Exit codes are stable.** Human, agent, and CI surfaces use `0` for clean/not-applicable, `1` for findings, and `2` for configuration, execution, or blocked-prerequisite failure. Exit 2 takes precedence over findings.
- **Consistent issue shape.** Every finding is an `Issue{Code, Path, Target, Message, ...}`; structured extras go in `Data` (JSON-serializable, clients union on `Code` — e.g. `FrozenScopeDriftData`). Messages should tell the agent what to do next, not just what's wrong.
- **Issue variants are optional grouping evidence.** `Issue.Variant` (`IssueVariant{Key, Label}`) names the case of a finding within its code such that one decision resolves every finding in it: sorted candidate types for `type_ambiguous`, declared type and candidates for `declared_type_mismatch`, type and field for field- and section-level ontology codes (plus expected target for `wrong_target_type`), the missing target for broken and placeholder links, the unknown name for unknown declared types and view targets, and the pool for `identifier_strategy_migration_required`. Per-instance codes (identifier collisions, link hygiene, code anchors, query recipes, code frontmatter, companion docs) emit none. `StableIssueKey` excludes the variant; evidence a resolution needs goes in `Data` (`type_ambiguous` carries `candidateTypes`). Ontology producers stamp `ValidationIssue.VariantKey/VariantLabel` through `pkg/ontology/issue_variant.go`, and changing which persisted findings carry variants bumps `OntologyMaterializationVersion`. Snapshots persist the variant; the diagnostics and summaries filters accept `variant` only together with `code`; `POST /api/v1/validation/groups` counts one scope by check, code, and variant with the summaries filter, so a group always equals its narrowed summary.
- **Remediation joins only after stable issue identity.** Every emitted issue code has a `remediation_registry.go` classification with an executable builder or a structured non-fixable reason. Enrichment runs after stable issue-key assignment and joins suggestions by that exact key before `BuildRepairPlan`; path/code/count inference must not attach an operation to a different finding.
- **Migration buckets summarize full issue sets.** Checks may emit `migrationBuckets` when repeated issues share one remediation shape. Buckets are computed before `--max-issues` truncates `Issues`, include safety tier/count/affected paths, and must not imply an automatic fix for contentful fields, wrong-type links, or query recipe drift.
- **Product apply guidance preserves invocation authority.** Callers pass one shell-quoted positional command through `Options.ApplyCommand`; the corresponding internal `Result.ApplyCommand` is non-JSON and `BuildNextActions` exposes it as `nextActions.safeAutoFixCommand`. The command retains the original selector and mutation-relevant vault/filter/scope/lifecycle flags rather than reconstructing authority from expanded checks. Deterministic per-check expansion is a legacy/internal fallback only.
- **Next actions cover exact issue keys and remain executable.** Confirmation and agent-required actions preserve the original selector/options and cover their precise stable issue-key set. Confirmation actions must be replayable through the public human `rzm validate fix` surface; otherwise they are `agent_required` with an explicit reason. A post-apply rebuild re-scopes the repair plan and next actions to the originally selected completed checks before returning it.
- **Soft skips use `Notes`/`Skipped`, not issues.** `CheckResult.Skipped` + `Summary` when a check can't run at all (no ontology schema, no intel store); `CheckResult.Notes []string` for per-item soft skips (e.g. unparseable `created-at`/`last-updated` timestamps). Notes never count toward `IssueCount` or flip `OK`.
- **`OK` and output limits are derived.** Finalization forces `OK=false` when `IssueCount > 0` or `Error != ""` and centrally truncates returned issues to `MaxIssues`; checks must still compute the true `IssueCount`, full migration buckets, and complete internal issue evidence before finalization. Stable action-to-issue attribution and post-apply reporting both use that complete set, never only the rendered prefix.
- **Performance over large vaults.** Batch store reads (`CurrentNotePropertyValues`, `OntologyEdgesForPaths` take path slices); share the ontology runtime via the `*WithRuntime` variants instead of re-acquiring the index lock; lazy-read note bodies and cache per note (`deviationsByEffort` pattern). Identifier migration reads selector assessments only for note paths absent from the typed root inventory, and reference/source/transaction discovery runs only for a materializable migration. No per-note store round trips in loops.
- **Identifier reconciliation plans complete source sets.** `pkg/validate/identifierreconcile` binds one canonical rewrite union to sealed field/link discoveries, the ontology schema hash, and every Markdown path/content hash—including notes with no relevant occurrence. The reviewed `RepairPlan` fingerprints that sealed assembly authority, so apply rejects a separately supplied assembly even when its physical operations happen to match. Source-bound nonblocking diagnostics remain fingerprinted `followUps` in both plan and execution reports; they never become executable operations or blocking conflicts. Assembly rejects caller-built spans, omitted discoveries, stale/mixed snapshots, incomplete preferred/alias/descendant obligations, and diagnostics that cannot be mapped to collision membership.
- **Collision membership survives batching.** Identifier rewrite, field, link, move, diagnostic, and postcheck intents carry sorted plural membership keys. Identical physical work unions membership rather than discarding action/issue provenance. A preferred rekey's governed rename, identifier/alias edits, descendant edits, and all inbound rewrites map to one EFF-0047 action; EFF-0048 does not define a transaction or lease type.
- **Full-source freshness is both review and apply authority.** `BuildIdentifierRepairPlan` re-enumerates the direct-filesystem source inventory before returning a reviewable plan. Apply canonicalizes that reviewed plan, verifies its supplied fingerprint, then `RepairAssembly.RevalidateCompleteSnapshot` re-enumerates the same complete inventory and schema under the opaque vault-bound lease immediately before an exact-fingerprint remap. Cache readers, caller-derived transactions, and synthetic no-op writes cannot substitute for either barrier.
- **Parent cycles belong to the ontology check.** The `ontology` check follows every note record's `@display(role: PARENT)` link through the indexed edges and reports each cycle once as `parent_cycle`. The issue is anchored on the cycle's lexically first record, lists every record in cycle order in `ParentCycleData.records` and the affected note paths, and is in scope for a postcheck when any record in the cycle is. Records whose chain leads into a cycle without being part of it are not reported. Choosing which link to change is `agent_required`.
- **Opt-in checks stay opt-in.** `fragile_external_link`, `orphan_block_ids`, and `placeholder_links` never enter `DefaultChecks` — their fixes are deliberate cleanup passes.
- **Links resolve the way Obsidian resolves them.** Link-extracting checks skip links in fenced, indented, and inline code. A link that fails Rhizome's note cache falls back to `obsidian.VaultFileIndex` (Obsidian's `getLinkpathDest`): case-insensitive names over every file outside dot-folders, only `.md` implied, ambiguous names resolved by source folder then shortest path. `.rhizome/ignore` never affects resolution, and a resolved Markdown file outside the indexed notes is read on demand so its headings and blocks are still checked. link-hygiene uses the same index, so a real note or attachment always beats an alias and a dot in a name is never an extension; a hygiene rewrite is `safe` only when the link resolves to the same unambiguous file before and after. Wikilink heading fragments compare with Obsidian's `stripHeading`; Markdown-link fragments also accept GitHub slugs and HTML anchors; block IDs stay case-sensitive.
- **Git evidence is bounded and exact.** History commands run with `core.quotepath=false`, parse `-z` output by field position (so no file name is quoted or mistaken for a header), set `GIT_NO_LAZY_FETCH=1` and `GIT_TERMINAL_PROMPT=0`, and time out (30 s for the log, 5 s per rename check). A partial clone, shallow clone, missing repository, empty history, ownership refusal, git failure, or timeout makes history unavailable with a specific note, and every unresolved link stays broken. One suite run scans unresolved links and reads history once, shared by `broken_links` and `placeholder_links`.
- **One owner per broken link.** `broken-links` reports wikilinks and Markdown note links; the ontology projection never emits `broken_note_link`. Starter managed-block templates (an `agents/AGENTS.md` whose starter directory holds a `template.yaml` declaring that directory name as its `id`) are skipped because their links target the receiving repository.
- **Broken versus placeholder is git evidence.** `broken-links` counts only unresolved note targets whose name appears among deleted or renamed-away paths (`git log --diff-filter=DR`, loaded lazily when something is unresolved) or among files still tracked in `HEAD` or the index, so uncommitted deletions and renames count. Other unresolved targets are placeholders, reported by the audit-only `placeholder_links` check and noted in `broken-links`. No history, a shallow clone, or `validation.brokenLinks.placeholders: strict` counts every unresolved link as broken. Fragment failures are always broken.
- **Retargets need strong evidence.** `needs_confirmation` retargets require one strong candidate: the same title up to case, punctuation, and spacing, or a git rename whose pre-rename source already contained the link. Candidates never include the source note, never cross the attachment/note boundary or the periodic-date/non-periodic boundary, and must contain the link's fragment. Partial title matches are `agent_required` evidence (`confidence: low`). Retarget edits set `PreserveDisplay`, which keeps the authored text as the alias and rewrites only links with exactly the reviewed fragment.
- **Explicit apply selection replaces tier selection, never safety checks.** `selectRepairActions` in `apply_reporting.go` is the single eligibility choke point. With empty `Options.ApplySelection` it applies `safe` actions plus `needs_confirmation` actions the `Confirm` callback approves. A non-empty selection (CLI `validate fix --apply --action <id-or-issue-key>` / `--from-plan <file>`) applies exactly the actions whose `ID` or any `IssueKeys` entry matches, whatever their tier, and never consults `Confirm`. Unlisted actions, including safe ones, are skipped. Any entry that matches no action, or any selected `agent_required` action, is an error raised before lease acquisition, journal recovery, or mutation. `ApplyRepairSession` validates the selection against the reviewed plan first, and the identifier/mixed path honors it through `ApplyFixPlan` because its lease-held replan must reproduce the reviewed fingerprint. Fingerprint, source-hash, lifecycle, and journal checks are unchanged.
- **Repair plans are immutable values.** Executable plans pass through `FinalizeRepairPlan`: stable ids, complete action/issue membership, raw-byte source hashes, required check selectors, and operation identities are required; affected paths and connected transactions are rebuilt deterministically. Plan fingerprints cover the lease-revalidation marker, each action's automation authority, operation effects, lifecycle claims/conflicts, required checks, and stable destination preconditions. Derived transactions are never caller authority.
- **Conflicts isolate at transaction scope.** Shared paths/identities form connected components. Overlapping spans, destination collisions, path-effect collisions, stale source, ontology preview conflicts, ambiguity, and lifecycle protection block only their connected transaction; independent transactions remain eligible and receive their own execution evidence.
- **Rename vacancy is stable authority with live enforcement.** A governed rename carries its exact and portable case-fold destination-vacancy requirements in the fingerprinted operation. Transaction preparation enforces those requirements against the live directory while holding the apply lease; runtime sibling inventory never enters the plan fingerprint, and a newly occupied destination skips only its connected transaction with replan guidance.
- **Repair paths preserve requested final spelling.** Resolve and contain the parent directory, then retain the canonical caller-requested basename for installation. This keeps case-only renames observable on case-folding filesystems while `Lstat`/`SameFile` preconditions still inspect the existing source and parent symlinks cannot redirect writes outside the vault.
- **Repair publication removes before installing.** Prepared states and journal entries share deterministic effect-then-path order: final absences precede final files, including after adding a completion receipt. Reverse rollback removes published rename destinations before restoring their sources. Recheck the relevant rename endpoints immediately before each rollback mutation as well as during complete preflight; recreated distinct sources remain blocking evidence. This prevents new ambiguous intermediate states without guessing intent for older journals that already contain both endpoints.
- **Legacy rollback order is private execution state.** After full validation, order the rollback states by the same effect and path before reversing them. Preserve the stored manifest and artifact order so valid older alphabetical journals recover without introducing duplicate endpoints; an already-recreated distinct source still blocks before mutation.
- **Journal before artifacts or writes.** Journal v1 lives under `.rhizome/repair-journal/v1/`. Prepare publishes and syncs a complete manifest before backup/stage artifacts, including sorted operation/action/issue membership so restart reporting does not depend on a caller's current plan, then durably records each successfully created artifact in `ownedArtifacts`; path shape alone never proves cleanup ownership. Older v1 manifests that omit all membership fields remain recoverable, while partial membership is rejected. Commit installs all staged final states, rolls back the whole transaction on an in-process failure, and publishes `COMMITTED` only after success. Recovery preflights every discovered journal before mutating any vault path. A prepared journal rolls back only when current bytes/modes, rename endpoints, durable ownership, and backup hashes prove a known original/final state. A committed journal is forward-verified, refreshed, postchecked, then cleaned; it never shares a call with a different new plan, which must replan after recovery. Startup only stabilizes unfinished prepared writes and terminal cleanup; committed source drift does not block startup or overwrite later edits. Committed journals remain intact and block validation and repair writes until strict recovery succeeds or the conflicting evidence is explicitly reconciled. Cleanup preflights an allowlist, removes owned artifacts, atomically renames the digest directory to `.cleanup-<digest>`, and fsyncs the journal root before deleting metadata. Unix fsyncs directory handles; Windows cannot flush them through Go, so it validates namespace paths without swallowing regular-file sync errors and uses `MOVEFILE_WRITE_THROUGH` for manifest publication, tombstone detachment, and vault replacement. Tombstones are terminal authority and can only resume cleanup, never rollback. Their mutable best-effort manifests retain only transaction-bound operation IDs and canonical checks; action/issue reporting is reconstructed only from an exact reviewed-plan match. Unknown root entries, metadata, drift, or corrupt evidence block new repairs without destructive recovery.
- **Pending journals block ordinary validation before projection mutation.** Product orchestration preflights journal evidence before calling the live/scratch projection refresher and repeats the check through `BeforeMutation` while the canonical index lock is held, before any projection store opens. Read-only suite execution returns `OK=false`, no checks, and no executable `FixPlan`; each selected product outcome is `blocked` with the exact recovery command. Evidence includes the canonical originating check ids persisted by each transaction; recovery unions checks and affected paths from every recovered state. Cleanup-only terminal recovery is a recovery-only barrier: one zero-delta refresh and held postcheck, no fresh mapper or mutation, then deterministic replan guidance. If terminal cleanup already removed its manifest, the identifier adapter falls back to the canonical reviewed transaction check union, then registry defaults.
- **Native namespace publication uses the same owner.** `ApplyNamespaceMutation` acquires the existing lease, recovers older work before invoking its read-only planner, and admits only witnessed rename/write effects grouped by one engine-owned identity. Native v2 purpose journals retain both overwritten endpoints, admitted standalone Git indexes, proved lock ownership, and bounded receipt reporting. Before a decision, rollback restores required files and admitted staging; synchronized COMMITTED or RESTORED ends historical rollback authority. One settled-decision field certifies marker durability and optional Git release for both Git and non-Git transactions. Terminal replay refreshes current regular files and absences across the recorded footprint without replaying historical renames. Exact directory entries own current source spelling; a proved case or normalization alias retires the recorded key and adds its observed current key. Private canonical caseless keys select candidates; physical identity still proves aliases and exact distinct entries remain separate. Fresh per-folder listings and file hash/mode observations must agree before and after refresh. Existing confined-parent resolution must produce exact current parent spelling; stale parent casing that it cannot normalize remains a conflict. Native cleanup names preserve the terminal decision after marker or manifest removal and resume cleanup only. Generic v1 recovery and postchecks remain strict. Destination-parent preparation retains empty folders on rollback, matching existing CLI behavior. An explicit invocation-local NamespacePostCommit callback may borrow the same lease synchronously after required convergence and cleanup, only for a successful committed current request. Optional failures and counts remain caller-owned; recovery and required failures never replay it.
- **One disk writer and one lease owner.** Ontology repair adaptation calls `PreviewCurrent` only. The transaction engine owns note writes and the index-lock release lifecycle; post-apply refreshers receive an opaque held token and cannot release it. `IndexLockLease.RequireHeldForVault` binds that proof to the adapter's normalized `.rhizome/index.lock`, not merely any held lock.
- **Interactive edits use the same writer.** Browser edit sessions replay and preview through `ontology`, adapt the reviewed complete-source replacements with `BuildOntologyEditSessionRepairResult`, and apply them through `ApplyRepairSession`. The repair engine owns the canonical lease, journal, exact refresh, postcheck, and durable completion receipt for both Markdown and provider-aware HTML saves. Browser code never calls `EditSession.Commit` or `CommitWithOptions`. Apply and completion-receipt publication wait cancellably for the index lock, requesting background priority even when the holder shares the process. Source preconditions remain checked under the acquired lease.
- **Refresh and postcheck share the commit lease.** The public refresher signature remains `Refresh(ctx, lease, changed, renamed, deleted)`. Its `PostApplyRefreshResult` transfers a prepared `*ontology.Runtime` plus idempotent `Close()` ownership; the engine passes that runtime and a private exact check/path scope to `RunSuiteOncePrepared` while the same vault-bound lease is held, then closes it before releasing the lease. A browser edit-session save (every action `ontology_edit_session_commit`) postchecks only the notes it wrote: ontology issues whose note or fix target is one of them, and the block-id migration sweep over just those notes. Prepared ontology-only postchecks capture source bytes only for affected notes; dependent issues already present in the prepared runtime remain in scope when their fix target is affected. A block-id migration that rewrites references lazily captures the complete source inventory before producing its safe fix. Other selected checks keep a whole-vault source snapshot. Whole-vault validation follows through the runtime's background refresh instead of holding the lease inside the save. Identifier apply requires this orchestration and owns its callback. Check execution/runtime errors retain committed evidence; ordinary findings do not create a recovery loop and remain visible through `RemainingFindings`, issue keys, and next actions.
- **Apply is one validate-owned session.** `ApplyRepairSession` consumes the already-reviewed in-memory `Result` and exact `RunContext`; JSON round trips are invalid because private identifier assembly/binding authority would be lost. It rejects missing refresh orchestration and disagreeing canonical roots before recovery or mutation, routes identifier/mixed plans through `ApplyIdentifierRepairPlan`, and routes generic plans through `ApplyFixPlan`. Postchecks include completed checks plus transaction/recovery-required checks, never selected blocked/not-applicable checks. A mutating success returns the actual `RunSuiteOncePrepared` result and `FixExecution`; no legacy second refresh exists.
- **Committed deltas are exact.** `changed` names final paths whose bytes differ after repair (including an edited rename destination, but not an equal-content rename), `renamed` records source/destination pairs, and `deleted` names final absences. Rollback reverses those effects: a rolled-back creation is deleted, not changed, and an edited rename maps `changed` back to its original path. Prepared recovery replays that rollback delta until cleanup completes; a later rollback precondition failure refreshes already-completed mutations and retains the partial journal. Refresh, execution reports, and recovery replay use the same deterministic delta.
- **Historical exceptions are proven, not declared.** Terminal-effort lifecycle authority comes from the raw source and staged result under the held lock, not caller metadata. The narrow exception requires claims to reconstruct every output byte; uncovered content, link-token escape, metadata mismatch, rename, or deletion is protected unless historical mutation was explicitly enabled. Post-closure history appends require an exact parser-recognized, line-anchored level-2 allowlisted section and insert at its next real level-2 heading or EOF; paragraph text, fenced/frontmatter lookalikes, and deeper headings never grant authority.

- **Soft item notes stay distinct from product outcomes.** `CheckResult.Notes []string` records per-item caveats without changing `IssueCount`. A whole-check absence/prerequisite failure belongs in applicability as `not_applicable` or `blocked`; legacy `Skipped` results must not cross the product boundary.
- **Maintenance checks stay in audit.** `frozen_scope_drift`, `fragile_external_link`, `orphan_block_ids`, and `placeholder_links` have fixed `audit` membership and are excluded from built-in `all`. Config may promote one deliberately into a configured suite.

### Native Git preparation

`pkg/validate/namespacegit` prepares the Git effect of admitted native namespace moves from engine-captured original endpoint bytes/modes in exclusively owned scratch. It returns canonical index/lock paths, raw original admission authority and separate standalone rollback/candidate snapshots. The engine alone persists those artifacts, acquires its proved-owned lock, revalidates the raw witness before authored publication, and owns decisions, release and recovery. Staging follows actual `git mv` semantics for the moved entry, including flags, intent-to-add and resolve-undo state; normalization preserves equivalent original rollback staging while split/sparse encoding and cache bookkeeping may change. Every command suppresses hooks/fsmonitor and binds its copied index/worktree. Redirected metadata or inherited Git selectors hard-refuse; cancellation stays cancellation. Only unsupported layouts or safe preparation failures permit the engine's explicit prepublication filesystem fallback, with truthful per-move history in mixed batches. See the [helper contract](../../../pkg/validate/namespacegit/CONTEXT.md).

## Must-dos when changing this subsystem

- New check = add its stable const in `types.go` and one complete descriptor in `registry.go`; CLI help, aliases, defaults, runtime acquisition, and dispatch derive from that descriptor. Document behavior in `docs/specs/process/audits.md` and managed guidance where relevant.
- Unit tests per check, table-driven, beside the implementation (`frozen_scope_drift_test.go` is the model: temp-dir vaults/fakes, no personal vault data). Cover: zero findings, findings, soft-skip Notes, and full issue production before centralized truncation.
- Test each contract at its live owner: real scans and `RunSuiteOncePrepared` own findings and repair actions, `findCandidateTiers` owns candidate ranking, byte edits go through `BuildRepairPlan` and `ApplyFixPlan` with the action's own safety, the product layer owns applicability and rendering, and `IndexValidationSnapshot` plus the refresh coordinator own publication and repair authority. A fail-closed path test names the guard it reaches (Markdown provider source admission or `StableIssueKey`) and pairs the rejection with a valid control. Do not add exported convenience wrappers for tests.
- Identifier tests additionally cover note and embedded preferred/alias claims, shared-vs-distinct pools, materializable and agent-required collisions, mixed executable/blocked components, stable action ids, complete-source repair assembly, prepared-runtime reuse, and the six-stage diagnostics envelope.
- Respect `--max-issues` (default 20, wired through `Options.MaxIssues` → `RunContext.MaxIssues`): runners return the complete deterministic issue set; `finalizeCheckResult` captures every stable key, then truncates rendered `Issues` while preserving the **full** `IssueCount`.
- Acknowledgement/resolution markers: when a check supports suppressing a finding in-note (e.g. `frozen-scope-drift acknowledged` + spec id in an effort's `## Deviations` section, matched case-insensitively), define the marker as a named constant, skip silently when matched, and document the convention in `audits.md`.
- Fixes attached to issues go through `FixAction` with an honest `Safety` tier; the repair session postchecks the committed result under the held lease — fixes and recovery must be idempotent.
- Post-apply runtime ownership is linear: the refresher returns the prepared runtime, the engine borrows it for `RunSuiteOncePrepared`, and `PostApplyRefreshResult.Close()` is called idempotently before lock release. A missing refresher fails before mutation; a refresher error or postcheck failure leaves committed journal evidence for forward recovery. There is no no-adapter or second-freshness fallback.
- Fixes attached to issues go through the repair plan/transaction engine with an honest safety tier. `rzm validate fix [selector]` plans by default; `--apply` is explicit, and postchecks use the prepared runtime returned by exact-path refresh rather than re-entering `EnsureFreshRuntime`.
- Closed/terminal entities are out of scope where lifecycle docs say so (frozen-scope-drift skips `complete`/`archived` efforts per SPEC-0051).

## Review checklist — problems to catch

- Registry drift: a stable check constant lacks a descriptor, descriptor metadata is incomplete, or aliases collide.
- Suite drift: audit membership leaks into built-in all, explicit selection validates irrelevant configured overlays, or add/skip overlap/nonmember skips are accepted.
- Outcome drift: a selected check disappears, a blocked/not-applicable check executes, a completed check has no/duplicate result, or a legacy `Skipped` result crosses the product boundary.
- Prerequisite lies: one probe claims multiple unproven domains, code freshness is inferred by walking roots, scratch CI builds an index, or output implies the persisted timestamp proves live-worktree freshness.
- Unbounded scans: per-note store queries inside loops, missing path-slice batching, re-acquiring the ontology runtime/index lock when `RunSuiteOnce` already pre-resolved one.
- `--max-issues` violations: a runner truncates before finalization, finalized `Issues` exceed the render limit, or `IssueCount`/internal issue keys reflect only the rendered prefix.
- Bucket/truncation drift: migration buckets computed only from truncated issues, or bucket safety tiers that imply silent repair for agent-required work.
- False positives on closed/archived entities (lifecycle-terminal efforts, archived notes) or on pairs already acknowledged via a documented marker.
- Checks reading files outside vault scope: bypassing `RunContext.NoteReader`/`VaultDef` with raw `os` calls or absolute paths not normalized through `pkg/paths`.
- Nondeterminism: unsorted map iteration feeding issue order, goroutine results not re-ordered.
- Soft per-item conditions reported as issues (inflating exit code 1) instead of `Notes`; whole-check prerequisites represented as legacy skips instead of typed outcomes.
- Missing tests for new finding `Code`s or new `Data` payload shapes; `Data` payloads that aren't JSON-serializable.
- Fix edits without a safety tier, or "safe" fixes that rewrite content beyond the issue's span.
- Repair operations with missing raw source hashes, incomplete source/destination paths, caller-authored lifecycle decisions treated as authority, or transaction conflicts collapsed into one global failure.
- Recovery that restores over unknown user edits, trusts an unhashed backup, creates artifacts before a durable manifest, or deletes journal evidence before refresh/postchecks succeed.
- Recovery that mutates an earlier prepared journal before every later journal passes preflight, combines recovered state with a different new plan, omits originating check selectors, or treats a recreated rename source as safe to overwrite.
- Delta drift: edited rename destinations omitted from `changed`, case-only moves treated as unrelated collisions, or recovery refreshing a different path set than the original commit.
- Any ontology adapter dependency exposing `Commit`/`CommitWithOptions`, or a `PostApplyRefresher` that can construct/release the engine's index-lock lease, expose its cleanup function, accept a token for another vault, or trigger a second freshness/index pass during prepared-runtime postchecks.
- Identifier repair assembled from caller-supplied ranges/plans, different field/link inventories, unmatched diagnostics, or a source/schema snapshot that was not revalidated under the apply lease.
