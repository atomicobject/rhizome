# CLI layer guidance

## Scope

- `main.go`: loads `.env` upward (`config.LoadDotEnvUpwards`) then `cmd.Execute()`. Nothing else belongs here.
- `cmd/`: one file per Cobra command or cohesive product surface (`create.go`, `validation_product.go`, `validation_product_runner.go`, `index.go`). Files define `new<X>Cmd()` constructors; wiring happens via `rootCmd.AddCommand`/parent `AddCommand` (see `cmd/root.go`, `cmd/agent.go`).
- `pkg/app/cli/`: orchestration/business logic for user-facing commands (`ListFiles`, `RenameNote`, `BuildFileContextText`, ...). Accepts `VaultDefinition` + `NoteReader`; testable without Cobra. Validation keeps its neutral run/result contract in `pkg/app/validationrun`, with source-stable aliases and renderers here.
- `pkg/app/cli/init/`: owns `rzm init` — config detection/migration, managed `AGENTS.md`/`CLAUDE.md` fences, starter scaffolds, and skill templates under `templates/`; RHIZOME.md templates are embedded directly from `docs/rhizome-md-templates/`.

## Design constraints

- **Diagnostics are offline evidence reads.** `rzm diagnostics index|reports|report|logs` reads bounded plain files through `pkg/app/cli/diagnostics` and `pkg/diagnostics`. Explicit vault directories bypass configuration. This family never opens the main index, constructs a recorder, or starts a runtime. It is an intentional CLI-only recovery surface; MCP parity would introduce a runtime dependency. Preserve one valid JSON result, stored records, coverage warnings, and measured summaries without automatic anomaly claims.
- **CLI and desktop share executable authority.** `pkg/app/repoexec.Select` is an inert resolution of external ownership, development builds, managed pins, and global fallback. CLI dispatch retains command exceptions and interactive trust; the one-shot desktop bridge in `pkg/app/desktop` requires explicit canonical-checkout trust before repository-selected code runs. Folder inspection performs no probe, installation, or trust write. `rzm desktop` stays on the invoking executable without a trust check, like `trust`, because it only hands a path to the desktop app through `open` process arguments. Desktop repository discovery reads Git metadata files and never runs `git` or repository code; index seeding runs only the worktree's own selected executable, after the same trust check. Update artifact smoke tests run in the extracted candidate's directory with delegation disabled, never in the invoking repository. Desktop global installs target only the user's owned `~/.local/bin/rzm` from a neutral update-planning directory and refuse symlinked destinations; they never advance repository pins.

- **Repository executable trust precedes execution.** Global dispatch requires user-local trust for the canonical checkout before a repo-selected executable, version probe, or bootstrap can run. Update commands in a pinned checkout also require trust, while staying on the global executable, because their downloaded binaries run a version probe. Delegation bypass variables are captured before repository dotenv loading. Noninteractive callers receive an actionable refusal; `trust` and `untrust` bypass delegation. Direct executable invocation and external binary managers retain their own authority. Trust accepts future changes in that checkout; it is not a sandbox.
- **Provider credentials are user-local.** `credentials import` reads explicit stable 1Password item references and saves once only after every read succeeds. Preserve unrelated global settings and environment precedence; never print values. Builds and releases never embed shared provider credentials.
- **Project KB is retired.** Init does not offer or embed the project KB starter. Existing installed files remain in user repositories; an existing selection receives an actionable error until its workflow template choice is changed.

- **Effort starter upgrades preserve concrete allocation ownership.** The shared `Effort` interface exposes identity without allocating it. Init may carry an adopted allocation contract to a new concrete sibling only when the shared interface and upstream contracts establish the same pool; contradictory or unrelated reuse fails closed. Agentic Engineering installation adds explicit effort HTML includes while preserving configured Markdown selection and unrelated includes.

- **Code execution is a bounded host control.** `agent code execute` is a thin front over `pkg/app/agentcode.Execute`. It resolves the executable, canonical vault, session and explicit Rhizome write authority, then runs the supplied JavaScript with managed client lifetime. The outer command's one-shot plan is empty; each catalog operation retains its existing runtime ownership. Inline code and stdin require no artifact directory. JSON script input uses the same 1 MiB limit before whitespace trimming; file input reads at most the limit plus one byte before parsing. Node is required, errors/results stay machine-readable, and the host cleans up on completion or interruption. It is not a sandbox or a new operation handler.

- **Code mode shares application work below Cobra.** `agent code serve` serializes catalog-selected operations over stdio. Shared tools use the same request preparation and handlers as their CLI fronts; local-only families extract functions called by both fronts. Never replay Cobra commands, capture process-global stdout, or spawn a command per call. The service binds one vault and detects configuration changes; each in-process call builds and closes its applicable runtime resources, and catalog-admitted typed reads run in the vault runtime instead ([[code-mode-skill-scripts|SPEC-0115]]).

- **Code-client generation is explicit.** `cmd/agent_code.go` parses the runtime-free surface/describe/generate fronts and delegates selected artifacts to `pkg/app/agentcode`. Generation writes only an explicit task directory; startup, init and index never generate clients. The generated adapter uses an explicit executable and vault with argument arrays, preserving existing CLI result and runtime semantics.

- `rzm index` selects work from configuration and freshness through the unified pipeline. Top-level `--code` and `--semantic` flags and their force overrides are retired; `--rebuild` explicitly replaces the full unified database under the index lock.

- **Direct mutations share the vault writer lease.** Note rename/move/delete, heading rename, and tag/property mutations acquire `index.lock` before reading content or discovering a batch, request priority, and wait with the caller context. A batch retains one lease through every write; nested rename work uses the already-held path. Previews remain read-only. Obsidian URI actions belong to the external editor and do not claim this lease.
- **Heading rename publishes one witnessed batch.** Apply recovers interrupted edits before taking its writer lease and capturing content. The heading and all inbound rewrites compose into one final document per file and commit through the existing edit session under the held lease. Each transform requires its immutable original bytes; unreadable potential backlinks stop apply before publication. Counts describe the plan, conflict outcomes fail the action, unchanged content reports `Applied=false`, and committed cleanup warnings retain `Applied=true` through the existing result message. The human command distinguishes unchanged content from publication and prints the result message.
- **Heading rename retains fragment-only link context.** An empty wikilink note target means the currently scanned source note. Refuse requested file symlink aliases in preview and apply before resolving the note to its canonical inventory path for content capture, link matching, and staging. In-vault parent-directory aliases remain supported. A different case spelling must name the same physical file; distinct case-sensitive notes keep their own identity. Match the local target to the renamed note before applying heading-text or block-ID rewrites, preserve its empty target and alias, and retain code protection. Identical fragment-only links in other notes remain local to those notes; preview and apply use the same matches and counts.
- **Legacy mutations honor provider capabilities before writes.** Note rename/move and heading rename receive the caller-composed metadata indexer. Registered formats without an executable projector and the requested mutation capability fail before filesystem changes; batch moves check every member first. A rename cannot convert between note formats or between notes and attachments. Unregistered attachment-to-attachment moves retain their existing workflow.
- **Note moves admit the complete endpoint set before writes.** Every source must exist and every occupied target must be a regular file; stat, parent, format, containment, and non-overwrite collision errors reject the entire batch before creating directories or moving files. Canonical parent paths and physical file identity reject duplicate sources, duplicate targets, target ancestor/descendant conflicts, source-target overlap, cycles, and self aliases. Ancestry uses path components and platform case comparison, so similar filename prefixes remain valid. In-vault parent symlinks are resolved, leaf symlinks are refused, and a case-only basename rename is allowed only when it names one existing directory entry. Its actual source entry spelling is retained for filesystem/Git operations even when the request uses another case spelling. Target parents are canonicalized while the requested leaf spelling is preserved, including when Windows resolves that existing leaf to its old case. Authored and canonical old paths remain alternatives of one logical rewrite, preserving basename ownership and update counts. Authorized overwrite uses `git mv -f` or `fileio.Replace`, preserving the destination on failed filesystem replacement; it never pre-deletes a target. Filesystem fallback leaves the Git index unchanged. The admitted renames and required backlink writes publish through one native validation transaction.
- **Native note moves use a read-only final-namespace plan.** One captured source set supplies original hash/mode witnesses and all required backlink rewrites. Compose shared hosts once, exclude overwritten destination bodies, and evaluate ignore eligibility at final paths, including moved sources previously pruned from discovery. Preserve request-order counts and skipped non-Markdown reporting. Walk entries retain their own leaf names for eligibility and reporting; eligible leaf symlinks fail preflight, while non-Markdown or excluded aliases remain outside required rewrites. The validation engine owns admission, recovery, Git staging, publication, and projection refresh under its lease. Commands and code mode explicitly compose `ValidationProjectionPostApplyRefresher`; a missing collaborator fails before publication. Populate legacy success fields only for this invocation's `Current=committed`, preserving complete display diagnostics in the private planner and only fixed move/link counts in the bounded recovery summary. Preserve current and recovered outcomes separately, and render known decisions before follow-up errors. Optional current code-reference writes borrow the engine lease after required convergence and cleanup, preserving namespace order with best-effort counts and no recovery replay. URI execution remains after the engine returns successfully with recovery clear.
- **Note metadata composition stays at the boundary.** One-shot command composition creates the built-in note-metadata indexer in `cmd/note_metadata.go` and passes it into indexing, ontology, validation, web, and MCP paths; business packages never select a provider.
- **Serve readiness follows the read surface.** `pkg/app/cli/serve` coordinates live capability publication below the Cobra adapter. After live runtime creation, a durable provider-current note projection admitted by the live ownership selector opens the narrow note-read gate while the complete ontology/graph gate stays closed. Each exact GraphQL operation still verifies every requested path before using that gate, and configuration reloads replace the read-side selector. Followers begin polling both shared publication transitions before waiting for their local search or code phases, and config hints refresh their selector and WatchHub exclusions. A cold leader opens both gates only after a successful index. Gate waits remain bounded and cancellable.
- **Serve write recovery is an application startup barrier.** `pkg/app/cli/serve.RecoverInterruptedWrites` stabilizes ontology and repair journals before Cobra constructs the live runtime. Keep the ordering and error context below the command adapter.
- **cmd/ stays thin**: flag parsing, option-struct assembly, output writing, and product dependency composition only. Business logic goes in neutral orchestration (`pkg/app/validationrun`, `pkg/app/validationproduct`) or subsystem packages (`pkg/app/cli`, `pkg/app/indexing`, `pkg/vault/obsidian`). Validation's production runner resolves one canonical vault/root/config and composes those packages; it does not implement checks or projection mutation itself.
- **Validation has one shared product contract.** `rzm validate [selector]`, `rzm agent validate [selector]`, and `rzm ci [selector]` compose through `pkg/app/cli` and accept at most one positional selector. `validate list` is registry-only; `validate fix [selector]` plans unless `--apply` is explicit. Never reintroduce repeatable `--check` or a broad parent `--fix` flag.
- **Renderer streams stay exclusive.** Agent and CI JSON output remains machine-valid; GitHub workflow commands appear only in the GitHub CI renderer. Validation findings return 1; configuration/execution/blocked prerequisites return 2 through `silentExitError`.
- **Identifier allocation uses one current runtime pair.** CLI/code-mode next-ID allocation and optional authoring-guide suggestions pass the refreshed ontology runtime's schema and store together, so sibling types added during startup contribute to the same pool as current persisted rows. Early next-ID schema admission retains existing missing/invalid-schema errors; a successful optional guide refresh uses its current schema for both rendering and suggestions, including identifier prefixes and authored field keys. The initial schema only gates lookup eligibility and supplies rendering fallback when refresh is unavailable, without failing the guide.
- **Identifier reconciliation is one additive envelope.** Human and GitHub renderers summarize collision count, plan fingerprint, history completeness, fallback count, and the six stable timing labels; JSON preserves the typed `identifierReconciliation` object unchanged. Planning-only zero values for apply/post-validation are truthful, not omitted or inferred work.
- **`rzm agent *` commands emit JSON** via the shared validation renderer and signal validation failure with exact exit 0/1/2. Human `validate fix --apply` carries a reusable `Confirm` callback through `validationProductRequest`; plan-only runs carry none. Agent apply always sets `NonInteractive` and a nil callback, so JSON surfaces never prompt. `validate fix --action <id-or-issue-key>` (repeatable) and `--from-plan <file>` require `--apply` and thread an exact reviewed selection to `validate.Options.ApplySelection`; the file parser (`ParseValidationApplySelection`) lives in `pkg/app/cli`. Human, agent, and CI commands share the same production runner.
- **Path handling**: resolve user inputs via `pkg/paths` — `AbsFromInputWithVaultPaths` for filesystem I/O, `ResolveNoteInputWithVaultPaths`/`ResolveCodeInputWithVaultPaths` for (rel, abs) pairs. No ad hoc `filepath.Abs/Rel`; indexes store vault-root-relative paths only (`VaultPaths.RelStrict` family). Legacy `obsidian.NormalizePath`/`AddMdSuffix` are compat-only.
- **Index diagnostics mirror system-note precedence.** `rzm index --explain` evaluates exact `CONTEXT.md` with the hard visibility matcher and reports its ordinary include/exclude bypass; all other paths retain the unified configured matcher.
- **Repo delegation does not own the pinned binary's config schema.** Global dispatch may warn about keys its full loader does not recognize, but it must select the repo binary from the `rhizome` block before that binary performs strict canonical config validation.
- **Pinned executable resolution has one owner.** `pkg/app/update.ResolveInvocation` resolves the current executable, the pin-gated repo target, and whether the process already has repo identity for both delegation and update. It first uses `LocalRhizomeConfig.UsesExternalBinaryManager`: external ownership trusts the current executable and produces no Rhizome repo target, while unknown or mixed ownership fails. Otherwise, a non-empty `rhizome.version` creates repo target ownership; `binaryPath`/`binaryDir` only choose its logical destination. File identity may classify the invocation, but mutation planning deduplicates logical pathnames rather than inode or symlink identity.
- **Unix delegation preserves process ownership.** Replace the launcher process with the pinned executable so supervisor signals reach the actual command once and its PID, terminal, and standard streams remain owned by that command. Windows retains its console-backed child and waits for its exit.
- **Pinned dispatch defaults to delegation.** At process entry, every user-facing invocation inside a pinned repo delegates to the selected repo binary, including ordinary init, embedded templates, version, help, completion, bare invocation, and future commands. The `update` command family and explicit `init --binary-manager external` migration stay on the current executable; `update --help` remains global while `help update` delegates. The pre-Cobra detector must explicitly cover every value-taking persistent flag so option values cannot be mistaken for a command. Existing debug/recursion guards, already-selected identity, self-healing bootstrap, and source-development rules remain the only other bypasses.
- **External-manager dispatch never delegates.** When the validated repository config declares external ownership, pre-Cobra dispatch runs the executable already selected by the external tool for every command. It must not inspect source builds, probe or repair `.rhizome/bin`, or enter pin/bootstrap/update classification.
- **Update target ownership is explicit and ordered.** `pkg/app/update.BuildUpdatePlan` owns the mode matrix. Global-entry plain update refreshes global and changes repo only after confirmation; global-entry `--latest` changes global then repo. `--pinned` and `--set-version` are always repo-only, and direct repo-scoped updates never infer a global path from `PATH`. Prepare every unique artifact before mutation, then replace global before repo and commit repo binary, marker, and pin in that order. Partial results must report completed targets even when a later stage fails.
- **External managers own updates.** Update grammar is validated first; then an externally managed repository refuses every valid `rzm update` mode before manifest fetch or executable mutation and directs the user to change the version through the external manager.
- **CLI <-> MCP parity**: `pkg/app/mcp/` mirrors CLI capabilities. New agent-relevant options must land in the shared handler and authoritative `ToolDescriptor` to be visible to agents; `pkg/app/mcp/CONTEXT.md` and `README.md` are the primary references. MCP surface is intentionally pared down — sensible defaults over knobs. One-shot runtime policy is declared by typed executable operation in `pkg/app/oneshotruntime`; command names must not accumulate as capability/wait switches in `cmd/`.
- **One-shot indexed exceptions are explicit.** `agent file-context`, `code-symbol`, `code-references`, `code-rationale`, and `graph-path` select only the existing query-only CodeIndex. The latter four use their typed `OperationID` plan and must not make a handler fallback store open. `agent semantic-query` retains its provider-only plus indexed read contract. `semantic-query --timings` is an additive CLI projection of the shared handler's `timings=true` diagnostics; it must not change retrieval or result JSON when omitted.
- **Context packing publishes final delivery.** File/vault builders retain pending session reservations until target clipping, header and warning assembly, and enclosing vault output are complete. Only complete deterministic containers authorize their source and nested fingerprints. Warning assembly preserves fingerprints within its exact retained original prefix; clipped containers and compressed summaries leave raw content eligible for retry. The compressor receives the request context; cancellation releases pending ownership.
- **One-shot live-note plans follow normalized input.** Agent files, tags, properties, community, health, report, vault-context, connection, and mutation-planning commands select readiness after their arguments are normalized. A supplied or generated session may use the narrow existing-only dedupe writer. Requests without a session must not open it. Runtime-free plans must keep a nil live runtime typed as nil so command cleanup cannot panic after writing output.
- **Human twins use the same vocabulary.** Root search declares direct provider/store ownership through `UnifiedSearchPlan` while keeping text rendering outside agent JSON. Root and agent query/recipe execution select `OntologyQueryPlan` only after preparation. Views share `ViewPlan`; root graph-context commands use `GraphContextPlan`, and root file context retains separate write authority for link-target apply. For `--ensure-link-targets=plan|apply`, root file context scans only explicitly requested configured code files through `pkg/app/cli`, honoring includes, excludes, and note aliases; `default` and `never` keep their prior behavior. `agent code-symbol-context` is a typed full-runtime parity exemption, not a command-name fallback.
- **Init templates are embedded sources**: edit `docs/rhizome-md-templates/*` for RHIZOME.md content and `pkg/app/cli/init/templates/**` for skills and starters. Refresh generated `.agents/skills` and `.claude/skills` copies with `rzm init`; never edit them directly. Cursor uses `.cursor/rules` and `.cursor/commands`, not a generated `.cursor/skills` tree.
- **Init asks only in a terminal.** `RunOptions.Interactive` (stdin is a terminal) decides whether init asks questions; every other run uses the recommendations and keeps edited files. A rerun prints the setup and a change list and asks once (`Apply? [Y/n/s]`); opt-in suggestions apply only after that confirmation. `rzm init --check` prints the same report, writes nothing, and maps `ErrChangesPending` to exit status 1; it is init's report mode, unrelated to validation selectors. `--workflow`, `--agents`, and `--search` express first-run choices; removed flags (`--yes`, `--template`, the per-surface agent modes, `--no-config`, rejection flags) fail through `initFlagError` with their replacement.
- **One ownership rule for generated files.** Every file init generates goes through one planner and applier (`pkg/app/cli/init/file_plan.go`): missing files are created without asking, files whose content matches the fingerprint in the tracked `.rhizome/generated-files.yml` are updated without asking, and only files someone edited need a decision. Interactive runs ask (take the update, keep my version, show the diff), one question per file across mirrored skill folders; every other run keeps edited files and lists them, and only a person's choice records a declined version. Files with no record that differ are grouped into one question; managed blocks are the exception because their fences mark them as Rhizome's. Skill folders carry no marker files: the record proves ownership, and files a newer version dropped or skills of inactive starters are removed only when they still match their record. Starter docs are created only, and offered as updates only with a requested refresh. Ontology refresh uses gqlparser-backed source positions to preserve each adopted identifier's complete allocation contract (`strategy`, `prefix`, `separator`, and sequential `pad`), and ontology fingerprints ignore those contracts, because init has no authority to rekey an existing identifier pool; unsafe preservation fails closed.
- **Managed `.rhizome/.gitignore`**: any new committed (non-transient) file under `.rhizome/` requires updating the `rzm init` template/writer so it stays tracked after init refreshes.
- **Dispatch is version-neutral.** Repository binary selection reads only the `rhizome` pin before delegation; unrelated unknown or older config shapes can warn but must not prevent the selected binary from running. `rzm init` migrates the three v0.49 workflow fields to tracked `.rhizome/workflows.yml`, removes only those fields from `config.yml`, and is idempotent.
- **Init owns binary-manager migration.** `--binary-manager external` is the sole authored transition in this slice. It skips pin creation/bootstrap, preserves existing external ownership on rerun, and clears conflicting pin/path fields once the rerun's confirmation covers the listed change (the flag itself is the confirmation without a terminal) without deleting `.rhizome/bin` cache files.

## Must-dos when changing this subsystem

- New/changed flag or command: update `README.md`; if agent-relevant, mirror it in the shared handler and catalog descriptor, declare CLI display order/category, add the CLI front when applicable, and update `pkg/app/mcp/CONTEXT.md`. Bias to minimal MCP options.
- Validation command changes must keep human/agent/CI selection and exit semantics identical. CI is Rhizome content validation only—not a build/test aggregator—and must never expose mutation/apply flags. A pending repair journal blocks before projection refresh and renders the exact recovery command; do not replace it with a generic retry.
- Validation has one caller-owned apply-command seam: Cobra shell-quotes the requested positional selector and mutation-relevant `--vault`, link-filter, scope, and `--allow-historical` flags, then carries it through `validationProductRequest`; `--max-issues` is presentation-only and is intentionally excluded. Never reconstruct product authority from expanded `effectiveChecks`; per-check commands are a legacy/internal fallback only. `RepairPlan.followUps` and `FixExecution.followUps` remain JSON evidence; human output groups them as review items and GitHub emits warnings. Coalescing identical plan/apply evidence must not change issue, error, action, or exit counts.
- New orchestration logic: put it in `pkg/app/cli/` with a `_test.go` beside it (table-driven, testify); `cmd/` file only parses flags and delegates.
- Init template changes: edit the directly embedded `docs/rhizome-md-templates/*` sources for RHIZOME.md guidance and `pkg/app/cli/init/templates/skills/...` for core skills. Starters group assets by install destination under `templates/starters/<id>/`: `repo/` (target repo root), `rhizome/` (`.rhizome/`), and `agents/` (skills, managed `AGENTS.md` block, skill overlays). Respect starter metadata (`templates/starters/<id>/template.yaml`) — keep resolution metadata-driven, no name-branching.
- New `.rhizome/`-resident committed file: update the managed `.gitignore` writer in init.
- Preserve user prose outside managed fences in `AGENTS.md`/`CLAUDE.md`. When `CLAUDE.md` includes `AGENTS.md` through an `@AGENTS.md` line and `AGENTS.md` is enabled, its managed block is a one-paragraph pointer and it carries no starter blocks, because Claude Code inlines the include and a second copy doubles hot context; reject template/skill collisions before writes (existing preflight pattern in `pkg/app/cli/init/run.go`).
- Config field additions: update `LocalConfig` (defaults/normalizers in `pkg/vault/obsidian`) plus `pkg/app/cli/init` detection/migration so `rzm init` stays consistent.
- Verify locally: `go run . --help`, `go run . <command> --vault <test-vault>`; full gate `make check` before commit.

## Review checklist — problems to catch

- Business logic living in `cmd/` (loops over vault files, link parsing, index access) instead of `pkg/app/cli/` or `pkg/vault/*`.
- Ad hoc `filepath.Abs`/`filepath.Rel` or `obsidian.NormalizePath` in new code instead of `pkg/paths` helpers; absolute or escaped paths reaching SQLite.
- New user-facing flag/behavior with no `README.md` update, or agent-relevant capability missing from its handler, descriptor membership/display metadata, or applicable CLI front.
- New committed `.rhizome/` file without the managed `.gitignore` template/writer update (file silently re-ignored on next `rzm init`).
- Direct edits to generated `.agents/skills` / `.claude/skills` copies instead of `pkg/app/cli/init/templates/...` sources; RHIZOME.md edits made outside the directly embedded `docs/rhizome-md-templates/` sources.
- Commands that may open `$EDITOR` on multiline `--content` (known hang in non-interactive runs — `note create`); new commands should detect non-TTY and fail or read stdin instead.
- Missing `_test.go` beside new orchestration code; tests depending on personal vault data instead of fixtures/temp dirs.
- A new persistent value-taking root flag omitted from `firstCommandArg` coverage, which can route global `update` through the pinned child by mistaking the flag value for a command.
- Interactive prompts in `rzm agent *` JSON commands (must be non-interactive; failures via `silentExitError`).
- Validation grammar drift: multiple selectors, `--check`, mixed suite/check selection, JSON plus annotations on one stream, or `rzm ci` invoking build/index/embedding work.
