# Init - Agent surfaces (prompts, commands, skills)

## Summary

`rzm init` writes agent-facing artifacts for detected environments and expands shared templates into harness-specific commands, prompts, rules, and skill directories. These are Rhizome-owned artifacts: generated file names use the `rhizome-` prefix where possible, and managed prose lives inside explicit fences.

### Starters

`rzm init` ships five starters, each a directory under `pkg/app/cli/init/templates/starters/<id>/` with a `template.yaml` describing it:

| id | `requires` | `activatesByDefault` | `installedAssetTypes` |
| --- | --- | --- | --- |
| `core` | — | — | `docs`, `ontology`, `query-recipes`, `managed-docs` |
| `agentic-engineering` | `core` | `action-items` | `docs`, `ontology`, `query-recipes`, `views`, `skills`, `managed-docs` |
| `complex-domain` | `agentic-engineering` | — | `docs`, `ontology`, `query-recipes`, `views`, `skills`, `managed-docs`, `skill-overlays` |
| `action-items` | `core` | — | `ontology`, `query-recipes`, `views`, `skills`, `managed-docs` |

`template.yaml` is the source of truth (`id`, `name`, `requires`, `activatesByDefault`, `installedAssetTypes`). `resolveTemplateSet` expands a user's explicit choices through `requires` (mandatory dependencies, e.g. `complex-domain` pulls `agentic-engineering` then `core`) and `activatesByDefault` (default addons that can be skipped via `.rhizome/workflows.yml` `addons.disabled`). The resolver is metadata-driven; it does not branch on starter names. `spec-driven` is normalized only as legacy migration input. `installedAssetTypes` is documentary metadata describing which asset families a starter ships — the actual install is driven by which family directories exist under the starter.

### Ownership modes

- **Managed agent-doc blocks**: `AGENTS.md` and `CLAUDE.md` preserve user prose outside Rhizome fences, then replace the core Rhizome block and one block per active workflow template.
- **Rhizome-prefixed helper artifacts**: command/prompt files are whole-file generated artifacts; stale files are cleaned up only when their names look Rhizome-owned.
- **Skill directories**: `.agents/skills` and `.claude/skills` mirror the same core and starter skill templates. Every file, markdown or not, goes through the one ownership rule in `file_plan.go`; scripts under `scripts/` are written executable.
- **Starter scaffold docs**: starter docs become user-owned after first creation; reruns do not rewrite existing `docs/` files unless `--refresh-docs` is passed.
- **Starter `.rhizome/` assets**: ontology schemas, query recipes, and views install under `.rhizome/{ontology,query-recipes,views}/` and share the same preflight collision checks. Each schema is named after its starter (`<id>.graphql`) so multiple active starters merge rather than overwrite.

## What matters operationally

- RHIZOME guidance is written first, then agent-specific artifacts.
- Existing agent docs are updated in place rather than blindly replaced.
- User content outside managed fences in `AGENTS.md` / `CLAUDE.md` is preserved.
- Core skills install independent of workflow starter choice.
- Starter-only skills install only when the starter is active.
- Skill templates are copied as directories, with markdown expanded and scripts preserved as executable when needed.
- Shared `.agents` skills are the recommended default for new repos.
- Cursor/Codex/Claude command and prompt artifacts are cleaned up only when they carry the Rhizome-managed prefix and are no longer in the current template set.
- Broken symlinked agent directories are skippable per file: a target under an unresolvable symlink returns `SkippablePathError`, and the applier warns and skips just that file instead of failing the whole run. `AGENTS.md` and `CLAUDE.md` writes are the exception; a broken parent directory for those still fails the run.

## Source of truth

- Command templates: `pkg/app/cli/init/templates/commands/*`. This directory does not currently exist in the embedded tree, so `loadCommandTemplates` returns zero templates and every harness's command/prompt directories receive no files today; the artifact matrix below describes what happens once templates are added back.
- Prompt target directories currently receive the same `templates/commands/*` family; the current runtime does not load a separate `templates/prompts/*` source family.
- Core skill templates: `pkg/app/cli/init/templates/skills/markdown/*`.
- Starter assets (per active starter `<id>`): `pkg/app/cli/init/templates/starters/<id>/` groups assets by install destination: `repo/docs/**`; `rhizome/ontology/*.graphql`, `rhizome/query-recipes/*`, `rhizome/views/*`; and `agents/skills/`, `agents/AGENTS.md`, and (for `complex-domain`) `agents/skill-overlays/*`. Each family is loaded by a dedicated `loadStarter*` helper in `helper_templates.go` / `template.go`; a missing family directory simply yields no files.
- Embedded Rhizome guidance chunks: `docs/rhizome-md-templates/*`.
- Starter ontology schemas preserve their source filename (e.g. `spec-driven.graphql`, `complex-domain.graphql`, `core.graphql`) so multiple active starters merge instead of clobbering a single `schema.graphql`. The Agentic Engineering starter intentionally retains the domain-accurate `spec-driven.graphql` filename. The merged loader picks up every `.graphql` under `.rhizome/ontology/`.

## Shared mechanics

### One ownership rule

Every generated file goes through `syncGeneratedFiles` (`file_plan.go`). Missing files are created without asking. A file that still matches the fingerprint recorded in `.rhizome/generated-files.yml` is updated without asking. A file someone edited is the only one that needs a decision: a terminal run asks once per file (mirrored skill copies share the question) with take the update, keep my version, or show the diff; any other run keeps it and lists it. Keeping records the declined version so the question returns only when a newer version ships. Scripts in a skill's `scripts/` folder are written executable.

### Cleanup boundaries

Cleanup never sweeps arbitrary harness directories. `cleanupStaleArtifacts` touches only non-directory files whose names start with `rhizome-` or legacy `rhizome.`. Stale skills (retired skills and skills of inactive starters) and files a newer skill version dropped are removed only when they still match the record; without a record they go through the grouped question, and anything else in the folder stays. Starter scaffold docs and root agent docs do not have stale-file cleanup beyond managed-fence replacement and removal of the old generated root `RHIZOME.md`.

### Broken symlink behavior

`ensureDirExists` treats valid directory symlinks as directories. Broken symlinks and symlinks to non-directories become `SkippablePathError`; the applier warns and skips that file. Root files such as `AGENTS.md` / `CLAUDE.md` and config writes fail instead.

## Collision semantics

- Unknown workflow templates are rejected by `normalizeTemplateNames`.
- Core skill and starter skill name collisions are rejected by `loadAllSkillTemplates`.
- Starter scaffold target-path collisions are rejected by `planTemplateScaffold` unless the bytes are identical.
- Empty markdown skill files and missing `SKILL.md` files are rejected while loading the embedded templates.
