# Search engine evaluation, September 12, 2026

Rhizome has a capable retrieval core, but the complete engine does not yet deliver consistently relevant or trustworthy results. The highest-priority problems are loss of ranking information, weak enforcement of precision modes, and confidence that measures packet completeness without establishing relevance. These need correction before tuning for web versus agent use.

This assessment examines checkout `0049fa9d`, the core `pkg/search` pipeline, semantic retrieval, both search orchestration paths, and answer assembly. The checkout was built and indexed. The live measurements below were taken after index completion with Voyage `voyage-4-lite`; selected semantic lanes returned evidence. Earlier measurements made during index construction are excluded. No search behavior changes remain in the checkout.

The core design has several strengths worth retaining. A planner selects retrievers and ranking policy; a service executes retrieval and merges candidates by canonical identity. Lexical, vector, symbol, graph, code-reference, and ontology evidence can contribute to the same source. Owner caps and semantic interleaving protect coverage against large documents. Exact vector search filters eligible chunks before nearest-neighbor selection, with deterministic tie handling and scalar parity tests. Source and NodeRef provenance survive retrieval, stale ontology chunks are rejected, and bounded expansion requires credible seeds. Deadline handling, lane diagnostics, and compact source-owned bodies are useful foundations for agents.

The weakness is that these mechanisms do not form one consistent ranking contract. The CLI and shared agent/web implementation construct different pipelines. The latter adds fusion, re-scores groups, clips scores, re-sorts, applies positional score decay, promotes selected source classes, and then chooses answer roles. A correct retrieval decision can be lost several times before the response reaches a caller.

| Priority | Finding | Evidence and consequence |
| --- | --- | --- |
| First | Post-ranking scoring destroys relevance order | A controlled probe supplied scores 3.0, 1.1, and 1.01. Group rollup clipped them to 1.0, sorted by path, and positional calibration produced 1.000, 0.975, 0.950 with the strongest candidate last. The apparent score separation was introduced after the relevance distinction had been discarded. |
| First | Precision modes do not reliably deliver their target | `go_to_def` for the unique `interleaveScoredChunksByOwner` symbol resolved the target and ran the definition lane, but the agent response's first five results contained two documentation notes and three other code symbols. It reported high confidence. Raw CLI search ranked the correct definition first; `codeSymbol` resolved it directly. |
| First | Confidence does not establish relevance | `zxqvnonexistent987` returned 240 candidates, 20 first-page results, no warnings, and high confidence. Selected evidence concerned PHP, broken links, and identifier tests. The confidence function grants high confidence when role coverage is complete and warnings are absent. That is packet completeness, not evidence that the query was answered. |
| First | Ordinary agent pagination changes its search window | With the evaluation server stopped, five pages of `Search (Hub)` reported totals 166, 166, 167, 242, and 270. Nine source refs on the last two pages had appeared earlier. The agent handler enables fixed candidate-window and digest behavior only when a folder or note-type argument is supplied. Otherwise internal K grows with offset. |
| Next | Repeated evidence increases score without new information | A controlled core probe merged the same candidate and the same 0.6 lexical evidence with itself. The lexical channel rose from 0.600 to 0.930. Merging bounds evidence count but does not deduplicate identical facts; channel aggregation sums them with decay. |
| Next | Fusion loses the configured timeout fallback policy | A controlled probe wrapped a ranker configured with lexical weight 0.123 and owner cap 3 in `FusionRanker`. Approximate fallback used lexical weight 0.800 and owner cap 1. The decorator does not implement the forwarding interface, so timeout/pruning policy can differ from normal ranking. |

Additional design concerns follow directly from source inspection, but their individual production impact has not been isolated through ablation. `AutoExpandRetriever` returns base candidates collected from a Go map. The service assigns retriever ranks from that output order, and fusion treats those positions as relevance ranks. This does not represent agreement among the original independently ranked retrieval lanes. The exact-title boost in `NoteLexicalRetriever` also saturates: when every query token already matches, the token score is 1 and adding the exact-match boost is clipped back to 1. Finally, specificity is added both before auto-expansion and by the specificity ranker; repeated evidence can compound the merge/aggregation weakness above.

Ten sequential live agent searches took 142–1,095 ms, with a median of 399 ms. These are local samples on this repository, not a load test or a production latency estimate. One measured title query spent 191 ms embedding, 310 ms in the vector retriever including embedding, 104 ms in graph diffusion, and 7 ms ranking. Retrieval and expansion dominated that request; ranking computation was cheap. These samples do not justify changing storage technology or adding an expensive reranker as the first response.

My recommendation is to retain the retrieval/indexing foundation and simplify the policy around it. Give one stage ownership of relevance order. Preserve unbounded ranking scores internally, distinguish them from any display score, and preserve exact target precedence through grouping. Deduplicate repeated evidence before scoring and make every ranker decorator preserve fallback policy. Apply filters before bounded retrieval and bind pagination to one candidate window for every caller. Require query-relevant support before assigning high confidence, while allowing explicitly weak semantic suggestions when useful.

Once those defects are corrected, introduce a small number of explicit caller profiles within that shared engine. Interactive discovery should emphasize exact title/path/symbol matches, compact source snippets, and useful first-page order. Agent discovery should retain broader source coverage and compact evidence packets; exact code and test tasks should use strict target-specific selection. Profiles should set retrieval budget, source diversity, expansion policy, and output shape. They should not maintain separate scoring implementations. Profile weights should be chosen from judged query results rather than intuition.

The existing tests are valuable but insufficient to claim excellence. Focused `pkg/search/...`, `pkg/app/unifiedsearch/...`, and web-package tests passed. Existing MCP and answer tests passed. `TestSearchIntents_P3` passed against the deterministic Python fixture. Three temporary probes failed with the exact mechanisms documented above; their output is retained here, and the temporary files were removed. The canonical quality document has nine query cases, but the designated archetype regression file has only two synthetic ranker cases. Neither component coverage nor deterministic embedding fixtures establishes semantic relevance across real corpora.

A useful quality gate should judge exact-target success at rank 1, graded relevance in the first 10 results, recall of required sources, precision-mode purity, confidence on irrelevant queries, and pagination consistency. Run it separately for raw ranked results and final responses with matched requests and index state. Include unfamiliar repositories and prose-heavy vaults, absent answers, ambiguous symbols, stale or missing lanes, and constrained searches. The current assessment is a repository-specific diagnostic sample, not a statistically representative relevance benchmark.
