# Credentials and 1Password

Secrets belong in 1Password, private user configuration, or protected GitHub Actions secrets. Never commit live credentials, unlock keys, encrypted credential bundles, private release locations, or copies in test fixtures. Never print values or include them in agent context.

## Developer setup

Ordinary contributors need no provider credentials to build, test, or use local Ollama embeddings. Direct cloud-provider access resolves keys from the environment first, then user-global `~/.config/rhizome/config.yml`. In Settings, an explicit Atomic Object server choice for Voyage or Jev overrides all local keys; Your key excludes server and legacy-bundle fallback. With no choice, existing precedence remains unchanged.

Atomic Object developers use dedicated shared Rhizome provider keys in a 1Password Environment. Install stable `op` 2.41 or newer, sign in to an account with read access, and enable **Settings > Developer > Integrate with 1Password CLI** in the 1Password app. In Rhizome setup or Settings, use **Import provider keys from 1Password**. Select Voyage and TypeSafe, enter the account and shared Environment ID supplied by the team, then approve the 1Password prompt. The CLI supports the same import:

```sh
rzm credentials import --from 1password --account example.1password.com \
  --environment <environment-id> --key VOYAGE_API_KEY --key TYPESAFE_API_KEY
```

The Environment ID is available in **Developer > View Environments > View environment > Manage environment > Copy environment ID**. Missing requested keys fail the import; existing shell values cannot substitute for missing Environment values. The desktop can find `op` in the process PATH, `~/.local/bin`, `/opt/homebrew/bin`, or `/usr/local/bin`.

Existing shared items can still be imported using explicit field references:

```sh
rzm credentials import --from 1password --account example.1password.com \
  --key 'VOYAGE_API_KEY=op://Shared/Rhizome/VOYAGE_API_KEY' \
  --key 'TYPESAFE_API_KEY=op://Shared/Rhizome/TYPESAFE_API_KEY'
```

Replace the non-secret references and account with those supplied by the team. Imports validate the source, read all requested keys before saving, preserve unrelated settings, and write the global config atomically with mode `0600`. This is plaintext user-local storage. Environment source references are remembered on this computer for re-import; they never enter repository configuration. Normal execution needs no `op` process. Repeat import after rotation; environment variables still take precedence.

CLI credential imports stay on the invoked Rhizome version, including inside repositories pinned to an older version. An import times out after 90 seconds. Cancel stops its credential process tree and discards a pending result. Cancellation cannot undo an atomic save that already completed; the desktop refreshes provider status after cancellation or failure. An abrupt app crash can leave an import running until its timeout and may allow it to finish before then. An older Rhizome version may discard the saved source references when it rewrites user configuration; enter them again to re-import.

The shared Environment or item and provider administration belong to the team, outside the repository. Use provider spend limits and separately scoped keys where available. Removing 1Password access does not revoke an already imported provider key; rotate the provider keys when access must end. Do not put tenant IDs, account defaults, live values, or exported secret files in Git.

The team API gateway ([SPEC-0129](../specs/technical/team-api-gateway.md)) replaces distributed keys with a per-person session. `rzm auth login` stores the session in the OS secret store (service `rhizome-team-session`, account = the gateway origin), never in `config.yml`. macOS uses the login keychain through `/usr/bin/security`; Linux uses Secret Service through `/usr/bin/secret-tool` from libsecret, with an unlocked keyring on the real OS user's `/run/user/<uid>/bus`. Linux helper processes use a fixed system executable and a minimal environment so repository settings cannot redirect the D-Bus service or credential backend. Records travel on private pipes, never in process arguments or diagnostic output; neither platform falls back to a plaintext session file. Any process running as the user can read that item while the keychain is unlocked; revoking the session or disabling the person in the gateway ends it, and daily limits bound misuse in the meantime. Provider keys stay on the gateway. The gateway is deployed. Desktop Settings groups account sign-in, independent Voyage/Jev route choices, manual key entry and 1Password import under Provider access. Signing in or importing keys does not silently change routing. The page reports defaults separately from actual running-repository connections; older pinned runtimes may not understand route choices and are shown as unknown. Keys are never returned for display. Add, replace and clear operations use the same private atomic user-global save and native configuration lock as setup/import.

## Development and release tooling

Public release writing and PR preparation use the active local Codex or Claude subscription and existing `gh` login. They require no model API key, Apple credentials or publishing tokens. Public builds, signing and publication use protected GitHub Actions secrets; routine preparation never unlocks 1Password. `scripts/with-secrets` remains optional tooling for development, explicit local signing candidates and private internal release work. Its Environment-based workflow requires 1Password CLI 2.41.0 or newer on PATH (or `RZM_OP_BIN`), an explicit `RZM_OP_ENVIRONMENT_ID`, and `OP_ACCOUNT`. Keep release credentials (GitHub publishing tokens and the desktop updater key) in a separate Environment named by `RZM_OP_RELEASE_ENVIRONMENT_ID`, so development runs, including coding agents, never unlock them; without it, `release` falls back to `RZM_OP_ENVIRONMENT_ID`. To stop approving every development run, run `./scripts/with-secrets sync-keychain` once (and again after rotating a key). After one 1Password approval it copies `VOYAGE_API_KEY` and `TYPESAFE_API_KEY` into the login keychain (service `rhizome-development`), passing them to `security` on standard input so no value appears in arguments or output; an agent can run it without seeing the keys. `with-secrets development` then reads them from the keychain without a prompt and falls back to 1Password when either is missing. Any process running as the user can read those two items while the keychain is unlocked, which is acceptable only for revocable API keys. Local Desktop Developer ID identities may live in the release Mac login Keychain, with password-protected p12 backups in a restricted 1Password vault. Apple notarization keys are materialized only as protected temporary files during the desktop signing build. CI uses encrypted secrets in the protected GitHub `release` Environment and a temporary Keychain; it must clean up temporary keys and the Keychain after the build. Keep its branch policy restricted to trusted main, with any explicitly authorized candidate exception removed after verification. Only the final public Linux publisher receives repository write/dispatch permissions and the Homebrew token; candidate mode skips publication. Shared frontend work, CLI compilation and artifact assembly receive no publishing credentials. The release guide lists exact variable names and recovery steps. Release publishing credentials are never copied to the development Keychain; `with-secrets release` asks 1Password every time. This is separate from ordinary setup-time import and is not required for Rhizome users. The local team API gateway that development builds start (`services/team-api`) reads the same two keychain items itself; the `rzm` under test never receives them.

The wrapper filters inherited credentials. Development commands receive only the required provider keys. Private local release work uses dedicated GitHub and Homebrew tokens; `RZM_RELEASE_GITHUB_TOKEN` becomes `GITHUB_TOKEN` only in its publishing subprocess. Public CI uses the workflow token for repository publication and a separately scoped `BREW_GITHUB_TOKEN` only for Homebrew operations. Build subprocesses must not receive provider, 1Password, or AWS credentials. AWS access is used only by the internal mirror publish step.

Public builds and releases never bundle provider keys or private mirror configuration. The temporary internal bridge may remain in public source (approved 2026-09-29), with internal releases continuing from the private archive until a replacement is ready. They bundle rotated Voyage and TypeSafe keys, AES-GCM encrypted under the existing `ATOMIC_RHIZOME_KEY`, so current Atomic Object users keep working without setup. The tracked `pkg/teamkeys/keys_encrypted.go` stays empty; `scripts/teamkeys/release.py` supplies the bundle through a temporary compiler overlay only when `RZM_INTERNAL_S3_BUCKET` is set and only for a verified private GitHub repository. Public builds reject inherited overlays, disable persisted Go settings, remove stale mirror configuration, and scan each built binary and staged installer before upload. Everyone who has held the unlock key can decrypt the internal bundle, including former holders; keep provider spend caps on these keys. See [internal releases](../RELEASING.md#internal-releases).

## Tests and GitHub

Ordinary tests use synthetic fixtures and no live keys. The optional TypeSafe smoke test requires both `-tags live` and `TYPESAFE_LIVE_TEST=1`, so an ambient key cannot enable it. Its manual workflow uses the protected `live-tests` environment on trusted branches. Ordinary pull-request check workflows must never receive live secrets. The public Release workflow may access protected signing secrets only after validating a merged same-repository release PR, or for an explicitly authorized manual candidate on a permitted trusted ref. Its read-only selection runs before signing, and candidate mode cannot deploy or publish.

## Commit protection and incident response

Run `mise install` to install gitleaks and `make hooks-setup` to enable commit checks. The pre-commit hook and `make credential-check` scan the Git index; stage intended changes before checking. They also block staged files that contain any value of 8 or more characters from a local `.env` (in the worktree or main checkout) or from a credential-named environment variable, naming the file and variable but never the value. CI also scans new commits after the documented historical incident boundary. Reports must redact values. Do not bypass checks or whitelist real credentials.

History through `961e3b41feb9e082985357acb710f7c6ab243b54` is retained by instruction. That boundary does not certify history as safe to publish. Revoke superseded or exposed historically bundled provider keys (Voyage, TypeSafe, OpenAI, Cerebras). The current internal keys and unlock key are intentionally retained until the bridge is replaced; rotate the provider keys and retire the unlock key then. Removing a bundle or rewriting Git history cannot revoke a credential. Update the shared item, repeat setup import, and restart processes with the new values.

The historical repository is retained as a private archive. This clean repository's source is public. Never merge archive history into this repository. Source publication does not authorize a release or prove that public installation works. The [open-source preparation specification](../specs/technical/open-source-preparation.md) records the source and artifact requirements.
