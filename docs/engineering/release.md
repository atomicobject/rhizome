# Release

Consulted when branching, opening or merging a pull request, versioning, writing the changelog, and recording deploy evidence. Used during planning, quality gates, and closure.

## Defaults

Work lands on a branch and reaches the default branch through a reviewed pull request. A user-visible or contract change gets a changelog entry in the same change set. Closure evidence names the commit or release that carries the work.

## Team extensions

Branch model: feature branches merge to `main` through reviewed pull requests (use `gh` outside the sandbox). Prepare public releases with the repository-local `rhizome-release` skill in Codex or Claude. It collects evidence, reviews the narrative and version, and commits the five release files on `release-prep/<version>`. The committed `docs/releases/<version>.md` is the canonical narrative. Merging that release PR authorizes CI to build and publish its accepted merge SHA; opening it does not authorize publication. Ordinary main merges and tag pushes do not release. Public local apply/publish/resume commands are disabled; `make cut-release` points to the skill. Private internal releases retain the local guided publisher and release-branch hotfix flow. See [docs/RELEASING.md](../RELEASING.md). Every user-visible or contract change adds a line under `## [Unreleased]` in `CHANGELOG.md` in the same change set. Effort closure names the PR or merge commit that carries the work. Release evidence uses completed efforts at the same Git revision; `scripts/release/CONTEXT.md` describes collection and publication boundaries.

Effort closure ships with the work, not after the merge. Before opening a pull request for effort-driven work, check the effort against the branch. If everything in scope is delivered or covered by a recorded deviation, commit the closure pass on the branch, add the pull request number to the effort once it exists, and update the record before merging if review or CI changes what was delivered. If work remains, tell the user what is left before opening or merging, and leave the effort active. An effort planned across several pull requests closes in its last one; when the user signals they are wrapping up, for example by asking to merge or ship, say whether the effort still has open work. An effort whose last pull request merged without closure closes in the next related pull request, not in a closure-only one.

The public CI publisher and supported private client publication commands must deploy and verify the pinned public release gateway source before GitHub or S3 uploads. Public release source equals the exact canonical client release commit; private release source is automatically pinned to public release with committed Docker-input agreement. Preserve trusted-main AWS authorization, exact deployment correlation, resumable receipts and post-wait topology checks. Ordinary main pushes do not deploy the gateway. Local preparation, read-only planning/preflight/dry-run and candidate-only CI must not deploy, and client publication is not authorized merely as a verification step. See [the maintainer guide](../RELEASING.md#gateway-deployment-before-publication).
