# Specs

## Summary

Specs define intended world-state. Read these before opening or updating an effort.

## Reading order

1. `process/`
2. then the domain spec family that governs the work: `product/`, `technical/`, `experience/`, or `operations/`

## Note families

- `ProcessSpec` for how the team works
- `ProductSpec` for user-visible behavior and product intent
- `TechnicalSpec` for implementation-facing contracts; these may be requirements-only or may include user stories when the subsystem work benefits from story-based scoping
- `ExperienceSpec` for UX/content behavior
- `OperationsSpec` for deployment/support/readiness contracts
