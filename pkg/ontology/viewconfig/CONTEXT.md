## Native configured view config

`pkg/ontology/viewconfig` owns the repo-authored configured view envelope under `.rhizome/views/*.yaml`. It should stay format-focused: load files, normalize known fields, assign source locations, and emit stable validation issue codes. Runtime execution belongs in `pkg/app/views`.

- **Native envelope**: `apiVersion: rhizome.view.v1` is Rhizome-native, separate from saved query recipes and Obsidian `.base` files. The envelope keeps `source`, `mount`, `defaults`, and `variants` distinct so type-mounted views, standalone views, and future card/kanban variants share one identity model.
- **One file, one view**: this slice intentionally supports one YAML document per file. Reject multi-document YAML with a stable issue instead of partially loading it.
- **Typed variants, one card spec**: `variants.table`, `variants.card`, and `variants.kanban` are typed. Card and kanban share `CardSpec` (`eyebrow`, `title`, `preview`, `fields`); `kanban.card` overrides `variants.card` whole rather than merging. A malformed card or kanban body reports `invalid_card_variant` or `invalid_kanban_variant` and keeps the file visible instead of failing the load. This package validates shape only; whether `columnField` is a usable single-valued field is a runtime question answered by `pkg/app/views` with a warning, because field capabilities come from the source adapter.
- **Table is always available**: a view that declares only card or kanban still executes as a table with columns synthesized from its card spec. `missing_table_variant` therefore means no executable variant at all.
- **Strict known fields, forward-compatible extras**: validate supported source/mount/default/table fields strictly, but ignore unknown fields from newer Rhizome versions. If this version cannot fall back to an executable table variant, report a validation issue and leave the config out of execution.
- **Tracked settings**: `.rhizome/views` is repo config, not transient state. Keep init-managed `.rhizome/.gitignore` behavior aligned whenever this location changes.
- **Issue codes are API**: CLI, agent validation, web catalog issues, and future UI repair flows consume these codes. Prefer adding a new code over changing the meaning of an existing one.
- **Custom source**: `source.kind: custom` with a relative `source.entry` makes the view's body code beside the definition ([[custom-view-apps|SPEC-0105]]). It stays a view definition so there is one loader, validator, catalog, and mount model; a folder of definitions is the multi-view unit and shares components through relative imports. Custom views accept standalone, type, interface, group, and node mounts and reject `defaults`, `variants`, and `filterPresets`. This package checks the entry's shape and existence and owns the one rule, `ServablePath` and `WalkFolder` in `folder.go`, for what in the views folder a browser may see: no definitions, no dot-prefixed names, no `node_modules`, and no symlink traversal; `pkg/viewscript` transforms scripts, `pkg/app/web` serves them at `/views/`, and the loader skips `node_modules` so a built view folder cannot contribute definitions.

- **Mount contracts**: group targets name effective Notes navigation groups, or `*` for all groups. Type and interface targets name one type or interface, or `*` for every type or every interface; `MatchesMount` treats the wildcard as matching any subject of that kind, reference checks skip it, and `ReplacesGenerated` refuses it, since one native view cannot take every generated view's slot. A native view on a wildcard stays listed with a `generic_native_mount` warning: it reads its own source, so every collection would show that one type. Node mounts name a note or embedded-node type and require custom code. `mount.group` is meaningful only on group mounts and as the rail heading of standalone mounts; elsewhere it is ignored with an `unexpected_field` warning so older v1 files keep working. Multiple definitions may target one subject; conflicting authored defaults at the same specificity emit a `duplicate_mount_default` warning for every conflicting definition and keep each view usable. `configuration` is an optional JSON object available to the selected presentation; nested YAML keys that are not strings become text: numbers and booleans as written, `~` as `null`, and timestamps as `YYYY-MM-DD` at UTC midnight, otherwise RFC 3339.
- **Schema-aware checks and writes**: `SchemaValidateOptions` is the one schema-derived option set for the catalog, Save view, and `rzm validate views`; it lists Date/DateTime selectors so `defaults.group.bucket: month` is rejected elsewhere (`group_bucket_requires_date`, `unsupported_group_bucket`), and table density is checked (`unsupported_table_density`). `Decode` is the loader's single-file parse, `Marshal` renders new files in two-space style, and `ApplySavedLayout` edits only the `defaults` and `variants` keys Save owns through yaml.v3 nodes so comments and other keys survive, re-encoding with the file's own smallest indentation so a small Save does not reflow the file.
- **Replacing generated views**: `mount.replaceGenerated` is valid only on native mounts that name one `type` or `interface`; `ReplacesGenerated` is the one rule both validation and target resolution use. Elsewhere it is an `unexpected_field` warning and ignored. Several valid replacing views on one target each get a `duplicate_replace_generated` warning, sharing the duplicate-default grouping, and stay usable.
- **Navigation parity**: `NavigationMembers` is the one Go rule for which types and interfaces the ontology summary lists, and `DisplayTree` derives roots and nesting with the same claim order as `web/src/components/noteRailGroups.ts`; `DisplayGroups`, group default selection, and `GET /api/v1/display-groups` all read that tree. `testdata/display-groups/rail-groups.json` is asserted by both sides; change both together.
- **Filesystem sources**: `LoadFS` loads definitions from any `fs.FS` with slash `Source.Path` values, as the bundled views source does. `ValidateOptions.EntryFS` checks custom entries inside that filesystem instead of on disk. `Origin` is catalog metadata assigned by `pkg/app/views`, never read from YAML.
