# Provider access

`pkg/app/provideraccess` is the one application factory that decides how Rhizome reaches Voyage and TypeSafe ([SPEC-0129](../../../docs/specs/technical/team-api-gateway.md)). Every production provider construction goes through `Default().NewEmbeddings`, `Default().EmbeddingConfig`, or `Default().NewTypeSafe`. Provider libraries receive the decision explicitly and never read the session store.

- A user-global `provider_access` preference controls each provider independently. `server` uses only the team session, even when caller, environment or saved keys exist; an unavailable session fails closed. `key` uses caller, environment, then saved keys, without server or bundle fallback. Repository configuration cannot supply this preference.
- With no preference, precedence stays direct key (`VOYAGE_API_KEY`/`RHIZOME_VOYAGE_API_KEY`, `TYPESAFE_API_KEY`, or a caller-supplied key), team session, legacy bundle (`pkg/teamkeys`), then unavailable. `Factory.DevBuild` first takes a signed-in loopback session in this automatic mode only. A store error can fall through to the bundle; unavailable errors use bounded reasons rather than arbitrary store error text.
- The choice is made once per construction. A gateway failure is returned to the caller and never retried through another billing source.
- `VoyageSource`, `TypeSafeSource` and `Reports` share construction's resolver. Reports expose only preference, route, key provenance/name, saved-key presence, origin and bounded reason. `TeamStatus` exposes account metadata. None includes keys, tokens, partial credentials or credential fingerprints.
- Runtime reports distinguish constructed Voyage access and the most recently constructed Jev client from the next decision using that process's environment and current global configuration. Before a provider is constructed, active access is unknown. Routing changes can require restarting Voyage; report comparison establishes routing provenance, never equality of secret key values.
- Health reads use `CachedRuntimeReports`: the latest immutable snapshot returns immediately while at most one background refresh performs configuration/keychain I/O, no more often than every five seconds. The first snapshot reports checking. These refreshes own no runtime stores or provider clients and stop scheduling after runtime cancellation; a loader already in progress retains its own bounded timeout.
- Non-Voyage embedding providers resolve exactly as `embeddings.NewProviderForConfig` does. The reranker keeps direct keys only.
- The application installs the real session loader once at startup with `Install`. The zero `Factory` has no loader and behaves as Rhizome did before team sessions. Callers keep close ownership of returned providers and caches.
