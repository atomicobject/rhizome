## Configured view runtime

`pkg/app/views` turns native `.rhizome/views/*.yaml` definitions plus generated defaults into executable table views. It is the shared runtime seam for web, CLI, and agent callers; handlers and commands should stay thin adapters over `Service`.

- **Section summaries**: a singular `@contains` field marked SUMMARY supplies compact indexed body text to native rows and cards. Its display capability is read-only: section workspace editing owns the prose, and the typed field remains a section.
- **Config ownership**: `pkg/ontology/viewconfig` owns file format, loading, and static validation. This package owns generated defaults, source adapters, table execution, fingerprints, and response shape.
- **Personal settings** ([[view-preferences|SPEC-0114]]): this runtime continues to own shared defaults and native execution. Personal state is owned by `pkg/app/userstate` in a separate ignored database; browser/native and custom kit clients hydrate valid overrides before dependent execution. Neither a catalog read nor an interaction writes YAML. Explicit shared Save promotes reviewed values, preserves unrelated authored configuration, and leaves personal-only widths and expansion choices to the client preference lifecycle.
- **Source adapters**: ontology-backed views must resolve through `noderead.Scope.TypeInstances` and hydrate through `noderead.Scope.Hydrate` so rows preserve canonical `NodeRef` identity. Do not add a path-only note scanner here.
- **Indexed embedded sources**: ontology-type views for embedded nodes should push schema-supported filters and first sort key into the GraphQL indexed root before display pagination. Keep search and unsupported filters/sort residual; expose `pushedConstraints`/`residualConstraints` so performance questions are debuggable.
- **Link target filters**: `eq` and `in` share the request-scoped pushdown target resolver with GraphQL. Canonical note-root paths use a provider-neutral indexed lookup; title/alias discovery is limited to 5000 target candidates across implementors and emits `link_filter_resolution_incomplete` above that bound. Candidate-scoped alias reads and cached target sets keep several filter values from repeating catalog scans.
- **Query recipes**: `query_recipe` sources call `pkg/ontology/queryrecipe` and extract node-like rows from `source.resultPath`, falling back only to recipe `outputContract.rowPath`. They are not a generic arbitrary table engine and must not fall back to the first array in a map. When extracted rows resolve to ontology types, derive the same schema-backed capabilities as ontology sources; recipes select rows, schema controls editability.
- **Rows**: every executable row should carry `ref` when available, plus `path`, display fields, and JSON-safe `fields` values for table operations. Link fields carry titled `relationValues` for every row, committed or staged: indexed field rows supply target refs, and staged or unindexed records resolve their raw values (embedded-node link fields read the inline key named for the field). Note-root records carry no field rows, so one `Scope.IndexedRecordFieldValues` batch serves every committed note row, matched by field name and value text; never resolve committed rows one note at a time. Values the index cannot vouch for share one index-only Resolve, except Markdown and relative wikilinks, which resolve from their own note. Ontology rows expose semantic schema field names such as `id`/`specStatus` while retaining raw `frontmatter.*` and `inline.*` selectors for explicit configs.
- **Link groups**: grouping by a link field keys each bucket on the resolved target (unresolved links on their target text) and labels it by the target's title, or an unresolved link's alias, else its target name. Groups follow their targets' `@display(role: RANK)` field, ranked targets first; unranked targets and unresolved links follow by label. Authored `group.values` order still wins. Relation lanes rank their targets the same way before stage and size. A resolved group's value is the target's canonical link, `[[<vault path without .md>]]`, which resolves from any note, so its key, collapse state, and board moves do not depend on which row sorts first; an unresolved group keeps its least authored spelling. Configured `group.values` and kanban columns for link fields resolve to the same canonical link before matching. Faceted link fields hydrate titles over every source row and list each target once, as its canonical link with a title in `labels`; group-only link fields hydrate over the filtered rows, in the same read. A request reports `view_relation_hydration_failed` at most once.
- **Edit metadata**: row capabilities may include `edit` for safe inline edits. Keep this schema-derived: enum fields expose valid options, Boolean/checkbox fields expose boolean toggles, and single relation fields expose target-node candidates. Web callers stage these as ontology edit-session ops; the view runtime does not write files directly. When a web request includes an edit-session preview, the service passes `ReadOverlay` through query deps and ontology sources so returned rows already reflect staged values; table renderers should not maintain their own read overlay. The one exception is a transient bridge: while a re-execution is in flight after an edit, the web shows staged scalar values and board moves from the edit session, then defers to the returned rows.
- **Defaults**: generated type/interface views are runtime-only and are named for the type's plural label, else its authored label, else its humanized name. Do not write generated defaults into `.rhizome/views`; generated definitions remain directly executable and selectable beside authored views, since an authored source may filter the collection. A valid `mount.replaceGenerated` view (`viewconfig.ReplacesGenerated`) takes the generated view's slot: the generated view contributes no choices for that target, stays addressable by ID, and the replacing view inherits its default role. Invalid definitions retain diagnostics but contribute no choices or defaults. `Catalog.Targets` resolves all compatible presentations with an exact authored default before a generic (`"*"`) one, and both before the standard view's default. Without one, a type or interface opens its standard view's default variant (the generated view's, or the replacing view's `defaults.variant`, else its first layout in Table, Cards, Board order); groups fall back to the bundled default by shape (see Group defaults by shape) and nodes to Structured. The workspace target has an empty name, offers standard bundled Briefing then Overview, and defaults to Briefing. Bundled group Overview replaces the built-in Overview choice and leads the group choices; types and interfaces offer the bundled Briefing instead (see Type Briefing). Conflicting authored defaults are warnings, so every conflicting view stays selectable and the deterministic choice order (order, then ID) picks the default. Node targets exist only for note and embedded-node types. Hidden definitions are excluded from navigation and remain addressable by ID. When an authored view declares no table columns and its schema uses non-NORMAL field importance, the implicit table chooses title, identifier, KEY fields in schema order, then Changed (which keeps its slot), and fills any leftover room with NORMAL fields; DETAIL stays available through capabilities but is not default-visible. Authored column and card-field lists remain exact.
- **Profile-driven defaults** ([[type-collection-views|SPEC-0112]]): generated views read `ontology.DeriveTypeProfile` and never field names. `generatedDefault` takes the profile, so tests build profiles by hand: shape picks sort and grouping (the lifecycle for `workflow` and `contract`; `dated` groups the primary date by month; `catalog` the first category field), up to ten columns end with the date and Changed, Cards needs a summary field (a DETAIL summary is never the generated card preview), and Board a lifecycle. The generated definition always says Table; `generatedDefaultVariant` decides Board for a workflow type from one indexed `OntologyFieldValueCounts` read, and `Catalog`, `View`, and variant-less `Execute` all apply it, so a target's default choice agrees with execution. `Execute` fingerprints the definition before that decision. Single-view lookups skip target resolution and count reads.
- **Lifecycle order**: grouping by a capability with the `status` role whose values all carry stages orders groups `active`, `open`, `done`, `dropped`, then declaration order (`lifecycleGroupRanks`). Generated views apply it to declared and inferred stages; authored views, including saved replacing views, apply it only when the enum declares its stages, so an authored view over an enum without declared stages keeps enum order as before. Authored `group.values` orders still win. Board columns keep the enum's order.
- **Roles and statistics**: ontology capabilities take roles from the source profile (`status` lifecycle, `summary`, `date` for Date/DateTime, `identifier` from identifier flags); `semanticRoleForKey` name guesses apply only to row keys of sources without schema fields. Enum values carry `stage`, `stageDeclared`, and stage-derived collapse. Type and interface executions return the profile and `ExecutionStats` computed over the filtered rows before paging, with `truncated` set when the source cap may have cut rows; reverse-count fill appears only when the request projected those counts (table columns, or any board or card layout). On board and card executions, page rows also carry `relationValues` for projected reverse fields: up to eight linking records, listed by title, from one relation read per field after paging that stops at eight edges per row (`FirstPerSource`, `hydrateReverseRelationValues`). Board and card executions then set each relation value's `status` (the linked record's lifecycle value, label, tone, and stage from its type's profile) for up to eight values per field and row, from one summary hydration (`hydrateRelationStatuses`); relation lanes read their target's stage and tone from those statuses. Table executions keep reverse fields as counts and hydrate no linking records or statuses.
- **Boards and Save**: board lanes come from the request's `laneField`, the kanban `laneField`, or the profile default, and index page rows per column; relation lanes order by the target's lifecycle stage from the relation statuses. `columnField` may switch to the lifecycle or a single-valued ordered field; a list enum cannot hold one column value. A requested lane field that does not resolve or repeats the column field is a 400; a configured one warns `view_kanban_lane_unsupported` and falls back to the profile default, as a bad configured column field warns `view_kanban_column_unsupported`. `Service.Save` leaves group, columns, density, and board fields the state omits unchanged (an empty density or lane field removes the key; a group with an empty field saves `group: {field: none}`, which `normalizedGroupFields` reads as explicitly ungrouped in saved views and requests alike). It writes `.rhizome/views` YAML (new replacing view from a generated one; in-place `defaults`/`variants` edits via `viewconfig.ApplySavedLayout` for authored ones). It refuses any issue `rzm validate views` would report on the written file, warnings included, then runs the state through `Execute` so it refuses what the runtime would (board fields, filter operators, group buckets, link filter values). It refuses symlinks and paths outside the views folder (checking `.rhizome/views` before creating it), and returns `ErrSaveConflict` on a stale definition fingerprint, when a valid view already replaces the generated view being saved, when a new file's name was taken first (new files are hard-linked into place, never renamed over), or when an authored file changed while saving (rechecked under a per-file lock just before the rename).
- **Execution order**: source -> search -> filters -> sort -> group summary -> pagination. Fingerprints should include definition, source identity, and normalized execution state.
- **Sorting**: indexed textual scalar, enum, Date, and DateTime fields retain the index's normalized lexical order during residual row sorting, with missing values last in either direction. Invalid Date and DateTime values also sort as null, matching failed parsing in the indexed typed columns; secondary keys break ties among invalid and missing values. Indexed Int and Float fields compare their typed numeric values, preserving 64-bit integer precision; invalid values and NaN follow SQL's null placement. Repeated indexed scalar fields normalize each value and select the minimum valid value ascending and maximum descending, matching SQL aggregation; all-invalid lists sort as null. DateTime uses canonical RFC3339 text with the authored offset and whole-second precision, matching its indexed column. Adding an unsupported secondary key must only break primary ties, including through field aliases. Other residual row sorts and unranked group values classify each value independently: numbers first, then dates, then text. Numeric strings sort numerically; dates sort chronologically; text sorts lexically. NaN sorts as text and infinities as numbers. Empty values keep their existing placement (first in ascending row sorts, last in groups), and equal row values use canonical node identity as the tie break. Pairwise filter coercion is separate from sorting.
- **Filters**: the reserved `stale` filter (`{field: stale, op: eq, value: "true"}`, unless a capability is named `stale`) runs residually through `staleRule`, the same rule as `ExecutionStats.StaleCount`: an active-stage lifecycle value unchanged for 30 days by the server clock. Residual indexed scalar equality uses typed numeric/date values and normalized text, matching indexed predicates. Equality and ranges share predicate coercion: unparseable numeric and DateTime thresholds fall back to normalized text; Date uses its text column for ten-character thresholds. Indexed Int range comparisons preserve 64-bit precision, and DateTime comparisons use canonical RFC3339 text with authored offsets and whole-second precision. Facet collection stops after 51 distinct values because fields above the 50-value bound are omitted.
- **Extension point**: add new sources as adapters that return canonical rows plus warnings. A future general GraphQL source should be additive to `ontology_type`, `ontology_interface`, and `query_recipe`, and should still preserve row identity when the result is node-like.

- **View targets**: table, card, kanban, Overview, Structured, Source, and custom entries share `ViewChoice` identity and selection. Standard choices come first: built-ins, then the subject's own native layouts in Table, Cards, Board order (generated, replacing, or a standalone target's own, named plainly). For a display group, the bundled `group.overview` replaces the built-in Overview and leads the standard choices (when it is hidden or invalid, the built-in navigation list returns as the fallback named Types, so it never shares Overview's name), followed by `group.briefing`, `group.trace`, and `group.sections` (matched by id so ejected copies keep the role). For a type or interface, the bundled Briefing (`type.briefing` or `interface.briefing`, matched by id) is the first standard choice, before its layouts, and there is no Overview. Every other authored choice follows by order, then ID, with `custom: true` and a qualified name. The web maps a remembered generated choice whose view was replaced to the replacing view's same layout. `viewconfig.MatchesMount` owns subject-free workspace, exact node, and exact-or-wildcard type/interface/group applicability; `viewconfig.DisplayGroups` derives effective navigation roots without creating semantic union membership. Durable target-scoped personal preferences refine this configured catalog and do not duplicate default policy.
- **Three origins** ([[group-views-and-view-platform|SPEC-0111]]): every catalog entry carries `origin`. `repository` definitions load from `.rhizome/views`; `bundled` definitions load from `ServiceOptions.Bundled`, the kit build's copy of `web/bundled-views` (nil without the web UI, `fstest.MapFS` in tests), and are validated with `EntryFS` set to that filesystem; `generated` definitions are runtime defaults. A repository definition with a bundled id replaces the bundled one, issues included, so ejecting never produces a duplicate id. The catalog lists entries by id; a target orders its choices as described under View targets, whatever their origin.
- **Group defaults by shape**: a group's default is an exact authored group default, then a generic (`group: "*"`) authored default, then the bundled default: `group.briefing` when the group has two or more navigation roots, else `group.sections`, falling back to the other one when the preferred view is hidden or invalid. Overview stays selectable and remains the default only when neither bundled view is available. `group.trace` is offered only when two distinct navigation roots (interfaces stand for their node implementors) link through a forward `@link` whose declared target is a root or a type within one; a field typed by an outside interface such as `Note`, or a link between implementors of one root, does not count. A type under two roots belongs to the first in the display-groups API's member order (rail label, then name), the order the bundled views' `planMembers` claims types in. These rules follow the ids, so an ejected copy keeps them.
- **Type Briefing** ([[type-collection-views|SPEC-0112]]): `type.briefing` (mounted on `type: "*"`) and `interface.briefing` (`interface: "*"`) share one entry in the group views' folder, so ejecting any bundled view copies them all. They take Overview's place as a type or interface choice but never its default role: without an authored default, the shape rule still opens the generated Table or Board. A remembered Overview choice for a type no longer resolves, so the web falls back to the target's default. A wildcard invocation context is refused; the host always supplies the concrete type or interface. The Briefing loads its collection from navigation, so it is offered only for a type or interface that navigation lists (`viewconfig.NavigationTree.Listed`): not for section types, embedded types without a display parent, or interfaces the rail hides.
- **Eject**: `Service.Eject` copies a bundled view's whole folder (the unit views share components in) into `.rhizome/views/<folder>/` through `os.Root`, leaving out tests and fixtures as the kit build does, writes nothing when any destination exists, and refuses an id a repository view already defines.
