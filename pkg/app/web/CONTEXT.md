## Web explorer + ontology HTTP surface

Serves the browser UI for file/tree/graph navigation plus the ontology workspace. Handlers should reuse the shared ontology runtime and persisted store; do not build a second note model for the web layer.

- **Entry points**: `server.go` wires routes/runtime; `handlers.go` serves explorer/search/graph data; `ontology.go` serves typed summary/query/inspect/workspace payloads.
- **Key invariants**: ontology pages only see notes admitted by vault include/exclude rules; filesystem-backed tree, raw-file, and rendered-note reads accept only paths whose resolved targets stay under the resolved vault root, and ignore rules apply to both a requested symlink alias and its in-vault target; rendered-note and ontology-workspace payloads must stay path-stable because compare panes and inline expansion reuse them as navigation state; summary/type browsing must degrade to indexed note metadata when query-schema generation fails or when no ontology schema exists at all, instead of hiding the note list; while an ownership batch has cleared the published metadata state, the summary serves the last published counts with `rebuilding: true` (zero counts with the flag before the first publication) instead of reporting an empty vault; untyped/schema-less notes should stay on the markdown path rather than synthesizing a structural view.
- **Agent chat**: `/api/agent/*` persists sessions and harness events under `.rhizome/agent/` as local ignored state. Each writable chat owns one lazily started `pkg/harness` session; pre-harness history stays readable and cannot accept new turns.
- **Canonical read surface**: public `node(ref:) { workspace { ... } }` GraphQL reads are the browser-facing ontology workspace contract. Root notes, sections, and embedded nodes resolve through canonical `NodeRef`; the TypeScript adapter owns pane/rail/view orchestration. The retired unversioned node-workspace detail and graph handlers must not be reintroduced.
- **Live ontology schema**: the web server refreshes its cached GraphQL definitions when authored `.rhizome/ontology/*.graphql` content changes. The source hash check does not read the index or alter an admitted exact-note snapshot; full workspace reads still wait for matching catalog publication before returning the new schema's data.
- **Startup gates**: `rzm serve` loads and classifies a prepared GraphQL operation before it requests live ontology dependencies. Singular `node` / `note` roots with raw-note-only nested selections may open only when SQLite contains a provider-current projection for every requested path and the live indexing selector still assigns each path to notes; fragmented `node` refs, `__typename`, `resolvedType`, `ref.typeName`, and type-conditioned fragments wait for the complete type model. Selection-policy reloads update the read side. Admission materializes metadata, properties, and tags in one short SQLite read transaction and uses that immutable fact bundle for the rest of the request, so concurrent publication cannot mix generations. Direct GraphQL and public saved-recipe execution share that prepared-query admission path. A validated existing Intel read handle is published during search initialization, before semantic startup, and exact hydration reads the admitted path's durable fact bundle without consulting the unrelated global ready bit. Workspace, neighborhood, graph, relation, and node-returning authored fields require complete readiness. A selected path whose source exists waits for publication even if the one-shot complete gate previously opened. Full workspace and fragmented reads additionally wait for the selected note catalog witness to match the provider-current source content hash and schema, without receiving the raw-only immutable fact admission; after complete readiness, an absent source returns a final missing result. An exact-row read error returns the same retryable 503 readiness response. Mixed, broad, semantic, runtime, validation, code, identifier, and introspection operations also wait for complete index readiness. Full readiness opens the note gate; an empty cold store stays gated, and followers poll both publication transitions.
- **GraphQL reader ownership**: default ontology services and queries resolve the current live-snapshot note reader on each call, then fall back to the configured server reader, including its watcher-backed inventory and refresh behavior. Preserve explicitly supplied readers and the raw-reader fallback for servers without a cache; do not bypass the live reader with a new raw reader.
- **Type/list seam**: lightweight read surfaces such as `/api/v1/ontology/types/{name}`, summary, and atlas should read through the shared node-centric type-instance catalog in `pkg/ontology`, which lifts note-path indexes and structural projections into canonical `NodeRef` results. Treat note-path indexes as persistence helpers, not the browser identity contract. Type-home list items (`OntologyNoteListItem`) MAY include `identityStatus` — the resolved value of the type's identity-level enum field (the first enum field whose lowercased name ends with `status`) — so cards can render a status pill without a per-note workspace fetch. The Go heuristic in `pickIdentityStatusField` mirrors the TS `pickIdentityFields` in `web/src/components/ontologyFieldPicking.ts`; keep them in lockstep.
- **Note-search type scope**: `/api/v1/search/notes` resolves interface filters through the node-centric type-instance catalog, then searches only file-backed NOTE-role implementors. Embedded implementors remain ontology instances but are not standalone note-search candidates. Candidate paths and final result filtering must use the same resolved concrete-type set.
- **Project search contract**: `/api/v1/search` adapts the shared ranked engine for browser use. Scope, owning-note type, and literal vault-relative folder restrictions apply before bounded candidate retrieval and again before ranking. Pagination tokens bind query, effective filters, vault identity, candidate window, and ordered-result digest; a changed window returns `CONTINUATION_STALE`. Results preserve canonical `NodeRef`, link target, code anchor/line, genuine source excerpts, bounded counts, and structured capability warnings. A title, heading, or path is never relabelled as an excerpt.
- **Personal view preferences** ([[view-preferences|SPEC-0114]]): `/api/v1/view-preferences` exposes read, patch, reset, and legacy import through `pkg/app/userstate`, independently of index readiness and the ontology edit session. The server owns `.rhizome/user-state.sqlite` lifecycle. If opening it fails, preserve its files and keep other web features available; preference routes report an actionable 503. Validate and bound scopes and values, retain canonical concrete invocation identity without byte offsets, preserve JSON null versus removal, and return explicit revision conflicts. Atomic per-key patches, reset tombstones, and one-time legacy source claims prevent lost edits and resurrection. Shared view Save remains a separate YAML operation.
- **Configured views**: public `/api/v1/views`, `/api/v1/views/{id}`, and `/api/v1/views/{id}/execute` delegate to `pkg/app/views`. Keep handlers thin and preserve row `NodeRef` identity so configured table rows open the same node workspace panes as type lists.
- **View targets and invocation**: the catalog also exposes compatible target choices and configured defaults, shared by browser and agent discovery. Custom `type`/`interface`, exact or generic `group`, and concrete `node` mounts use the same definition loader and validation; the `/views/<id>` shell and HTML context injection resolve through the configured-views catalog and refuse a view it marks invalid (raw `/views/_files/<rel>` assets stay path-gated only). If the ontology cannot load, standalone views fall back to schema-less validation so their links keep working, and subject-mounted views answer 503. `/views/<id>?context=...` validates concrete context against applicability and supplies server-authored configuration plus canonical invocation to both script and HTML entries. Preserve context through the HTML entry redirect, inject invocation before module scripts, and retain path containment, serving exclusions, origin/frame-source checks, and custom-code versus isolated-note hosting. Exact group defaults precede generic ones; groups are presentation metadata. [[unified-view-contract|SPEC-0110]] owns this contract.
- **Bundled views and view files** ([[group-views-and-view-platform|SPEC-0111]]): bundled views are served like repository views, with files under `/views/_bundled/<folder>/<file>` from `BundledViews` (the embedded `bundled-views` copy, or `RHIZOME_BUNDLED_VIEWS_DIR` while developing them, read through `os.Root` so no symlink leads out of it), and their invocation carries `view.origin`. Every view file answers with an ETag and `Cache-Control: no-cache`, so unchanged files revalidate to 304; transformed modules are cached by name and source hash, and the ETag salt changes per process. The shell stays `no-store`. A sibling `.css` side-effect import is rewritten to `<file>.css?rhizome-css`, which answers a module that links the stylesheet once per document. Plain `.js` and `.mjs` modules are transformed only when they contain such an import, keeping their syntax and module format; others are served as written. Bundled shells get no stamp; repository shells carry `folder`, matching the `views.changed` event's `{folder}`. That event comes from one poller in `custom_view_watch.go` that runs only while an `/api/v1/events` stream is open, because the vault watcher excludes `.rhizome/`; closing the last stream (`Server.Close` ends them all) returns only after the poller has exited, so nothing is announced afterwards; the stamp route remains the standalone fallback.
- **Display groups**: `GET /api/v1/display-groups` arranges ontology-summary members with `viewconfig.DisplayTree`. It includes the rail's `Other` bucket for ungrouped roots, last as in the rail, because the catalog targets `Other` like any group and the bundled group views look their group up here by name. A member's `issueCount` is the published validation issue count of its type or interface scope (one batched scope summary read with `InterfaceImplementors`), so a badge matches the scoped issues panel it opens; the Notes rail and ontology summary still count notes with ontology assessment issues.
- **Hosted node context**: a custom frame can receive the canonical node ref already resolved through the host's staged workspace read, so switching presentations after a staged rename or node creation preserves that subject. The hosted transport marker conveys no edit-session or token authority; reads/writes still use the frame bridge and session-aware API. Direct standalone node invocations re-resolve committed identity. `hosted=1` is a caller-controlled URL parameter, so both modes require a valid vault-relative `notePath`, a ref `typeName` that is empty or equal to the context type, and strip caller byte offsets and `parentId` before the ref reaches the invocation; public identity (`nodeId`, fragment, structural fingerprint) is kept. Do not force a hosted staged ref through a committed-only lookup or put edit-session state in launch URLs.
- **View workspace behavior**: `NotesWorkspace` renders an active configured view as the root stacked pane. Clicking a configured table row opens the file/node workspace in a new pane to the right, leaving the view available as the root context.
- **Canonical graph payload**: `NodeWorkspaceResponse` now publishes `focusedNodeId`, canonical `nodes[]`, typed `edges[]`, and optional `views{renderedOutline,structuralOutline,relationGroups}`. Treat those graph fields as primary identity-bearing data; `fields[]`, `collections[]`, rendered sections, and structural trees remain additive compatibility or convenience projections.
- **Sliceable workspace contract**: GraphQL selection sets are the loading boundary. `workspace.loaded{rendered,assessment,structure,relations}` reports selected domains while omitted assessment/relation fields perform no corresponding side work.
- **Status model**: `NodeWorkspace.status` is the aggregate pane status, and `fields[]` / `collections[]` now carry the same `NodeStatus` shape for granular validation/dirty surfaces. Server assembly should populate validation from ontology assessment, while live edit-session dirty/rebase/conflict overlay may still be composed client-side from canonical session metadata.
- **Validation API migration**: the retired `/api/v1/validate` returns 410 with `VALIDATION_API_RETIRED`. Clients discover `/api/v2/validate` through capabilities; do not restore legacy result hydration. Snapshot `issueCodes` is the complete generation vocabulary, independent of loaded pages.
- **Validation read contract**: `/api/v2/validate` separates the current run lifecycle from `publishedGeneration` and its typed snapshot, read together in one SQLite snapshot. Running and failed refreshes retain the last published counts/check outcomes; invalidation marks that snapshot stale. A missing, incomplete, stale, or failed snapshot never becomes a clean health state. `/api/v1/validation/diagnostics` returns bounded generation/filter/sort-bound pages with text and contextual scope filters. `/api/v1/validation/summaries` batches up to 200 global/file/note/node/type/interface aggregates from the same persisted membership model and applies the same optional diagnostic filter as detail pages. Public REST, OpenAPI, and GraphQL use canonical check IDs and the same issue/file/note/repair counts and page limit of 200.
- **Repair review contract**: `/api/v1/validation/repair-reviews` creates opaque reviews from a published generation, plan fingerprint, and stable action IDs. Get/apply routes expose presentation diffs and typed lifecycle outcomes while the server retains the original validation authority. Never rebuild operations from cached diagnostics or browser recovery. Review apply rechecks generation, source preconditions, confirmations, and manual-path reservations, then uses the canonical repair engine. A repeated apply on a retained terminal review returns its recorded result.
- **Edit sessions**: `/api/v1/edit-sessions` is the canonical write surface. Server memory owns the live `EditSession`, but every response returns the full canonical op list so the browser can persist a recoverable session snapshot and recreate the server-side session after restart.
- Save publishes `node.changed` with refreshed paths and domains after successful projection, cache, and workspace refresh. Warnings suppress the readiness event, and receipt replay does not publish it again. A separate WatchHub hint retains semantic work even when foreground reads consume cache dirtiness. See [[docs/reference/subsystems/ontology|Ontology subsystem]].
- Successful source commits also return `refLineage` from their existing current-source replay. This mapping binds original field-edit refs to committed refs, survives receipt replay, and lets clients stage subsequent edits without waiting for view reads. Refresh warnings do not invalidate this source mapping; unresolved or ambiguous refs retain strict rejection.
- **Session-aware reads**: web handlers own edit-session restore/preview and convert the result into `noderead.ReadOverlay` before calling GraphQL or configured views. A later field edit may carry the changed structural identity emitted by that preview; stage canonicalization may accept it only through the same session overlay and map it to one unique prior session ref. Do not put session logic in query recipes or table renderers; they should consume already-overlaid read results.
- **Revalidation boundary**: `create`/`stage` return canonical staged state only; `GET`, `preview`, and `commit` revalidate against disk so the UI can surface `dirty` vs `rebased` vs `conflicted` without reimplementing ontology diff logic in the client.
- **Recovery contract**: browser-stored snapshots are backup state, not authority. Restored sessions must still run through server-side preview/rebase/conflict detection before the UI treats them as live again, and the browser must scope recovery state per tab/window so one pane stack cannot resurrect another tab's session.
- **Node identity**: browser refresh/edit targeting should prefer canonical `NodeRef` payloads (`touchedNodeRefs`, resolver results, future subscriptions) over raw `path#fragment` strings; locator strings remain request inputs only.
- **Section refs**: rendered section ids (`path#slug-offset`) are not the same thing as heading anchors (`#Heading`). Web focus helpers and structural pane-open logic must accept both; otherwise section-targeted panes resolve canonically but still render the full note through an unfocused compat view.
- **Refresh behavior**: commits and rebased/conflicted sessions must refresh both touched panes and sidebar/search data; otherwise the browser can show stale type lists or note-search results even when the note pane is current. After a successful commit has refreshed exact derived paths, the web runtime queues a serve-lifetime validation refresh. The readiness coordinator debounces that request with watcher invalidation so one change does not launch duplicate full scans; Save can report durable completion while validation publishes its later generation.
- **Live update path**: `/api/v1/nodes/events` is the SSE invalidation stream. The server resolves requested refs on subscribe but events echo the ref exactly as subscribed; it re-resolves from the last announced projection (whose structural fingerprint follows renumbered items), sends `canonicalRef` only when the locator itself changed (a renumbered item, not a new fingerprint from an edit), and advances each subscription's version after publishing so an unchanged file is not announced again. The browser should treat events as refetch triggers for matching panes rather than as authoritative content patches.
- **Browser server-state ownership**: `web/src/api/queryClient.ts` owns the single TanStack Query client and `queryKeys.ts` owns identity construction. Query keys must include every behavior-changing input; API wrappers accept an optional `AbortSignal`. Components keep route/selection/draft/layout/display state locally, but must not mirror reusable server responses into unguarded effect state.
- **Notes type-list contract**: `/api/v1/ontology/types/{name}` is the only Notes type-list read. Do not pair it with the public typed-list GraphQL operation: the REST payload already contains the rendered list fields, and duplicate reads create failure and response-ordering boundaries. Initial load, empty success, background refresh, and retryable error are distinct UI states; data from one type must never render under another type route.

- **Application host boundary**: validate Host before application/API dispatch, including read and mutation routes. Allow a configured HTTP(S) application origin independently of HTML viewing, including LAN and reverse-proxy hosting. Remote HTML viewing still requires separate HTTPS application and content origins. Keep isolated HTML viewer host routing explicit. HTML notes remain trusted active repository content with eligible-vault resource access and message nonce isolation.
