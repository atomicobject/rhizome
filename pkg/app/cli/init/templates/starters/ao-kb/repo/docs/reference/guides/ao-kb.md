# AO KB knowledge workspace

The optional `ao-kb` starter presents an existing AO KB's Markdown knowledge in Rhizome and compiles the selected product's model into read-only bindings. The AO KB root must be the vault root, at schemaVersion 8, or at 4 through 7 for a single-product KB, which sets up knowledge-only (see "Older AO schema versions" below). It installs Assertion, Source, Concept, Artifact, ConflictRegistry/ConflictEntry, and the read-only MapOfContent, Submission, and CurationDocument types in the Knowledge group, a workspace with Attention, Concepts, Assertions, and Knowledge trace, assertion and source presentations, claim-to-source, reverse-impact, concept-evidence, and artifact-evidence recipes, and the binding compiler. The selected model is indexed read-only, with native evidence links and per-file sync observations.

## Setup

Run from the vault root, using the repository's Rhizome launcher in place of `rzm`. The `ao-kb-setup` skill follows the same sequence.

1. `rzm init --add-addon ao-kb` for an existing Rhizome repository, or `rzm init --addons ao-kb` on first init. Init installs static assets, the binding compiler, and `.rhizome/source-ownership.yml` before anything is compiled or indexed, so AO's files are protected from the start. It runs no project-specific compiler. `rzm init --check` checks managed files only. If the repository already defines its own Rhizome types for AO notes, such as `assertion`, `concept`, `source`, or `artifact` in `.rhizome/ontology/`, the check's `knowledge bindings` row names each file and type: their query roots collide with the starter's types, the combined schema cannot compile, and both would claim the same notes. Retire or rename them, and update anything that references them, before refresh. The starter's types replace them.
2. Module actions run only in a trusted repository: run `rzm trust` once in the repository. Without it, `node .rhizome/modules/ao-kb/scripts/check.mjs` prints the same check. The Knowledge views use one other action, `ao-kb/read-evidence`, only to read a raw source file or `.kb/index/kb-weights.json` when the file is gitignored; without trust such a passage shows as unresolved and the saved analysis as unavailable, never as a clean result.
3. `rzm ao-kb check` (also `rzm module ao-kb check`) is read-only and needs Node. It returns JSON with `starterInstalled`, `bindingsReady`, `indexReady`, and named checks whose status is `ok`, `warning`, `error`, `pending`, or `unsupported`. The model dependency and model bindings rows name their state instead: `dependency missing` (uv or `rzm` is not on PATH, or uv cannot prepare AO's pinned packages from its offline cache), `duplicate IDs` (AO model records share an ID; the row names each occurrence), `stale` (configuration changed since the last refresh), or `error`. Knowledge rows cover the AO root (`.kb/config/vault.md`; schemaVersion 8 is the inspected baseline, a `vault.md` that records no schemaVersion reads as current as it does in AO, and a single-product KB at 4 through 7 reads knowledge with the model `not applicable`), product mode, toolkit stamp, note includes, source ownership, knowledge bindings, sequence-shaped frontmatter connections, and saved analysis. Model rows come from the compiler's own check: dependencies (`uv` on PATH supplies Python and AO's pinned kb-site package), model bindings, model index, and whether every compiled source is declared AO-owned. Successful execution alone does not mean setup is ready.
4. Include AO Markdown under `assertions/**`, `sources/**`, `concepts/**`, and `artifacts/**`, plus the exact `.kb/curation/_conflicts.md`, or `.kb/curation/*.md` when that folder holds other curation registries, logs, or reports (the check requires it then): discovery skips hidden directories unless an include names the path, so a broad `**/*.md` does not reach them. Append missing paths and keep unrelated rules. When `notes.includes` is absent, discovery already covers every Markdown file, and a first include list replaces that default: start it with `**/*.md` so the rest of the repository stays indexed. The check reads simple include lists and reports uncertainty for other YAML forms. Raw `sources/_raw/**` files support evidence display but are never typed Source records. If AO's site build runs in the repository, add its output folder (`_site/` by default, or `site.out` in `.kb/config/site.yaml`) to `.rhizome/ignore` so built pages are not indexed as notes.
5. Make sure source ownership is `ok` before refreshing. Add any AO-authored location outside the standard layout to `.rhizome/source-ownership.yml`.
6. `rzm ao-kb refresh-bindings --product <slug>` for a KB with product roots (the product is required and persisted in `.rhizome/modules/ao-kb/bindings/selection.json`), or `rzm ao-kb refresh-bindings --single true` for a single-product KB. Later refreshes reuse the selection; `--toolkit <absolute path to packages/kb-site>` selects a local AO checkout at the pinned revision. Node first generates `.rhizome/modules/ao-kb/ontology/ao-knowledge.generated.graphql`; the Python model stage writes `ontology/ao-model.generated.graphql`, generated node views, and `bindings/manifest.json`, which may be committed as derived artifacts, and never changes AO files. A failed knowledge stage keeps its previous generation. A failed model stage keeps the current knowledge admission and previous model generation, reporting model setup incomplete. Rerun the check: model bindings and model source ownership must be `ok`.
7. Add the exact model source paths listed in the manifest to note includes, preserving existing rules; a knowledge-only KB lists its declared model files even when none exist yet. Changing includes does not stale the bindings, but init records includes in the managed `AGENTS.md` and `CLAUDE.md` block, so rerun `rzm init` afterwards or `rzm init --check` reports those files. Run `node .rhizome/modules/ao-kb/bindings/cli.mjs index`, which runs real indexing and verifies model record counts, then `rzm agent ontology-query --query '{ assertion(first: 1) { title } }'`. An empty response is expected only for an empty KB. The final check must report both bindings and index ready.

Report **starter installed**, **bindings ready**, and **index ready** separately. Use the check's computed `bindingsReady`, not the saved manifest's status, which only records the last successful refresh. Neither managed-file checks nor prerequisites alone certify a usable projection.

## Older AO schema versions

A single-product KB at AO schemaVersion 4 through 7 sets up knowledge-only, without migrating and without uv or Python. Knowledge reads through a read-only adapter for AO's documented key renames: `assertionKind` for `kind`, `format` for a source's kind, `attestedBy` for `speaker`, and `supportingAssertions` for an artifact's `supported_by`, each read only when the current key is absent. Raw values are shown as stored. Product-model bindings need schemaVersion 8, so the model stage is `not applicable`: refresh publishes knowledge bindings and records the model manifest as `not applicable` with the reason; the check reports `bindingsReady` with `modelReady: false`, and its model dependency, model bindings, and model source ownership rows say `not applicable`; the index wrapper indexes, skips model-record verification, and writes a receipt that `indexReady` compares. AO's own migration is the way to enable the model. A legacy product-mode account is reported `ao_schema_unsupported`.

Every index receipt carries a site source signature over every Markdown file the Knowledge site reads: `assertions/`, `concepts/`, `artifacts/`, and `sources/` (except `sources/_raw/`), `_moc.md` and `MOCs/`, `_improvements/` (except `_archive/` and `_pending-attachments/`), and `.kb/curation/*.md`, at the account root and the selected product's root, plus the model sources at schemaVersion 8. Editing, adding, or deleting any of them, including an underscore-named artifact AO's reader skips, asks for one reindex. Receipts written before this signature existed expire once after upgrade.

## Supported versions and syntax limits

The inspected baseline is AO KB schemaVersion 8 with the AO prompt toolkit at commit `e9dce951` (ao-kb 7.138.8, kb-site 3.137.0). Like AO, the starter reads a `vault.md` with no `schemaVersion` line as current. Single-product schemaVersion 4 through 7 is read knowledge-only, as above; older versions are unsupported: upgrade AO KB first. Newer ones are also reported unsupported, although AO's reader accepts them, because the knowledge conventions are pinned to version 8. When `.kb/config/manifest.json` pins `siteEngine`, it must pin 3.137.0 or that commit. A single-product KB that never enabled AO's site engine has no manifest; the pinned reader is then the only one, the check notes `ao_site_engine_absent`, and enabling the site engine later stales the bindings. Knowledge admission reads a scaffold manifest with no `siteEngine` entry, as AO's older scaffolds write, like an absent one; the model stage keeps its own pin check. A selected product root always needs its own pin. Other versions get a clear unsupported result rather than a guessed model.

- Frontmatter `connections` must be map-shaped; the check names sequence-shaped files. Keep assertions and concepts directly under their type or product folder.
- Typed connection fields such as `supports` link assertions to assertions. AO also accepts `supports` targets that are concepts or artifacts, and Rhizome currently returns a GraphQL error for that whole field on the assertion when any target is another type or does not resolve, so other valid targets on that assertion are not listed there. The assertion's links and backlinks still show every link.
- Structured model sources read YAML and JSON with a pinned profile. Tags, anchors, aliases, merge keys, multiple documents, duplicate or complex mapping keys, and unsupported numeric or date spellings produce a source-located diagnostic and no partial model. A model row assembled from overlapping account and product mappings is rejected with both source paths. Generated `reads_fields` is not projected.
- Calculated AO judgments are never recomputed. Saved analysis appears only as dated AO output.

## Positional records and links

Model records whose AO kind declares `key: null` have positional identity. Rhizome labels them positional, and their locators are bound to the host file's revision: any edit to that file, including insertion, reorder, or whitespace, makes an old positional link unresolved instead of letting it point at whichever row now holds the position. Keyed records keep their identity when rows are reordered. Use keyed records for links you intend to keep.

## Read-only behavior

`.rhizome/source-ownership.yml` declares AO KB's standard layout AO-owned: `.kb/`, `assertions/`, `sources/`, `concepts/`, `artifacts/`, `decisions.md`, `_moc.md`, `MOCs/`, `_improvements/`, and the same paths under every `products/<slug>/` root, whether or not that product is selected. Rhizome refuses native edits to those files on every surface. The editor hides Edit and shows the declared reason. GraphQL and HTTP capabilities report `canEdit: false` with that reason. HTTP edit sessions refuse field and source edits at staging and recheck ownership at commit, so an edit staged before the declaration changed is refused. CLI property edits, moves, renames, and heading renames refuse, including link repairs whose rewrites would reach an owned file from an unowned one. Agent surfaces (MCP, agent CLI, code mode) keep these operations plan-only. Ownership comes from the declaration, not from typing, so owned files with malformed frontmatter, untyped raw sources, and stale or failed bindings stay read-only.

This is an application boundary, not a file permission: AO skills and external editors still change the files, and Rhizome does not claim their edits passed AO validation. Add any other AO-authored location your KB uses; never add unrelated notes. Re-running init keeps your edits. Removing the add-on keeps the declaration; delete it explicitly to end the protection. Change knowledge through AO's `/ao-kb:process`, `/ao-kb:curate`, and `/ao-kb:suggest` skills. The setup skill never invokes AO ingestion, curation, generation, or publishing.

## When to refresh bindings

| Change | What to run |
| --- | --- |
| AO edits to notes or model rows, including added, deleted, or reordered records | Normal indexing; the running Rhizome runtime picks these up. The index receipt expires and bindings stay ready. |
| Metamodel or project override (account or product copy), product registry or markers, site-engine pin, product selection, ownership declaration, artifact phase folders | `rzm ao-kb refresh-bindings`, then the index wrapper. The check reports stale bindings until then. |
| Note includes | No refresh; rerun `rzm init` so the managed guidance block matches. |
| Starter upgrade through `rzm init` | Refresh and index, then run both checks. |

## Recovery

- A failed refresh keeps the previous generated schema and marks its manifest stale; the check shows the AO error, such as a YAML parse error with its file. Wherever model data appears, the Knowledge views read both manifests and say when bindings are stale, incomplete, or unreadable, so the retained generation never reads as current. Fix the AO file, refresh, and run the index wrapper. Do not delete authored sources to repair bindings.
- `ao_index_inputs_changed` means AO files or configuration changed while the wrapper indexed: refresh, then run the wrapper again.
- `ao_refresh_locked`: remove `.rhizome/modules/ao-kb/bindings/refresh.lock/` only after confirming no refresh or index wrapper is running.
- A collision in `knowledge bindings`: retire or rename the named local types, then refresh.

## Release boundaries

Static knowledge types remain installed so views validate before setup. Before the first refresh, multi-product knowledge typing is unscoped and check reports incomplete setup with `rzm ao-kb refresh-bindings --product <slug>`. Generated admission then scopes knowledge and model evidence to that product. AO keeps knowledge at account `<type>/<slug>/`, or `artifacts/<phase>/<slug>/` and `artifacts/<slug>/`, rather than under product roots. Registered product folders determine scope; other notes select products through `products: [alpha]` or `["*"]`. Missing/null/empty-string `products` means shared, while `products: []` reaches no product. Unselected notes remain available to ordinary source search without satisfying selected AO evidence IDs.

A selected product's metamodel follows AO's precedence. AO's product commands copy the account's `.kb/config/metamodel.yaml` over the product's copy first, unless the product's `.kb/config/product.yaml` lists `metamodel.yaml` under `owns`, so the bindings read the account file in that case too, and an account metamodel edit takes effect on refresh. A product that keeps its own project override must own its copy; otherwise AO's next command replaces it, and the check notes `ao_config_mirror_differs` on the product file while the copies differ.

Install `uv` on PATH for the model adapter. Knowledge admission needs Node alone. Every check reruns the adapter offline to detect source compatibility errors separately from stale configuration. Prefix matchers cannot reproduce AO's `placed()` depth restriction for nested assertions/concepts. Keep those notes directly under their documented type or product folder. Admission compares frontmatter `products` values exactly, as AO does, and ignores inline `products::` fields. It matches the key case-insensitively, while AO reads only `products`; the check's `product tags` row names any note that spells the key otherwise. Adding or renaming an artifact phase folder changes admission scope and requires refresh; check reports `ao_artifact_phases_stale` with the changed folder set.

The optional toolkit stamp is `.kb/config/manifest.json`'s `toolkit` block (`version`, optional `commit`, `via`, `at`). It records the AO plugin that last scaffolded or synced the KB, not the version of every file or compatibility with the latest toolkit. Missing stamps are reported as unknown template age.

Saved AO analysis is read from `.kb/index/kb-weights.json` and displayed with `meta.asOf`. Missing or invalid analysis is unavailable; presence does not certify freshness, truth, or a clean KB. Rhizome does not recompute AO judgments.

## Re-init, removal, and ejection

Re-run `rzm init` to receive managed updates. Unedited managed files update; edited files are preserved and reported for reconciliation. Re-running unchanged init leaves managed bytes unchanged. Existing AO records and AO skills remain owned by AO.

`rzm init --remove-addon ao-kb` follows normal starter removal: unedited installed assets are removed and edited assets are preserved. `rzm init --eject ao-kb` keeps installed files and ends their management; `rzm init --restore ao-kb` resumes it. Generated schemas, views, manifests and source ownership are outside init's managed-file inventory and remain through ejection and add-on removal; review these explicitly when removing a projection. Neither operation migrates or deletes AO-authored knowledge. Re-run the checks and indexing after any binding update.

For generated view contracts, pinned compatibility limits, staged publication and recovery, read `.rhizome/modules/ao-kb/bindings/README.md`.

Bindings do not depend on `.rhizome/config.yml`, so indexing that rewrites it does not make them stale. If AO files or configuration change while the wrapper indexes, it reports `ao_index_inputs_changed` and issues no receipt; refresh bindings, then run the wrapper again. A later authored edit expires the receipt while compatible bindings remain ready; normal indexing refreshes those values.
