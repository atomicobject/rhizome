# AO KB setup

Use the repository's Rhizome launcher for every command below. Run from the vault root, which must be the AO KB root (the account root for a multi-product KB). Keep AO knowledge and model authoring with `/ao-kb:process`, `/ao-kb:curate`, and `/ao-kb:suggest`. Never run AO ingestion, curation, generation, or publishing during setup.

1. **Install.** `rzm init --add-addon ao-kb`, or `rzm init --addons ao-kb` on first init. Init installs static assets and the binding compiler. It declares no source ownership: AO KB notes are edited through Rhizome like any other note, and AO's own skills keep editing them too. It runs no project-specific compiler. `rzm init --check` checks managed files only.
2. **Trust.** Module actions run only in a trusted repository. If `rzm ao-kb check` is refused as untrusted, ask the user to run `rzm trust` in the repository; it is interactive, so never run it for them. Until then, `node .rhizome/modules/ao-kb/scripts/check.mjs` prints the same check.
3. **Check.** `rzm ao-kb check` reports named rows. Knowledge: AO root `.kb/config/vault.md`, schemaVersion (8, or absent, which reads as current as in AO; a single-product KB at 4 through 7 reads knowledge through a legacy spelling adapter, with the model stage `not applicable`; a legacy product-mode account, or anything older or newer, is unsupported and AO's own migration is the upgrade path), product mode, toolkit stamp, note includes, source ownership, knowledge bindings, sequence-shaped frontmatter connections, and saved analysis. Model: compiler dependencies (`uv` on PATH supplies Python and AO's pinned kb-site package), model bindings, model index, and model source ownership. Below schemaVersion 8 the compiler dependency and model bindings rows report `not applicable` with the reason, and uv is neither needed nor looked up; do not install it for a legacy KB. A fresh installation reports incomplete bindings and the exact refresh command. Resolve root and version errors before refresh; install uv on PATH for the model stage. If `knowledge bindings` is `error` because local schema types collide with the starter's (for example lowercase `assertion`/`concept`/`source`/`artifact` in `.rhizome/ontology/`), stop and ask the user whether to retire or rename them; they are the repository's own customization, and the starter's types replace them.
4. **Includes.** Note includes must cover `assertions/**`, `sources/**`, `concepts/**`, and `artifacts/**`, plus the exact `.kb/curation/_conflicts.md`, or `.kb/curation/*.md` when the folder holds other curation documents (registries, logs, reports), which the check then requires: in product mode also include `products/<selected>/.kb/curation/*.md` for the selected product’s curation documents; discovery skips hidden directories unless an include names the path. Append only what is missing and keep unrelated rules. If `notes.includes` is absent, discovery already covers all Markdown; a first list replaces that default, so start it with `**/*.md`.
5. **Ownership.** The `source ownership` row reports what `.rhizome/source-ownership.yml` does now. An installation from before editing was enabled still carries the starter's former read-only declaration; the row says so, and the refresh in the next step lifts exactly those former AO KB paths while keeping entries other tools declared. A repository that wants AO's tools to be the only writer of some paths declares them itself; never add such an entry on the user's behalf.
6. **Refresh bindings.** `rzm ao-kb refresh-bindings --product <slug>` for a multi-product KB (the product is required and persisted), or `rzm ao-kb refresh-bindings --single true` for a single-product KB. Later refreshes reuse the selection. Its output is the check's computed state. Below schemaVersion 8 refresh publishes knowledge bindings only and records the model stage as `not applicable`; the check then reports `bindingsReady` with `modelReady: false`, and the requirements on model rows below do not apply. `--toolkit <absolute path to packages/kb-site>` selects a local AO checkout at the pinned revision. A single-product KB that never enabled AO's site engine has no `.kb/config/manifest.json`; refresh proceeds with the pinned reader and the check notes `ao_site_engine_absent`. Knowledge admission also reads a scaffold manifest with no `siteEngine` entry, as AO's older scaffolds write, like an absent one; the model stage keeps its own pin check. Knowledge admission publishes independently through Node. A model dependency or compatibility failure keeps the current knowledge scope and previous model generation, and reports model setup incomplete. Then rerun the check: model bindings must be `ok` before indexing. Its state names the problem: `dependency missing` (install uv or let refresh download AO's pinned packages), `duplicate IDs` (the AO source must make each ID unique; report it rather than editing AO files), `stale` (refresh), or `error`. Then make the check's `note includes` row `ok`: it names every compiled model source no include covers (structured sources need an include naming their extension; `**/*.md` does not activate them). Append exactly those entries and preserve unrelated rules. Changing includes does not stale the bindings, but it changes the managed guidance block, so rerun `rzm init` before the final `rzm init --check`.
7. **Index.** `node .rhizome/modules/ao-kb/bindings/cli.mjs index` runs real indexing, verifies model record counts at schemaVersion 8 (below it there is no model to verify), and writes a receipt signed over the model sources and every file the Knowledge site reads, so editing, adding, or deleting a map of content, submission, curation document, or underscore-named artifact asks for a new index. If it reports `ao_index_inputs_changed`, AO files or configuration changed while indexing; refresh bindings and run the wrapper again (no receipt is issued for changed inputs). Then prove the knowledge projection with `rzm agent ontology-query --query '{ assertion(first: 1) { title } }'`.
8. **Knowledge site.** Once index ready, the Knowledge group opens on KB overview and the Knowledge panel shows at the bottom of the Notes sidebar for Knowledge subjects; a legacy KB gets the same site. When you describe a page, a count, or a label to the user, use the label's meaning from the guide's "The Knowledge site" table, which says exactly what each label claims (a kind group is not a judgment, stored confidence is the recorded value, a hollow date comes from the file name). A "not enough to draw yet" state or an incomplete-count note reports the KB's data, not a setup failure.

Report three states separately, with evidence: **starter installed** (`init --check` and the check's `starterInstalled`), **bindings ready** (`bindingsReady` from the check, never the saved manifest alone; for a legacy KB, say the model stage is `not applicable` and name AO's migration as the way to enable it), and **index ready** (the check's verified receipt plus a typed knowledge query). Include the source ownership row, the selected product, and saved analysis's `meta.asOf` or unavailable state. Neither `init --check` nor the check action alone proves a usable projection.

In a multi-product account, static knowledge typing is unscoped until the first successful admission refresh. AO knowledge stays in account `<type>/<slug>/` and `artifacts/<phase>/<slug>/`; shared type-root notes follow `products` selection. Unselected knowledge remains searchable as ordinary notes. Ordinary authored edits need normal indexing; metamodel/config/selection changes require binding refresh.

For direct CLI instructions and lifecycle behavior, read `docs/reference/guides/ao-kb.md`.
