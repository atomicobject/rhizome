## Init setup and template refresh

`pkg/app/cli/init` owns `rzm init`: config detection/writes, agent-surface mode resolution, managed agent docs, workflow starter scaffolds, starter ontology schemas, command-backed prompt/command artifacts, skills, and the one ownership rule for generated files.

- **Entry points**: `Run`, `DetectLayout`, `planAgentSurfaces`, `planTemplateScaffold`, `renderRhizomeMd`.
- **Starters (four)**: `core`, `agentic-engineering`, `complex-domain`, `action-items`, each a `templates/starters/<id>/` directory. `core` is the shared Person/identity base; `agentic-engineering` requires `core` and default-activates `action-items`; `complex-domain` requires `agentic-engineering` (transitively `core`); `action-items` requires `core`. `spec-driven` is accepted only as a bounded migration input. Installs combine via metadata-driven resolution.
- **Source layout by destination**: each starter groups assets under `repo/` (written into the target repo at the same relative path, today only `docs/**`), `rhizome/` (`ontology/<id>.graphql`, `query-recipes/`, `views/` → `.rhizome/`), and `agents/` (`skills/` → `.agents/skills` and `.claude/skills`, `AGENTS.md` → managed template block, `skill-overlays/` patching other starters' skills; only `complex-domain` ships overlays). Each family has a dedicated `loadStarter*` loader. A missing family dir yields no files; `TestStarterDirectoriesGroupAssetsByDestination` rejects unknown entries.
- **Guidance composition**: the shared Rhizome skill owns proportional retrieval, evidence authority, safe authoring, validation, and degraded-operation behavior. Agentic Engineering owns delivery phases and authorization continuity; Complex Domain adds source, requirement, process, workflow, and traceability behavior through its own skills, recipes, and the additive alignment/reconciliation overlay hooks.
- **Key invariants**: fail before any init write when `.rhizome/config.yml` is malformed or has an invalid known-field type; warn and preserve unrelated unknown keys. Before normal init, losslessly move the v0.49 `workflowTemplates`, `workflowTemplateAddons`, and `workflowTemplateManagement` keys into `.rhizome/workflows.yml`, remove only those three legacy keys, and update managed ignore state; retries must be idempotent. Normalize legacy `spec-driven` selections, dependencies, fences, and fingerprints to `agentic-engineering` before ordinary resolution. Install replacement assets before retiring legacy files; remove only files proven unchanged by the shipped fingerprint catalog, retain modified or unproven process docs for explicit reconciliation, and commit canonical workflow state atomically so failures replay safely. Preserve user prose outside managed fences; reject template/skill collisions before writes; starter docs refresh only when requested; starter-doc update availability comes from embedded-source fingerprints, not local doc diffs; ontology schemas keep their source filenames and merge under `.rhizome/ontology/` rather than overwriting a shared `schema.graphql`; starter-owned query recipes and views install under `.rhizome/query-recipes/` and `.rhizome/views/`; prompt target dirs currently reuse `templates/commands/*`.
- **Binary-manager migration is explicit.** `--binary-manager external` records provider-neutral external ownership, skips the default Rhizome pin and repository binary bootstrap, and preserves an existing valid selection on later init runs. Clearing conflicting Rhizome-managed pin/path fields appears in the rerun change list, so the rerun's one confirmation covers it; without a terminal the flag is the confirmation. Cache contents remain untouched.
- **First run** (`first_run.go`): one findings screen, the workflow question (three choices), a semantic search key only when Voyage AI (or the chosen provider) has none, and one confirmation (`e` opens settings), then an offer to build the index (default yes) through `RunOptions.IndexNow`; reruns offer to update it only after applying changes, and runs without a terminal never index. Semantic search is enabled only with a usable key; off on purpose is recorded as a provider with `enabled` unset. Agents come from repository markers plus `claude`/`codex`/`cursor` on `PATH` (stored as `on`). Without a terminal the same recommendations apply with the Agentic Engineering workflow. The Atomic Object key is mentioned only when the binary bundles team keys (`credentials.Session.OffersTeamKey`).
- **Machine first runs** (`first_run_json.go`, `first_run_options.go`): `Plan` (`--check --json`) and `Apply` (`--json`) run a first run without asking or printing and return one document (`SetupSchema`) built from the same display functions the terminal prints with; both refuse a configured folder (`ErrNotFirstRun`). First-run options `--addons` (listed add-ons enabled, unlisted default add-ons disabled in `workflows.yml`), `--skip`, `--keep-indexed`, and `--search-key-stdin` (saved through `saveKey` after skip detection has run `git`, because saving exports the key to the process environment; never printed; refused with `--check`) fail before any write. `--agents shared` writes AGENTS.md and shared skills without a harness, which the desktop sheet sends when no agent is checked. A failed pinned install is reported in the result because the setup was written. The desktop setup sheet is built from these documents ([[desktop-repository-setup|SPEC-0118]]).
- **Index scope** (`scope.go`): `ReadScope` and `ChangeScope` back `rzm index scope`. A first run plans `.rhizome/ignore` with the same transforms `apply` writes with (`plannedIgnore`: the built-in list before the first rule, `withIncludedSubtrees`, `withSkipChanges`), so planned rules equal written ones. `ChangeScope` applies every edit in memory and writes once, atomically; removing a suggested skip drops its reason line and writes a keep line.
- **Reruns** (`rerun.go`, `settings.go`): `initRun.resolve` computes the final config and classifies every generated file without writing; `apply` writes generated files, then config. A rerun prints the setup summary and a change list: setting changes, suggestions to remove notes or code folder limits that miss content, a missing embeddings provider, the version pin, generated files, and `.rhizome` support files. Suggestions (semantic search once a key is available, a workflow's new default addon) join the list only in a terminal; batch runs list them and leave them, and `--check` does not count them. In a terminal one `Apply? [Y/n/s]` covers everything; `s` opens the four-section settings menu. `--check` prints the same report and returns `ErrChangesPending`. Moving away from a workflow in settings asks to remove or eject it; choosing a workflow again restores it. A recorded `.rhizome/workflows.yml` with no templates means no workflow, so leftover starter docs never re-infer one. An ejected starter's dependencies are frozen with it (`frozenStarters`).
- **Index scope**: first runs write no folder limits: notes cover all Markdown and `code: {enabled: true}` covers every supported language (`applyFirstRunDefaults`, `enableAutomaticCodeScope`; see the code-intel subsystem note), so `.rhizome/ignore` is the only way content stays out. For configs with folder limits, or with code off, reruns suggest removing the limits or turning code on (`notesLimitDrift`, `codeDrift`), ignoring content init proposes to skip; suggestions apply only after a person confirms, because a limit may be deliberate. The managed AGENTS.md block says "whole repository" or names the limits.
- **Skip suggestions** (`skips.go`): `detectSkips` proposes tracked (`git ls-files`), detected, indexable files under a vendored, generated, or test-fixture folder name, minified or bundled files, generated-code files (suffix or a `Code generated ... DO NOT EDIT` first line), and files over 1 MB. First runs show them in a Skip row; reruns and `--check` list them; confirming or a non-terminal run writes them under `# rhizome: suggested skips` in `.rhizome/ignore`, one reason line per entry. `# rhizome: keep indexed <path>` stops a path from being proposed; settings can skip a path or stop skipping one. Ignore semantics are unchanged: these are ordinary anchored patterns that `rzm index --explain` reports by line.
- **Generated files follow one ownership rule.** `planAgentSurfaces` and `planTemplateScaffold` build a `filePlan`; `applyFilePlan` classifies each target (missing, current, unedited, edited, local-only, unknown) against `.rhizome/generated-files.yml` and writes, keeps, or removes it. Missing and unedited files need no decision. Edited files are asked about only through a terminal UI (`terminalOwnershipUI`), one question per mirrored group; without one they are kept and listed, and no declined version is recorded. Unrecorded differing files share one grouped question, except managed blocks, which count as Rhizome's. The record replaces the retired `.rhizome/template-rejections.yml`, family update policies, source fingerprints, and per-skill `.rhizome-managed` / `.rhizome-managed-files`, which the first run folds in and deletes. When a managed agent-doc refresh preserves any template block in place, the core Rhizome block keeps its existing position. Starter docs are created only; `--refresh-docs` applies the rule to them. Skill overlay fragments may name a skill-relative Markdown `file` (default `SKILL.md`); unknown files and slots fail closed. Ontology refresh preserves the installed preferred identifier's complete allocation contract (`strategy`, `prefix`, `separator`, and sequential `pad`) with gqlparser-backed source locations, `ontologyFingerprint` ignores those contracts, and init never performs an implicit rekey.
- **Starter metadata**: `templates/starters/<id>/template.yaml` is the source of truth for `id`, `name`, `requires`, `activatesByDefault`, and `installedAssetTypes` (documentary list of families). Keep resolver behavior metadata-driven rather than branching on starter names.
- **Starter resolution**: `.rhizome/workflows.yml` `templates` stores only explicit user workflow choices. `resolveTemplateSet` expands metadata `requires` and `activatesByDefault`; `resolveManagedTemplateSet` then applies `management.ejected` so adopted-but-unmanaged starters stay visible without being refreshed.
- **Addon state**: `.rhizome/workflows.yml` may carry `addons.enabled/disabled` for explicit addon choices. Required dependencies cannot be disabled; default addons can be skipped by listing them in `disabled`. Existing configs that predate addon state keep their explicit templates until someone accepts the rerun suggestion.
- **Management state**: `.rhizome/workflows.yml` may carry `management.ejected`. Ejection keeps installed files and existing managed starter blocks exactly as they are, including fence comments; it only removes the starter from future management. Optional default addons active only through an ejected starter default to ejected. Retired `management.updatePolicy` and `management.sourceFingerprints` are cleared by the next init.
- **Generated-files record**: `.rhizome/generated-files.yml` holds only fingerprints of what Rhizome wrote and versions a person declined, with sorted keys; an unreadable record is treated as absent. Do not store starter or config state there.
- **View starter family**: starter `views/` assets install to `.rhizome/views/*.yaml` and participate in the same preflight collision checks as ontology, query recipes, managed docs, and skills.

Installation adds explicit effort HTML includes, preserving configured Markdown and unrelated patterns. The shared Effort interface has no identifier allocator; concrete siblings share a compatible pool. On upgrade, adopted strategy, prefix, separator, and padding may propagate to a new sibling only through a matching shared-interface/upstream contract. Historical files are not rewritten. Canonical authoring and lifecycle rules remain in the starter templates.
