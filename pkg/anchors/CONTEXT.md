## pkg/anchors

Binds **vault notes → code** via code anchors (note frontmatter targeting symbols/call-sites/paths).

- **Entry point**: `Service.NotesForFile(ctx, path)` — which notes apply to this file?
- **Note ingestion boundary**: `ExtractAnchorDeclarations(ctx, NoteSource)` is the narrow adapter seam for note-derived code-anchor declarations. Do not add new general note metadata ownership here; consume canonical note facts from `notemeta`/orchestration.
- **Canonical source only**: production callers provide `notemeta.NoteSourceSnapshot` with a vault-relative path. Raw path/content ingestion adapters are intentionally absent; the degraded-mode watcher receives a snapshot factory from bootstrap to avoid an import cycle.
- **Format provenance boundary**: SQLite metadata now records source format and projection status, but this package remains a Markdown code-anchor adapter. Do not interpret, persist, or promote generic provider projections here; a provider-aware adapter is a later migration.
- **Requested-path availability**: global note-metadata readiness gates Store inventory reads. The internal durable-row seam exists for provider-aware `notemeta.Indexer` orchestration; SQLite does not independently decide whether a row is compatible with the active provider or currently note-owned.
- **Ownership-transition invalidation**: retiring note ownership returns every removed note-anchor association for cache invalidation, deletes only newly orphaned anchor rows/scopes, and durably marks the ownership generation pending. Phase 3 callers must rederive affected source paths and acknowledge only the exact generation after all lanes converge.
- **Key invariant**: anchors are note→code (live in frontmatter); write operations are serialized via shared mutex
- **Bounded startup reads**: `IndexedContextStore` exposes exact-file and directory-boundary-scoped code→note/rationale/resolved-edge reads, exact selected-note metadata, and an aggregate/limited persisted graph summary. SQLite applies target scope and hard result caps before materialization; callers must not substitute graph-wide reads plus in-memory filtering.
- **Bounded semantic reads**: directory note seeds use ordered `NotePathsByPathPrefix` with an explicit limit. Embedding search requires current metadata for a live chunk and the query dimension before KNN or scalar limits; retained vector rows cannot authorize reused chunk row IDs or previous dimensions. Vector bytes still supply scores. Search uses exact prefiltered vec0 `MATCH` KNN, deterministic chunk-ID tie ordering, and adaptive boundary probing; never post-filter a fixed global KNN window or recreate vec tables on a query path.
- **Chunk-content publication**: replacing an existing chunk with a different content hash retires its embedding metadata and ontology embedding sidecar before updating the hash, in the same transaction. Unchanged hashes retain their evidence; physical vectors and hash-addressed caches remain reusable. Provider failure leaves the changed chunk unavailable to vector search and eligible for retry. Previously stranded evidence has no recoverable old hash; explicit `rzm index --rebuild` regenerates it.
- **Embedding identity reads**: vector publication resolves chunk IDs once per bounded write batch inside the existing writer transaction. Missing chunks and empty vectors retain their skip behavior; metadata, vector bytes, owner partitions, and one generation advance publish or roll back together. Do not prepare row IDs outside the transaction, where chunk retirement could invalidate them.
- **Indexed ontology summary**: startup summary reads schema readiness/materialization, note totals, and bounded authored resolved-type counts/examples from `ontology_note_types`. Do not derive public type names from `ontology_nodes`, which also contains internal fallback catalog nodes.
- **Code publication**: live indexing and queued batches share preparation and persistence. SQLite publishes summaries/meta, refs, external evidence, Intel, and rationale in one transaction; doc links retain their separate publication seam. Generic stores publish supported artifact families before summary/meta freshness, propagate failures, and attempt all three reverse-index families with joined errors. They do not provide rollback. Invalidate file context after publication attempts, including partial-error returns, so a completed read during a write cannot leave old rows cached after publication returns. Cache misses capture one global generation under the existing cache mutex; per-file and whole-cache invalidation advance it even when the cache is empty, and a late read only caches its result when that generation is unchanged. The in-flight read can return its prior observation. Unrelated invalidation may discard a valid cache fill, without extra persistent state. `IndexerVersion` v1.16.0 makes normal reindexing repair older live publications that falsely advanced freshness.
- **Rationale schema ownership**: Rationale FTS tables, rowid mappings and indexes are established and validated at store initialization. Search, replacement and deletion do not create schema; atomic persistence rollback includes canonical rationale, FTS and mapping rows.
- **Batch-store ownership**: when `ApplyCodePersistenceBatch` is available, it owns summary/meta durability too; avoid pre-writing file summaries/metas on that path or code batches double-write the hottest tables.
- **Live preparation**: pre-resolved paths retain their identity, unchanged sources skip parsing and publication, and live work omits unused definition-delta reads. Capture old dirty-scope relationships before publication and mark old/new relationships plus post-write ancestry only after success. Public queued preparation publishes tail hints before writer handoff; private live preparation leaves the single hint update to publication. Hand-built work remains supported by the writer.
- **Batch intel edge policy**: live indexing resolves call/import/type/member edges eagerly; full batch indexing persists anchors/FTS/defines eagerly but defers store-backed edge resolution to the later rebuild pass; avoid reintroducing per-file resolver lookups on the hot ingest path.
- **Same-run fresh state**: during unified indexing, freshly computed `CodeIndexWork` refs/anchors may flow forward in memory for rebuild/scope work before sqlite readback; treat sqlite as the durable boundary and fallback for untouched paths, not the default rendezvous point for just-computed rows.
- **Scope lookup path**: call-file lookup is now a read path plus runtime cache merge; do not move `CallFilesByCallees` back under the shared write lock unless the semantics truly require write-serialized temp state.
- **Indexing perf**: `BuildCodeIndexWork` now emits separate `codeindex.hashcheck`, `normalize`, `doclinks`, `rationale`, and `process.code` timings; use those before guessing at the remaining `index_code` wall.
- **Semantic overlap**: full-scan code embeddings can now prepare from fresh `CodeIndexWork` before intel persistence completes; reverse-index/call-edge rebuilds still stay behind the durable post-write path.
- **C# indexing**: `ParseRecovered` is trusted for reverse-index + intel writes. C# emits imports, type refs, ctor/object-creation edges, member refs for static/value reads, fields/properties/events/indexers/delegates/operators, and lightweight typed-receiver call edges.
- **C# resolution**: file-local `using` plus nearest-`.csproj` explicit `global using` aliases feed nested-type resolution, `typeof`/`nameof`, and static-container refs such as `LegalStatuses.Pcs.Active`.
- **C# limits**: recovery is syntax-local (modern collection-expression shapes); no Roslyn semantic model or ambiguous-import disambiguation. Instance property reads stay conservative, target-typed `new()` only resolves in cheap explicit contexts, and generated `*.Designer.cs`/auto-generated files stay intentionally thin.
- **TypeScript/JavaScript formats**: treat `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, and `.cjs` as one centralized source family across discovery, watcher routing, parser dispatch, coderefs, and reports. Keep TypeScript and JavaScript grammar selection explicit.
- **TypeScript/JavaScript resolution**: repository-local literal module resolution is filesystem-only, cached outside persistence, and root-confined. Preserve NodeNext source substitution order, local package `exports`/`imports`, nearest tsconfig/jsconfig aliases, and explicit barrel bindings; retain ambiguity instead of choosing nondeterministically.
- **TypeScript/JavaScript precision**: emit relationships for static ESM, side-effect/re-export forms, literal dynamic imports and requires, and statically enumerable callable branches. Do not invent same-file member edges for unknown receivers or resolve computed/runtime module sources. See [[typescript-javascript-indexer-coverage]].
- **External target boundary**: `intel_symbol_ref_targets` remains raw parser identity. Canonical pathless external targets use a separate N:1 catalog mapping; sparse per-association evidence (including a separate external-import family) derives classification only after local resolution wins. See [[docs/specs/technical/external-code-reference-targets|SPEC-0081]].
- **External persistence boundary**: qualifying indexers set `ExternalEvidenceReady`; the queued code batch replaces natural-key evidence only after raw refs are durable in the same transaction. Ready+empty clears stale evidence, while not-ready skips the classifier batch and avoids external temp-table work for unsupported languages; parse failures never replace refs/evidence.
- **External isolation**: external catalog/evidence writes stay batched behind the unified SQLite writer. External rows are never source-backed anchors, chunks, FTS/embedding/search documents, ontology nodes, default graph nodes, Explorer entries, or definition targets; only explicit external-reference/impact surfaces may project them.

### Web graph cache freshness

`sqlite.GraphWebFingerprint` reads a persisted graph-domain incarnation and revision. Intel migration v62 installs transactional triggers for graph-relevant inputs, including endpoint type and score data; external evidence does not invalidate the ambient graph. New graph read dependencies must extend trigger coverage and cross-handle cache tests. No connection is reserved and no read performs repair.

Schema v62 is forward-only. Older binaries reject it. Rollback requires stopping every Rhizome process and restoring a pre-upgrade index or explicitly rebuilding derived state with the older binary after moving the database and its sidecars aside. Never automatically downgrade or replace a live database.

Graph document and anchor score replacements prepare arguments and check cancellation before the writer lock, then use bounded multirow SQL inside one transaction, preserving input order, duplicate last-write behavior, blank-key filtering and trigger-driven graph revisions. Chunk failures roll back the initial delete, all score rows and revision together.
