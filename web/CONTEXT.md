# Web UI data lifecycle

React/Vite browser for Notes, Ontology, Explorer, Agent, and GraphQL. Server state uses TanStack Query. The app-level edit provider owns route-independent draft/session state; focused controls own selection, focus, and composition.

## Ownership

- Internal fallback note and section types are navigation identities only. Use `publicTypeName` for type labels and badges; preserve raw types in node refs and query/edit contracts.

- Shared chrome: `AppShell` and `base.css` own the compact global header across every route. The editable project-search field submits through Rhizome's ranked search and opens a retained search tab; drafting text alone does not run a query.
- Atlas: the type index searches navigation choices without removing graph nodes. Focusing a type emphasizes its direct connections and centers its readable card; card links open type details. ELK and cards share fixed header, row, padding, and border geometry. Preserve ELK port choices and routes; endpoint adjustments must move adjacent bends to keep routes orthogonal.
- Query cache: API-derived reusable reads only. Keys include every response identity: type/interface, path, session, search, view id/state, graph scope, and edit-session fingerprint.
- Local state: route-independent drafts, directory expansion, tab identity and order, temporary search, paging, focus, drag state, and explicit GraphiQL execution. Meaningful view selections and display choices use the shared personal preferences client and ignored server store ([[view-preferences|SPEC-0114]]).
- Notes shell: `NotesShell` coordinates layout and the existing edit session; `useNoteTabs` owns the vault-scoped Home, collection, note, search, and view tab set, with one retained `view:<id>` tab per configured view id. Problems has a stable reusable collection tab that retains its scope and selected issue while inactive; Changes is available only while the edit session has uncommitted changes. Search tab ids are stable while query/filter request identity may change in place, and the stable `searchTab` URL id lets Back/Forward restore that same tab. Retained panels, note drill state, local filtering, and TanStack Query pages stay mounted across tabs and app routes. Inactive note, search, and graph queries are disabled. Each mounted `NoteTab` owns one `usePaneStack` for node drill history and request generations; switching tabs preserves that history. Each tab retains its focused fragment; explicit navigation updates it, and resolved stable refs replace the current URL without adding history. Deep-linked nodes retain a cached file-root pane. `nodeEventHub` shares one node-event connection across the union of subscribed canonical refs.
- Rails: `NotesLeftRail` owns collections and one immediate title/path/type filter for its independently scrolling note list. It does not issue project searches. Display groups and parents organize the left-rail presentation only; type and interface counts retain their query semantics. Declared interface parents remain available even with fewer than two implementors. Embedded implementors appear as disabled children, while standalone embedded types stay out of the rail. Every rail row shares a fixed 18px caret gutter per depth (an inert spacer when it has no children) so same-depth labels align, a group header is a caret button that toggles expansion beside a label button that opens the group workspace, with its children one depth below it; group workspaces hide the note list; and `activeCollection` — not `selectedType` — drives the selection highlight. `NotesRightRail` reads the active note tab's focused workspace and outline callbacks; only its Graph tab requests the local graph. When no note tab is active, the active collection view's selected record renders into the rail through `RecordRailPortal` (`recordRail.tsx`): the view keeps its own rows, capabilities, and edit session, and the rail only provides the slot. While a table shows, it holds the rail open, with a placeholder until a row is selected, so selecting a row never reflows the table under the pointer. A click on a table row or its title selects the record for the rail; Enter, double-click, Cmd/Ctrl-click, and the record's Open action open the note, and F2 edits an editable title. The rail's record list starts collapsed while the Home tab shows a type or interface collection view other than Overview. Both rails are omitted while a search tab is active. Session state remembers context collapse and the selected context tab.
- Home: `HomeTab` hosts collection surfaces and resolves their choice through the shared view selection; types and interfaces open their generated view's default layout (Table, or Board by the shape rule) unless an authored default exists, and offer the bundled Briefing as their first choice instead of Overview ([[type-collection-views|SPEC-0112]]). All notes resolves the catalog's `workspace` target with context `{ kind: "workspace" }` and has no built-in view: if the catalog fails it shows an error with retry ([[scope-overview|SPEC-0117]]). Groups take their views from the catalog; the built-in navigation list, labeled "Types", appears only while the catalog cannot load, and the built-in type Overview likewise. A remembered Overview choice for a type resolves to the default. While the type fallback is selected, `HomeGraphLayout` keeps one global graph at a stable React position across type/interface selections, including delayed type reads, under `NotesTypeHome`'s information band. Graph loading, errors, and retry are independent of collection data; cached graph renderers remain mounted during refresh failures.
- Configured views: `ConfiguredView` owns the shared shell and passes one renderer contract to the table, board, and cards presentations. Board moves build one field operation and stage it through `onStageOps`; renderers never write notes directly. Manual ordering (SPEC-0108) lives in `viewOrdering.ts` (pure placement) and `useViewReorder.ts` (drag, drop, and Alt+Arrow state shared by the table, cards, and board): when the effective sort leads with an editable number, enum, or boolean field, a drop stages that drop's `setField` ops in one `onStageOps` call, and renderers re-sort each group by the staged values until the view re-executes. The variant comes from the selected view choice; filters, grouping, sorting, and paging remain controlled execution state. For type and interface sources (SPEC-0112), the facet line reads `stats` and toggles ordinary filters, the table loads more rows on scroll by growing one window from offset 0, and row density, visible columns, and column widths are durable preferences scoped to the view and concrete invocation. Applicable filter, sort, and grouping state is shared across native variants; renderer layout and expansion keys stay distinct. Preference hydration precedes dependent native queries. Columns no matching row fills hide unless the reader filters on them or re-shows them; re-shown columns are stored apart from the column set so the other empty columns keep following the data. Bulk edits build each row's operation with the same `editOpForCell` path as a cell edit and stage the batch in one `onStageOps` call.
- Reading and editing: `NoteTab` resolves Structure/Markdown and custom node presentations through the shared view selection, remembered through the shared preferences service per vault and canonical node. `OntologyNotePane` owns the compact toolbar and scrolling body. Browse-mode Markdown renders authored Markdown read-only; edit-mode Markdown sends one witnessed full-source operation and protects frontmatter, headings, block IDs, and links that require structured operations. Non-Markdown notes use format-specific Preview/Source labels. `FieldEditor` selects controls from each owning field's server capability. All writes still pass through the ontology edit session.
- Browser location: one `useSyncExternalStore` adapter; navigation writes history then notifies the adapter. The `view` parameter addresses an active view tab; note and search URLs no longer carry it. Search URLs carry the submitted query, effective kind/type/folder filters, and stable retained-tab id. Initial vault hydration restores untouched stored tabs while honoring tabs closed before status arrives; v3 tab storage migrates the prior v2 note/search shape when needed.
- Edit staging: `src/staging/` is the one home for reading staged edits. Any server read whose answer changes with staged edits uses `useStagedQuery` (`stagedQuery.ts`), which keys by session fingerprint, sends the session to the API, and holds the previous same-subject result during refetch. Any question about what the session stages for a node (changed fields or collections, touched, staged value, counts) goes through `stagedState.ts` with a `StagedTarget` rather than reading the session's `ops`, `changedFieldsBy*`, `touched*`, or `collectionChanges` fields; the Changes review surface still edits the op list itself. The session fingerprint changes only when the server acknowledges session state (its revision); reads never send a session the server has not acknowledged. Conflicted sessions keep their staged read overlay until resolution. API wrappers reach staged routes through `stagedRead`: GET for committed state, POST with the same query parameters plus `{editSession}`. `usePaneStack` keeps its request generations but follows the same fingerprint: when it changes it reloads every pane the previous or current session touches, so callers never refresh panes. A successful save calls `forgetCommittedStagedReads` before the session clears. The controller also publishes `readLifecycle` with a new revision and display-only submitted operations. View reads key by that revision so only a successful request issued after persistence can release the saved display overlay. `useStagedQuery` returns `displaySession`, `displayData`, and `savedEditsPending`; these retain optimistic placement and the last same-subject raw data across pending or failed canonical reads. Each reader combines only saves it has not yet adopted, then overlays newer dirty edits. Display sessions never go to the API. Discard clears dirty edits while readers awaiting canonical data retain their saved overlay; readers that already adopted it remain clear. Failed or conflicted saves retain dirty edits and expose their outcome.
- API boundary: generated OpenAPI/GraphQL types stay authoritative. Read wrappers accept `RequestOptions.signal`; HTTP failures use `ApiError`.

## Invariants

- Personal view preferences belong to `.rhizome/user-state.sqlite`, separate from shared `.rhizome/views/` YAML, staged content edits, and the disposable index. Native clients use `useScopedViewPreference` and the aggregate `useViewPreferences`; custom views use kit `useViewPreference` or subscribed `getViewPreference`. Scope includes view ID and concrete context with optional host `slot`; the public kit's authored `options.slot` becomes a nested `widgetSlot` and preserves that host slot. Accessor reset removes its exact key; the host's `resetFamily` clears its base and persisted child widget scopes, including unmounted widgets, without crossing another host slot. Selection is target-scoped. Preserve canonical node identity and omit mutable offsets.
- Defaults never autosave. Invalid preferences fall back with a visible error, failed optimistic writes retain unsaved values and visible errors with retry, and reset removes overrides to follow current authored defaults. Atomic named-key patches preserve unrelated changes; acknowledge legacy import before clearing its source, and never resurrect reset state. Matching mounts synchronize after acknowledgment and refresh on focus/reconnect.
- Ordinary view interaction remembers personal settings without writing YAML. Explicit shared save presents what it will publish, includes temporary search only by explicit choice, and clears only promoted overrides after success. Widths and expansion choices survive, including a generated-to-authored ID transition. Group expansion keys include grouping-field identity and stable group identity so content refreshes cannot reset unchanged groups.

- Never render data under a different subject than its query key. A staged read may hold its previous same-subject result while a refinement or the edit session refetches, with a visible refresh marker (SPEC-0074).
- Same-key cached data may remain during background refresh; different-subject data must not masquerade as loading or empty state.
- Initial loading, empty success, retryable error, and background refresh are distinct UI states. Read-only GraphQL POSTs honor initialization retries; edit POSTs are not replayed. `VaultInvalidationBridge` advances a shared index revision on index events and connection openings. Failed panes retry once per newer revision, including events received during a failed request, without needing an already-resolved node subscription. Before a target resolves, retries retain its public canonical locator, including structural fingerprints and node IDs. Initial object targets keep their note path and source fragment separate from this serialized retry identity.
- Public vault SSE is an invalidation signal. One app-level bridge invalidates typed key prefixes; it does not patch content. Global graph refreshes coalesce at a fixed five-second deadline from the first index event. At that deadline, cancel pending graph reads before invalidating, including first loads, because a response completed after an event may still contain older data. Active graphs get one corrective read per burst; inactive graphs stay dirty until observed. This can refresh a graph already read during the burst. Validation diagnostics and scope summaries are immutable within their published generation, so invalidation preserves their cached pages and active pagination requests. Refresh the validation envelope; a new published generation selects new query keys. Reconnection cancels pending global graph reads and refreshes all queries because a rebuilt database can reuse generation numbers.
- Node SSE stays keyed by the stable set of active canonical `NodeRef`s; loading state changes do not reconnect it. Pane reads are canceled when superseded, closed, deleted, or unmounted. Deletion also invalidates the request generation and clears both requested and resolved refs, so a late response cannot restore the body or subscription. Preserve `usePaneStack` request generations so late responses cannot restore obsolete content.
- Same-node background refresh preserves the mounted reading surface, scroll position, mode, and drill history. Different-node reads clear the prior identity; they must not show the prior body as the new node.
- Graph gestures: pinch (Ctrl+wheel on trackpads) zooms, dragging pans, and visible zoom/fit controls remain available. Ordinary wheel events neither pan nor zoom a graph and retain native page scrolling.
- Home type selection changes reducer emphasis only. Keep `highlightTypes` out of Sigma graph-construction dependencies, preserve global nodes/edges and camera state, and keep dimmed nodes hoverable and clickable. Legend counts come from the graph being rendered.
- Notes navigation uses one open contract: normal note links create or activate one retained tab per file and node identity (a root note and an embedded node in the same file get separate tabs), and Cmd/Ctrl links open beside without activation. Opening another file or node never replaces an existing tab. Within-note section navigation stays in the existing tab.
- Applying or removing staged operations refreshes the union of previously and currently touched notes (owned by `usePaneStack`); discard reloads canonical disk content. Stable operation IDs replace earlier values for the same target. Narrative and whole-document Markdown editors wait 300 ms after continuous input, allow one request in flight, retain only the newest queued value, flush on blur or navigation, and keep the original source witness.
- Edit snapshots and raw input drafts are scoped by vault path plus browser tab. Each raw draft is keyed by its canonical operation target and persists synchronously, including incomplete or invalid text. Discard clears only the active owner. Local operations and verified base documents persist before transport. Normal stage requests carry only changed operations; a single snapshot retry restores an in-memory session after a server restart.
- Save persists one immutable pending submission before its commit request. Retries and reload recovery resend the same request ID, accepted revision, canonical operations, and verified bases before newer drafts are staged. A successful result removes only the submitted boundary; later typing remains pending. Commit outcomes are `committed`, `unchanged`, `conflicted`, or `failed`; only the first two close edit mode when no newer draft remains.
- Mutations sequence writes to the same resource, recover after failure, and invalidate authoritative reads after success. Save ends Saving and releases the action queue at persistence acknowledgement; background invalidation does not delay subsequent edits.
- Successful commits return verified `refLineage`. A reader applies mappings only while retaining that saved display snapshot; canonical adoption retires its mappings independently of other readers. The controller maps queued and newer edits through the commit that completed after they were captured, while preserving operation IDs. It keeps no workspace-wide history of aliases that could rewrite fresh references after an external restore. Expected-field witnesses advance only for fields written by the successful submission; unrelated witnesses remain strict. Discard preserves mappings for saved displays still awaiting adoption.
- Browser-storage failure is non-fatal to successful server operations.

## Markdown editing contract

- The narrative editor is a Markdown source editor. It must preserve all authored text and unknown syntax unless the user changes that text.
- Atomic provides source-aware decoration and editing help for common Markdown, code fences, tasks, links, and WYSIWYG GFM tables. Editing a table cell may normalize the authored table source.
- Rhizome resolves wikilinks, aliases, local headings, block references, and normal Markdown links through vault metadata and note search. Ambiguous targets stay unresolved.
- Frontmatter, tags, inline properties, callouts, embeds, HTML, math, and unknown extensions are source-preserved. They are not all rich interactive widgets in the editor. Rendered note view remains the authoritative rich presentation.
- Images stay in source mode until Rhizome can resolve vault-relative assets and control remote loading. The editor must not send raw relative paths to the browser or load remote media without the product's content policy.
- A narrative draft stays local while it is dirty. Staging coalesces repeated changes by owned source block, commit flushes the latest draft, and replay fails closed on missing identity, stale source, or invalid UTF-8 ranges.

## Tests

- Exercise API reads and SSE through typed fetch and EventSource fakes in `src/test/`; keep real client parsing, query behavior, and graph modules in component tests.

- Unmount graph components before restoring WebGL fakes so Sigma teardown retains its rendering environment. Run `make check` and `make web-e2e` sequentially: both consume the generated embedded web assets.
- Prefer deferred-promise Vitest tests for request reordering, selection changes, collapse during load, and queued mutation state.
- Use Playwright for cross-route identity regressions such as Notes Specs and Explorer `notes/specs/`.
- GraphiQL remains imperative because execution is a user command rather than shared application server state.

## Custom view kit

`web/kit/` is the public surface for custom views and standalone tools ([[custom-view-apps|SPEC-0105]]), built by `vite.kit.config.ts` into `pkg/app/web/assets/dist/kit/v1/` after the main build, because that build empties `assets/dist`.

- **`/kit/v1/` is a versioned contract.** The module names in `kit/boot.js`'s import map and the exports of `@rhizome/kit` and `@rhizome/ui` are what agent-written views depend on. Add exports freely; a breaking change ships as `/kit/v2/`. The init skill `custom-views` documents this surface and must change with it.
- **`boot.js` owns the environment**: import map, theme, fonts, and Tailwind's browser compiler, from one classic script tag. The Go shell at `/views/<id>` and an authored HTML page use the same tag, so neither duplicates the import map.
- **One token source.** The build prepends the `:root` block of `src/base.css` to `kit/theme.css`, which maps those tokens onto shadcn's variable names. Do not copy token values into the kit.
- **The kit reuses `src/api/client.ts`**, so custom views and the first-party UI share request behavior. `@rhizome/ui` components keep shadcn's names and props on purpose: agents already know them.
- **Custom views are trusted, same-origin code** framed without a sandbox by `CustomViewFrame`. The isolated viewer host is for HTML notes only. Navigation and edit-session messages are validated for origin and the specific frame source.
- **Edit sessions**: `kit/editSession.tsx` bridges an embedded view to the workspace edit session over the messages in `src/lib/customViewMessages.ts`; `CustomViewFrame` is the host side. The host also sends `readLifecycle` with save/discard/failure/conflict outcomes. Kit reads reuse `useStagedQuery`, pass cancellation signals, and return `editOutcome` and `savedEditsPending`. `useGraphQL` and `useViewRows` accept an optional `optimistic(data, displaySession)` callback for query-specific display updates; it always receives raw server data, so repeated renders never apply the callback to its own output. Saved display edits remain until a successful post-commit request returns, while newer dirty edits take precedence. `useSetField(query.displaySession)` binds mutations to that reader's retained reference mappings; GraphQL edit refs include `structuralFingerprint`. Mutation invocation captures this scope before asynchronous work, and canonical adoption retires it for that reader. Views get no long-lived session of their own; `immediate` mode commits each write in a one-off session.
- **Freshness** (SPEC-0111): `VaultInvalidationBridge` publishes every vault stream event to `query/vaultEvents.ts`, and `CustomViewFrame` forwards each one to its frame as `rhizome:event`, so a hosted frame opens no stream; a standalone page opens its own through `openReconnectingEventSource`. `kit/freshness.ts` coalesces bursts (a trailing 150ms debounce with a 1s max wait, since each refresh cancels in-flight fetches) and invalidates by class in one call per flush: index and node events refresh data, schema events also refresh type documentation, validation events refresh the validation envelope and display groups, and a reconnect refreshes everything because missed events are not replayed. `views.changed` reloads a repository view whose own folder changed; for any other folder it refreshes data, since the vault watcher never reports `.rhizome` and the view catalog would otherwise go stale. Bundled views never reload. `kit/startView.tsx` attaches that reload path before the module loads, so a view that fails to load or mounts itself still reloads; a hosted frame compares the served folder stamp at startup and after each stream reconnect, and only standalone repository pages keep the folder-stamp poll as a fallback.

- **Source stamp checks**: `kit/startView.tsx` permits one active stamp read per view. Each read has a ten-second deadline covering both fetch and body consumption, and lifecycle cleanup also cancels it. Aborting releases the pending check and suppresses late results; completion clears its deadline and cancellation listeners. Standalone repository polls skip hidden pages and ticks while a read is pending, and advance the baseline only on success. Hosted startup and reconnect checks retain the served baseline and never poll; a reconnect during a pending check queues one follow-up that starts after the event, since a pre-reconnect response cannot cover missed source changes. Failed or expired reads leave later standalone polls and queued hosted checks available.

## Bundled views

`bundled-views/group/` holds the group views Briefing, Trace, and Sections (SPEC-0111) and the type Briefing (`type-briefing.tsx`, registered as `type.briefing` and `interface.briefing`; SPEC-0112). They share one folder because ejecting copies a folder and the two Briefings share modules. Its `README.md` ships with the views and is copied into a repository by `rzm view eject`, so it addresses a repository author; Rhizome-only development notes live here.

- `vite.kit.config.ts` copies the folder into `pkg/app/web/assets/dist/bundled-views/`, leaving out `*.test.*` files and `__fixtures__/`. To see edits without rebuilding, serve the folder from disk: `RHIZOME_BUNDLED_VIEWS_DIR="$PWD/web/bundled-views" ./bin/$(go env GOOS)/rzm serve`.
- Tests run with the web suite (`npx vitest run bundled-views`). They use the synthetic groups in `__fixtures__/groups.ts`, which answer in the server's response shapes, and the kit's internal `renderView` harness through `__fixtures__/harness.tsx`; `__fixtures__/collections.ts` adds what the type Briefing reads (reverse fields, a dated type, collection targets). Browser journeys live in `tests/e2e/group-views.spec.ts` over `tests/e2e/fixtures/group-views/`, and the type Briefing's in `tests/e2e/type-views.spec.ts`.
- The type Briefing reuses the group model as a one-member group (`collectionGroup`, `useCollectionModel`): the same pure derivations and blocks, plus `collection.ts` for spreads, months, and per-field fill. Its query reads reverse fields and inbound neighbors only, and its signals open the collection's Table choice by choice id, since opening the generated view's id lands on its default layout.
- The views take each member's lifecycle field, gap fields, and key text fields from the type profile, and each value's stage from enum documentation; they never guess from field names or tones. Fixture type documentation must therefore carry a `profile`, and an interface member reads the interface's own documentation, so fixtures include it.

## Shared view invocation

[[unified-view-contract|SPEC-0110]] makes Overview, native Table/Cards/Kanban, and custom HTML/TSX peers under one registration, context, configuration, lifecycle, and service contract. The host resolves catalog choices and supplies existing native renderers or an active custom frame; selection does not belong separately to HomeTab or ViewTab. Type collections, interface collections, display groups, and individual nodes have distinct subjects. Selection is explicit request, valid vault/subject-scoped preference, configured default, then built-in fallback; exact group defaults outrank generic ones. `ViewSelector` marks the default, and picking it clears the preference.

- `src/views/context.ts` owns `ViewContext` and `ViewModuleProps`. Definition applicability and concrete invocation are separate: a `"*"` mount receives the actual group. Node context retains concrete type and full canonical `NodeRef`, including embedded identity.
- `kit/viewContext.ts` exposes the server-validated invocation through accessors/hooks for TSX and HTML. Custom configuration comes from the authored definition, never a URL override. Context changes remount the frame, and inactive custom frames unmount to release connections and polling.
- The kit's `useViewRows` adapts the same `executePublicView` collection service used by native views, including capabilities/warnings and workspace-staged reads. Query identities include invocation context and edit-session fingerprint. Promise `executeView` reads committed state. Views must not duplicate the native executor or create an independent workspace session.
- `openNode`/`nodeHref` preserve canonical identity and an optional named presentation; `openView`/`customViewHref` preserve a concrete subject. App links use `presentation` for a node presentation, while `/views/<id>?context=...` launches the same custom page directly. Existing standalone links remain valid.
- Reopening an existing note without a presentation preserves its explicit request; a supplied presentation replaces it and explicit `null` clears it. Display groups organize navigation and registration, not query membership. A reusable bundled group page consumes the same context and services and needs no special route.
