# Rhizome Desktop

A Tauri 2 app for local Rhizome repositories and Markdown vaults. Every window has a toolbar in the app's chrome theme and a content area showing the selected worktree's own Rhizome runtime. The toolbar names the repository and worktree the window shows, each opening a fuzzy finder, and carries the workspace's section tabs and search. Adding a repository only inspects it. Trust and setup are explicit actions in the content area.

## Development

Install Node 22.12+, Rust, Go, and the [Tauri platform prerequisites](https://v2.tauri.app/start/prerequisites/).

```sh
cd desktop
npm ci
npm run tauri -- dev
```

The Tauri development and build hooks run `make build` (the workspace web UI, then `rzm`; `NO_WEB=1` skips the web build) and copy `rzm` into the app's sidecar slot; development then starts Vite. The app's companion is that `rzm`, run as `rzm desktop-bridge`. `npm run dev` starts only the shell frontend; native operations require Tauri.

```sh
npm run check
npm run build
npm run rzm
npm run test:native
npm run tauri -- build --bundles app
```

Native builds use the host platform. The `rzm` staging script rejects cross compilation because Rhizome embeds SQLite through CGO; with `RZM_DESKTOP_PREBUILT_RZM` set it copies that binary instead of building one, which is how a release bundles the exact `rzm` it archives. The macOS app is produced in `src-tauri/target/release/bundle/macos/Rhizome.app`. Release builds add `--config src-tauri/tauri.release.conf.json`, which ad-hoc signs the bundle and creates the signed updater archive; see [Releasing](../docs/RELEASING.md).

The selected runtime must support `serve --headless`. For a local development build, run `make build` from the repository root, then choose `bin/darwin/rzm` under Settings > Use an existing executable. Repository development settings continue to take precedence. Global executable overrides expect a native Rhizome binary; external-manager folders may use a launcher script through their folder options.

## Distribution and updates

[SPEC-0122](../docs/specs/technical/desktop-distribution-and-updates.md) owns this behavior.

- Every public release publishes `Rhizome-macos-arm64.dmg`, the updater archive and its signature, and `latest.json`, built from the same tag as the CLI archives. The app's version is the release version; the committed `0.0.0` marks a development build.
- The app contains that release's `rzm` and uses it as the global executable unless Settings selects another. Folders the app sets up therefore pin the app's version. Library version 3 forgets a `~/.local/bin/rzm` selection saved by the removed managed install, once.
- The updater reads `https://github.com/atomicobject/rhizome/releases/latest/download/latest.json` at launch and every 24 hours, downloads a newer release, and verifies its signature against the public key in `tauri.conf.json`. The toolbar then shows Restart to Update; the app installs only on that action, Rhizome > Check for Updates…, or `rzm update`, which launches the app with `--install-update`. Restarting reopens the windows; running runtimes keep running. Rhizome Dev and local builds (version `0.0.0`) never check.
- Settings > Install Command-Line Tool links `/usr/local/bin/rzm` to the bundled `rzm`, asking for an administrator password only when the directory is not writable. Deleting the app leaves the link dangling, so `rzm` stops running it. The app never replaces or removes an `rzm` it did not link, and reports which `rzm` the login shell finds first.
- A managed worktree whose pin differs from the app's version shows a toolbar offer. Update Pin runs the app's `rzm update --set-version` for that worktree and reopens it; Not Now hides the offer for that repository until a newer app version.

## Rhizome Dev

`make desktop-install-dev` builds a separate "Rhizome Dev" app from the primary checkout on `main`, with its own bundle identifier, app data, and an icon carrying a DEV badge. It also runs `make build`, then quits a running Rhizome Dev, replaces `/Applications/Rhizome Dev.app` (set `RHIZOME_DEV_APP_DIR` for another directory), and opens it. Linked worktrees and other branches are refused so unmerged work never replaces the installed app; `RHIZOME_DEV_INSTALL_FORCE=1` overrides the check. `scripts/icons.sh` regenerates both committed icon sets, `src-tauri/icons` and the badged `src-tauri/icons-dev`, from the SVG masters in `docs/brand`; small sizes use the simplified masters drawn for them.

## Opening from the terminal

`rzm desktop [path]` runs `open -n -a <app> --args --open <canonical path>` (macOS only). A running app receives the arguments through the single-instance plugin and the new process exits; otherwise the new process is the app and handles its own arguments after restoring the session. Only process arguments carry the request, never a URL scheme. A relative path is logged and ignored; a missing folder shows an error in the window.

The request goes to the most recently focused window (the first restored window when none has had focus yet), or to a new window when none is open, which is brought forward and the app activated. The app discovers the path's repository, adds it to the library when it is new (a worktree of a known repository merges into that entry), and picks the deepest configured worktree containing the path. A Git worktree root, or a folder beside a subfolder vault, opens that Git worktree's vault when the vault's repository is already in the library. The shell then selects that repository and worktree exactly as choosing it in the repository finder would, with a fresh selection number, so it outranks any earlier pending selection and the usual trust, seeding, and setup steps apply. When nothing matches, the window shows the error and keeps its selection. For a smoke test, pass `--env RHIZOME_DESKTOP_DATA_DIR=<absolute dir>` to `open`, since `open` does not pass the caller's environment.

## Operation

Before [desktop verification](../docs/engineering/quality-gates.md) or diagnosing user state, record the host (`hostname`, `uname -sm`), checkout (`pwd`, `git rev-parse HEAD`), running app bundle path and build version, selected worktree's `rzm` path and `--version`, and actual app data directory. Confirm that the host and app match Drew's screen before interpreting a missing library. Use the override passed at launch, not the terminal's current `RHIZOME_DESKTOP_DATA_DIR`. On macOS, the default is `~/Library/Application Support/<bundle identifier>`; Rhizome and Rhizome Dev use separate identifiers.

- The library lives in `library.json` (version 3) in the native application data directory. A version 1 `folders.json` migrates on first use: folders that are worktrees of one Git repository merge, and their executables and recency carry over. A folder that was unavailable during migration keeps its own entry until discovery resolves it, or until a worktree of its repository is added, and then merges the same way. `folders.json` is left untouched. Corrupt or unsupported files produce an error and are preserved. A library change made in one window (adding or removing a repository, a primary worktree, an executable) is sent to every window's shell. Each library snapshot, in a broadcast or a command response, carries a revision that every save increments, and a shell applies only a snapshot newer than the one it holds, so a response that arrives after a later save cannot restore what that save removed.
- `RHIZOME_DESKTOP_DATA_DIR` can select a separate absolute application data directory for development or smoke tests.
- A Git repository's identity is its canonical common Git directory, so adding any of its worktrees selects the same entry. A folder outside Git is a repository with one worktree. A Rhizome folder configured below its Git working tree, such as `<repo>/docs`, is a repository whose worktrees are that subfolder of every Git worktree; its identity is the common Git directory plus the subfolder, and a Git worktree without the subfolder is listed as unavailable. The library saves such a repository under a worktree whose own configuration is the subfolder, since another worktree's unconfigured copy of it would rediscover as the whole repository. The companion discovers worktrees by reading Git metadata files (`.git`, `commondir`, `config`'s `core.worktree`, `worktrees/*/gitdir`, `worktrees/*/locked`, `HEAD`, `refs/remotes/origin/HEAD`); it never runs `git` or repository code. Worktrees Git would prune (missing and unlocked) are hidden; a locked worktree whose folder is missing stays listed as unavailable. A `git init --separate-git-dir` repository records its main checkout only in that checkout's `.git` file, so add the repository from the main checkout: added from a linked worktree, it lists only linked worktrees, as `git worktree list` does, unless `core.worktree` names the main checkout. Discovery reruns when any window gains focus, when the library changes, and every 30 seconds while a window is visible. One companion process discovers every repository at once.
- Worktrees present when a repository is added are acknowledged. One discovered later shows a dot on the toolbar's worktree and in the finders until it is opened.
- The primary worktree is the one with `origin/HEAD`'s branch checked out, otherwise the main working tree. The repository's context menu, on its toolbar name or a repository finder row's actions, can choose another, set a worktree's executable, or remove the repository from the library.
- Opening a worktree runs, per window: discovery, trust and setup checks, seeding, runtime start, then page load. The content area shows the current step and elapsed time until the page has loaded, except during the first 0.8 seconds, so reopening a running worktree shows no progress screen. Each shell numbers its selections when the user makes them, so a slower selection, such as a repository whose discovery is still running, never replaces a newer one. Reselecting a worktree reuses its page only when that page finished loading; a load that failed or timed out navigates again. When a window shows no worktree (an unavailable repository, a removed one, or an open that stopped for trust or setup), its content view leaves the runtime's page, so the page's event stream no longer keeps that runtime alive, and the app stops supervising it. Opening a configured worktree with no database, when the primary has one, first runs that worktree's own selected executable as `rzm new-worktree <primary>` (skipped when the executable lacks the command). A seeding failure offers Try again and Start without copying. A newer selection discards a slower earlier open. Different worktrees open in parallel; the same worktree is serialized and converges on one runtime.
- An unconfigured worktree shows a setup sheet instead of opening. The companion runs the executable that would set the folder up (the global one, or a Rhizome source checkout's own build once trusted) as `rzm init --check --json` with the sheet's choices, and reruns it shortly after each change, so the findings, choices, and Writes row come from that version. Set up runs `rzm init --json` with the same options and sends a typed search key only on standard input, never in arguments. When the folder is configured after the run, even if installing its pinned version failed, the app records trust for it, so opening needs no second prompt. An executable without these options gets an update prompt with Manage installation. The repository menu's What Gets Indexed… page lists every ignore rule by layer, including rules inherited from `.gitignore`, through the worktree's own `rzm index scope --json`, and writes each edit through it. Before setup, the sheet's Skip row opens the same page, which holds edits as `--skip`, `--keep-indexed`, and `--include-ignored` options until Set up.
- Runtime presence is app-wide. While any window is visible, one poller asks the companion every 3 seconds for the runtime state of every worktree in the library, and again right after a window gains focus or an open finishes. One companion process probes all worktrees concurrently, with a one-second limit for each. A worktree is running when its manifest's loopback origin, folder, process, and mode verify; starting when a live process holds its runtime but has not verified (booting, busy, or being replaced by `rzm start`), or while a window is opening it; otherwise stopped. Runtimes started or stopped from a terminal appear within a few seconds. Finder rows show a green dot for a repository or worktree that is running and an amber ring while one is starting, next to the red new-worktree dot. Shells receive only these states, never runtime addresses or tokens.
- A worktree shown in a window is kept available. The web UI's event stream counts as runtime activity, so a headless runtime does not idle-exit under it, and the app adds no keep-alive of its own. When the poller sees a displayed worktree's runtime stopped on two consecutive polls (for example after `rzm stop`, a crash, or the idle exit of an older pinned Rhizome), and no window is opening that worktree, the window shows "Rhizome stopped — reconnecting…" and reruns the open steps. Trust is already recorded, so no prompt appears unless trust is actually required. After 3 consecutive restarts without a loaded workspace the window stops retrying and shows the error with Try again; a workspace that loads resets the count. Relaunch and follow actions apply only to the selection they were computed for, so switching worktrees cancels them. So `rzm stop` on a displayed worktree is followed by a relaunch; switch the window away first to keep it stopped, or choose Stop Rhizome from the repository's context menu. That stops the runtime through the companion, as `rzm stop` does, after every window showing the worktree leaves its page and shows it sleeping. Nothing relaunches a sleeping worktree until the user opens it again, by selecting its repository or choosing Start Rhizome. When another process replaces the runtime, the app follows the replacement. A new process on the same verified origin leaves the page loaded, since the web UI reconnects its own streams. A new origin is verified by the companion, becomes the content view's only allowed origin, and is loaded. The app replaces a runtime itself in two cases. Choosing Restart Rhizome from a repository's context menu replaces that worktree's headless runtime. When a worktree runs a developer build (`rhizome.devBinaryDir` or a Rhizome source checkout), the poller watches that executable, and once a changed build holds still for one poll, every running headless worktree on it reopens on the new build. Windows showing a restarted worktree reload it. Settings lists the worktrees that run developer builds.
- Each window is a native window with two webviews (Tauri's `unstable` multi-webview feature). The shell webview draws the toolbar and status views; the repository content webview is a child positioned over the shell's content region and is hidden whenever the shell draws there. Because the content webview covers the shell, repository options use native popup menus, and the finders draw in a third, transparent webview (`shell-finder-N`) above the content view. Its label gives it the shell's capabilities and nothing more; the shell builds its rows and runs the chosen open.
- The toolbar draws the workspace page's header controls ([SPEC-0119](../docs/specs/experience/desktop-unified-toolbar.md)): the section tabs, project search, the Notes issue badge, and the keyboard shortcuts button. An initialization script sets `window.__RHIZOME_DESKTOP__` in the content webview, and the web UI then hides its own header. The page reports its section, search text, and Notes issues by setting its document title to `rhizome-desktop:` and JSON. The native layer accepts that title only while the page is on the verified runtime origin, checks every field, and relays it to the shell as a `page` message. Any other title, and every page load, clears it. Toolbar controls send a `page` request that the native layer hands the page as a `rhizome:desktop` DOM event with a fixed, serialized detail. The controls show only while the shell is not covering the page and the page has reported, so a runtime older than this contract keeps its own header and the toolbar adds nothing.
- Only `shell-*` webviews receive capabilities (`capabilities/shell.json` scopes by webview, never by window). Content webviews have no native command permissions. Their navigation stays on the verified runtime origin and its isolated HTML viewer origins (32 hexadecimal characters plus `.localhost`, on the same port). External HTTP links open in the default browser. A frame-based content area is not used because Rhizome's custom views and HTML viewer send `frame-ancestors` restrictions.
- macOS permits HTTP only for the local runtime and its localhost viewer hosts. The bundled `Info.plist` scopes its [App Transport Security exception](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppTransportSecurity/NSExceptionDomains) to `localhost` and its subdomains so isolated HTML previews load in WebKit.
- Appearance (Match System, Light, or Dark) and the chrome theme (Graphite, Slate, Spruce, Oxblood, or Indigo) are app-wide settings in `preferences.json`, chosen from View › Appearance, View › Theme, or Settings ([SPEC-0126](../docs/specs/experience/workbench-redesign.md)). Appearance applies natively, so every webview's `prefers-color-scheme` follows it. Windows and webviews take the theme's colours as their backgrounds, the shell paints the saved theme from an initialization script, and each workspace page receives a `theme` page command. A page's first paint uses the theme current when its window opened, or a newer one the page remembers from an earlier command.
- The workbench sidebar's collapsed state is app-wide too, as `sidebarCollapsed` in `preferences.json` ([SPEC-0128](../docs/specs/experience/workbench-sidebar.md)). Each runtime page receives a `sidebar` page command when it first reports and then reports `sidebarCollapsed` in its title. The toolbar's first control, the sidebar toggle, and View › Show Sidebar or Hide Sidebar (⌃⌘S) store the new state and send it to every window's page. ⌘\ pressed in the page raises the `sidebarToggles` count in its report, and the app stores and broadcasts that change the same way. A changed `sidebarCollapsed` without a higher count is a reply to the app's own command, so a late reply cannot undo a newer choice. The sidebar's width stays per repository, in the page's storage, and that repository's other windows follow it. The toggle and the menu item are disabled on GraphQL and while the window shows no runtime page that has taken the command.
- `session.json` records each window's position, size, and selected repository and worktree. Geometry is recorded when a window opens, moves, or resizes, and again on quit, so an unmoved window restores too. Session writes are serialized from snapshot to file, so a delayed save cannot overwrite a newer one. Launch restores every window from the last session. Closing a window removes it from the session; quitting (⌘Q) keeps all open windows. The last window closed while no others were open is kept, so the next launch or Dock reopen restores its layout and selection.
- Menus: File → New Window (⌘N), Switch Repository… (⌘O), Switch Worktree… (⇧⌘O), Add Repository…, Close Tab (⌘W), Close Window (⇧⌘W); Edit → Go to Note or File… (⌘P), Search This Project (⌘K), Copy Page URL (⇧⌘C); View → Reload Page (⌘R), Back, Forward, Appearance, Theme, Show Sidebar or Hide Sidebar (⌃⌘S); Rhizome → Check for Updates…, Settings… (⌘,). The repository finder lists known repositories by most recent use and fuzzy-filters them by name and path: Enter opens the highlighted one's primary checkout in this window, ⌘Enter opens it in a new window, ⌘1–⌘9 open the first nine, and → at the end of the query opens its actions. The worktree finder lists this repository's worktrees, primary first. Go to Note or File asks the page to open its ⌘P finder. Another menu command closes an open finder first. Close Tab asks the web UI to close its active note tab and never closes Home or the window. Copy Page URL copies the content view's current address (macOS only). Search This Project focuses the toolbar's search field from either webview.
- A repository's context menu also opens its runtime in the default browser (the current page when this window shows it, else the runtime's home page, starting the runtime first when it is not running), and reveals the worktree in Finder. The repository finder shows a hollow ring for a repository with no running worktree and a dashed one for the repository whose worktree this window shows sleeping.
- Both webviews disable Tauri's native file-drop handler. With it on, the native view claims every drag, so pages never receive `dragover` or `drop`, which the web UI's reordering needs. The Dock and a second launch focus an existing window or open one.
- Switching worktrees, closing a window, and quitting leave runtimes running; a worktree no window shows returns to Rhizome's normal lifecycle, so a headless runtime idle-exits after an hour without clients. The app stops a runtime only when the user chooses Stop Rhizome, and only one whose manifest and health name that worktree.
- Settings and the setup sheet show the Atomic Object team account ([SPEC-0129](../docs/specs/technical/team-api-gateway.md) US5). The native layer runs the bundled `rzm` directly as `rzm auth status|login|logout --json` in the app data directory, without provider key variables in its environment. Sign-in relays the CLI's `authorize_url` event to the window's shell as a `team` message, takes the final `signed_in` or `error` line, skips lines it does not recognise, and kills the child on Cancel, when its window closes, on quit, or after 5 minutes. One sign-in runs at a time, and only the window that started it can cancel it.
- Install Command-Line Tool links `/usr/local/bin/rzm` to the release app's bundled `rzm`; replacing or removing an existing entry requires it to point into a Rhizome app bundle. Settings can select an existing Homebrew installation or local build instead of the bundled executable.

The release app and its bundled `rzm` update together. `rzm update` through the bundle hands global updates to the app and handles repository updates separately. Repository pins, development overrides, and external managers retain their authority; the app advances a managed worktree's pin only after its Update Pin offer is accepted.
