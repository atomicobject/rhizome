## Bounded, resumable release planning and canonical publication

Public release preparation belongs to the repository-local `rhizome-release` skill. The active Codex or Claude session uses its existing subscription to synthesize and revise the release narrative. `prepare_release.py` collects source-bound evidence and deterministically applies reviewed drafts; it never launches another model, builds, tags, deploys or publishes. Normal local preparation requires no release secrets.

`release_intent.py` defines the public handoff. Fresh main and the previous version tag bind a five-file release PR: root and embedded changelogs, compiled version, `.github/release-plan.json` and `docs/releases/<version>.md`. The last file is the exact GitHub release narrative. Versions must exceed both source and prior-tag floors. Preserve human edits when refreshing an open PR against fresh main.

`ci_release_selection.py` admits only a merged same-repository `release-prep/<version>` PR into main, with matching reviewed/accepted trees, source relationship, ordinary tracked release files and strict five-file changes. All later jobs use the accepted merge SHA, not a moving branch. Ordinary merges and tag pushes do not release. Manual dispatch selects only a nonpublishing candidate.

The Release workflow builds shared web/desktop frontend assets once on Linux. `ci_release_frontend.py` binds their exact contents to source/version and validates the archive before replacing generated output. Linux builds Linux CLI binaries, the AppImage and the Mac scanner. Windows builds and signs the canonical Windows CLI and per-user NSIS installer on its native host. The protected Mac job waits for both exact native groups, verifies their manifests and hashes, then compiles Darwin binaries and Tauri, bundles, signs, notarizes and verifies the actual distribution copies. That same Mac job is the sole updater-signing coordinator. `RZM_DESKTOP_PREBUILT_FRONTEND=1` preserves the Linux frontend build while the native hook copies the exact arm64 sidecar. Final archive assembly and publication run on Linux.

`ci_release_artifacts.py` collects worker outputs, verifies Go platform/source metadata and GoReleaser version metadata, scans public content, and assembles deterministic archives with licenses, the installer, all three desktop targets and signatures, the complete updater feed, desktop provenance, checksums and a source/version manifest. Only generated `pkg/app/web/assets/dist/` changes may account for a dirty Go build; other source changes fail verification. Missing, unexpected or tampered files stop assembly.

`ci_release_publish.py` is the only public publisher. It runs in the canonical GitHub repository on trusted main, verifies the bundle, advances release/tag refs atomically without force, gates on the exact deployed gateway source, and publishes committed notes without rewriting them. Partial matching drafts resume; conflicting content stops. A complete matching release, CLI formula and Desktop cask is a no-op. The cask reuses the verified DMG and links its bundled CLI; the CLI-only formula remains. Tap-tree checks distinguish absent recipes from API failures, and partial recipe writes resume without replacing unrelated tap files. Homebrew-only recovery verifies the gateway and refs afresh before its write. Recovery reruns only failed jobs in the original workflow run, using the original verified artifact retained for 30 days. Rebuilding signed assets can change bytes at the same source and cannot replace an uploaded partial release; expired artifacts require recovery and reconciliation. GitHub and Homebrew credentials are scoped separately; read-only assembly and candidate mode never gain publication permissions.

Signing credentials live in protected CI secrets and restricted offline/1Password backups. `ci_desktop_signing.py` imports an ephemeral Keychain and materializes protected signing files; cleanup runs even after failure. `run_clean.py` passes a protected file reference through GoReleaser, while `build_desktop.py` compiles without credentials and exposes them only to signing/bundling. `apple_signing.py` handles notarization and verifies the app, mounted DMG and updater archive without credentials. The updater verifier uses the committed public key and offline locked dependencies. No provider credentials or credential files enter public artifacts.

### Evidence and private legacy orchestration

Git first-parent history defines delivery units. Curated changelog entries, verified completed efforts, PR descriptions, commits, paths and statistics enrich them. `effort_evidence.py` follows an HTML workspace's explicit Markdown work-log link at the same Git revision; missing components produce diagnostics. Governing specs must be discovered SpecLike notes under the snapshot's config and ignore rules. Working-tree content and directory proximity do not establish delivered lifecycle evidence.

With no reachable version tag, empty base fields mean first publication in this repository, not a reset of product history. Collection includes the root commit without creating a Git object. Version floors still come from the source version. Bounded packets support local editorial judgment; raw diff volume does not choose the release headline.

The private archive retains `release_cli.py`'s local model-generated plan and checkpointed publisher when `RZM_INTERNAL_S3_BUCKET` is set. Its apply requires an attached clean canonical branch at freshly fetched origin, verified private repository visibility, publishing credentials and private key inputs. Apply owns three version/changelog files and records its date before mutation. Main cuts atomically advance both canonical branches; release hotfixes integrate into main through a synthetic conflict-free merge. Resume revalidates the plan, tag and remote topology. Never force conflicting refs or turn a failed dry run into publication. The old apply/publish/resume and direct local GoReleaser entry points reject public publication.

Internal bundles are temporary compiler overlays produced by `scripts/teamkeys/release.py` after private visibility checks. Public builds reject overlays, disable persisted Go settings, strip mirror configuration and require redacted credential scans. See [credential policy](../../docs/engineering/secrets.md).

Gateway gating remains in `release_gateway.py`, exact Actions identity checks in `release_gateway_runs.py`, source agreement in `release_gateway_source.py` and tagged topology in `release_publication.py`. Every supported public/private publisher gates before uploads and rechecks refs after waiting. Trusted-main orchestration tests/builds an immutable source checkout; private publishers receive no AWS permissions. Receipts correlate an exact request/run and are reusable only within the live publishing process ancestry, not as a skip control.

- **Public entry points**: `prepare_release.py`, `ci_release_selection.py`, `ci_release_frontend.py`, `ci_release_artifacts.py`, `ci_release_publish.py`
- **Private legacy entry points**: `release_cli.py`, `cut_release.sh`, `generate_notes.py`
- **Deep docs**: [Release process](../../docs/RELEASING.md), [[../../docs/specs/technical/evidence-grounded-release-orchestration|SPEC-0078]]


## Native desktop candidates and the joined feed

`build_native_desktop.py` consumes the exact native GoReleaser CLI through `RZM_DESKTOP_PREBUILT_RZM`. It selects the Windows current-user NSIS or Ubuntu 24.04 AppImage profile, each with only the rzm sidecar. A transferred frontend uses `RZM_DESKTOP_PREBUILT_FRONTEND=1`; both Tauri phases preserve it and only stage rzm. Windows signs canonical `rzm.exe` once before packaging; the installer signer skips those finalized bytes. Compilation gets no signing credentials. Linux and Windows jobs never receive the updater key or publication permissions.

Windows production builds require protected `WINDOWS_SIGNING_CONFIG` (an argv command with one `%1` and declared environment names); `WINDOWS_SIGNING_SECRET` supplies only those named credentials. No production Windows certificate or signing service is configured for this port, so production assembly stays blocked rather than advertising unsigned packages. The independent unsigned Desktop portability workflow and installed-upgrade fixtures remain available for GUI acceptance.

The native builder extracts the final package and verifies exact sidecar inventory/hash before recording `desktop-candidate.json`. Linux inspects ELF imports/interpreter/RPATH and GLIBC requirements, rejects unresolved or non-system dependencies, and executes an isolated copy without loader overrides or developer PATH. Windows inspects DLL imports, resolves only Microsoft-signed System32 components, records DLL hashes and executes a standalone copy with system-only PATH. Immutable runtime images copy rzm alone, so an extra GCC runtime found only on developer PATH is a failed candidate. Manifests distinguish the supported baseline from the measured build host; Windows Server CI is not Windows 11 GUI evidence.

`ci_release_artifacts.py prepare-native` validates both same-run native group manifests and binds copied candidate files in `native-inputs.json` before the Mac coordinator sees signing credentials. No release-branch advance or nested workflow dispatch is required during builds. `join_desktop.py` checks this source/version-bound input set, keeps the existing verified Mac archive/signature, and uses `assemble_desktop.py` to sign final native updater bytes. Raw NSIS installers and AppImages are the updater payloads. A joined feed and `desktop-assembly.json` appear only after all three signatures verify. The Mac manifest records the canonical raw CLI hash separately from its signed packaged sidecar hash; Windows/Linux must retain exact byte equality.

Final Linux assembly retains main's deterministic archive/license contract. Each archive's CLI must match the canonical CLI hash recorded by the desktop coordinator. Native candidate packages must match the coordinator's signed bytes. `verify_bundle` checks the exact complete inventory, all hashes, source/version, updater signatures and CLI bindings before the sole CI publisher receives the bundle. Missing, unexpected, unsigned, stale or tampered platform inputs fail closed.

The nonpublishing installed-upgrade fixture uses `build_upgrade_fixture.py --target windows-x86_64|linux-x86_64 --output <fresh-directory>`. It builds exact versions `0.0.1` and `0.0.2` with a whitelisted loopback endpoint/public-key overlay and a discarded ephemeral private key. Its optional `--team-api-origin` is validated; the default `https://team.example.test` cannot complete login. The Desktop portability workflow's optional upgrade fixture job retains versioned packages/signatures/manifests, a root feed advertising `0.0.2`, public key/overlay and instructions. Serve the extracted root with `python3 -m http.server 9444 --bind 127.0.0.1`, install `0.0.1`, then invoke its updater. These retain the production application identifier, so installed checks use a disposable OS account or VM. GUI acceptance and the first real production-feed upgrade at the second public release remain separate evidence.

The exact Tauri detached signer and pinned Rust verifier were exercised with an ephemeral test key; `desktop_signer_roundtrip_test.py` is opt-in. This proves cryptographic payload/signature handling, not native installed upgrades. Candidate, dependency, native builder, shared-frontend, coordinator, bundle and workflow contracts have focused Python tests. Full native builds and signing behavior belong to CI and the installed-app acceptance checklist.


Validated candidate-only Release runs retain the full build pipeline, including Mac notarization and the same updater coordinator. Windows may remain unsigned in that explicit mode. Every CI group and final release manifest records `candidate_only` as a Boolean, and desktop assembly records `candidateOnly` plus `production: false`. Collection, coordinator input validation, assembly and bundle verification take an explicit candidate mode; their production defaults reject it. The public publisher also independently requires `candidate_only: false` and production desktop proofs before any write. This mode grants no deployment/publication authority and does not introduce another signing service or key owner.

The sole public CI publisher resumes only immutable matching drafts with the committed notes. Advertisement authenticates every uploaded byte, publishes with latest promotion disabled, verifies anonymous versioned assets, signatures and the complete feed, then promotes and smoke-tests latest with recovery. Both fixed Homebrew recipe hashes derive from that verified inventory and remain deferred until advertisement completes; partial CAS writes resume independently. Gateway, advertisement, recipe and tap proofs share one same-run retained `release-state` directory. Advertisement and tap helper modules have no standalone public writing CLI.
